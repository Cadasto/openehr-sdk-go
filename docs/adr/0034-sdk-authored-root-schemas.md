# ADR 0034 — Each generation target's root is an SDK-authored BMM schema over the pinned openEHR schemas; the ADL 1.4 operational template is modelled from Template.xsd

- **Status:** Accepted, 2026-11-02 — maintainer decision on [PR 360](https://github.com/Cadasto/openehr-sdk-go/pull/360), taken after the AM Release-1.4 schemas were compared with the pinned AOM 1.4 BMM and the OPT corpus validated against `Template.xsd`.
- **Amended 2026-11-02** (maintainer decisions taken in the delivery of REQ-176): (a) what P_BMM has no construct for, such as a class a target leaves out or a name for a schema's anonymous type, goes into SDK extension keys of the root JSON, each entry with its reason and upstream reference, which the generator reads, so still no Go table names a class ([§ REQ-041 *SDK-authored root schemas*](../specifications/bmm-conformance.md#sdk-authored-root-schemas)); the roots are held to that by the root check, a Go test, in place of the BMM checker the *Consequences* below name, which the tree does not hold. (b) The loader's include merge resolves a diamond: where two includes bring one class in two forms and one form's schema descends from the other's, the descendant's form wins, so the AOM 1.4 root includes the RM root and receives the RM form of `AUTHORED_RESOURCE` without declaring it ([§ REQ-045](../specifications/bmm-conformance.md#req-045--bmm-loader-is-a-building-block), ADR 0002 D2). (c) The round trip of [§ REQ-176](../specifications/clinical-modeling.md#req-176--adl-14-operational-template-model) compares the two documents normalised, a `Hash` member's entries as a set and numbers by value among the rules, and the encoder writes `Hash` entries sorted by key; the RM resource classes take the AM Release-1.4 shape everywhere, keyed by language with no `id`. (d) `OPERATOR_KIND` and the type of `timezone_validity` are integer enumerations, written as their integer codes in both canonical formats, since FerroEHR 5.5.0 refuses the `timezone_validity` words on template upload. (e) An `xsi:type` value under any prefix bound to the XML Schema namespace reads as its BMM primitive, and any other prefixed value is still refused ([REQ-056](../specifications/wire.md#req-056)).
- **Amended 2026-11-03** (maintainer decision): the AOM 1.4 root's id is `openehr_operational_template_1.4.0`, since the names the model's delivery gives spell out "operational template" and keep "OPT" for the file format; and STRAND-17, which this record opened, is resolved by [ADR 0035](0035-compile-step-reads-operational-template-model.md).

## Context

**What the pinned schemas cannot say.** The SDK generates its openEHR types from the BMM schemas it pins ([REQ-041](../specifications/bmm-conformance.md#req-041--pinned-bmm-sources)), and REQ-041, before this decision, said that the BMM wins over any other statement, that hand-written code embeds no out-of-band knowledge of openEHR types, and that a suspected BMM defect is raised upstream rather than worked around. For the ADL 1.4 operational template, the documents a CDR and every ADL 1.4 tool exchange, the pinned schemas fall short in four ways:

- No BMM defines the OPT 1.4 classes. AOM 1.4 refers to a Template Object Model that openEHR never released; the AM Release-1.4 `Template.xsd` (`OPERATIONAL_TEMPLATE`, `C_ARCHETYPE_ROOT`, `FLAT_ARCHETYPE_ONTOLOGY`, `ANNOTATION`, `T_VIEW`, `T_CONSTRAINT`, `T_ATTRIBUTE`, `T_COMPLEX_OBJECT`, `C_CODE_REFERENCE`) is the only formal definition, and the pinned ITS-XML closure vendors it.
- The AOM 1.4 BMM includes only BASE 1.3.0, so `ARCHETYPE` inherits the BASE form of `AUTHORED_RESOURCE` (`uid`, `annotations`, `original_language` as a `TERMINOLOGY_CODE`, no `revision_history`). The AOM 1.4 specification names the RM `common.resource` package as its dependency, the RM Common IM keeps that package for ADL 1.4 only and names the BASE one as its successor for ADL 2, and the AM Release-1.4 `Resource.xsd`, `Template.xsd` and every OPT carry the RM form. The `rm` package already holds the RM form of the five classes BASE and RM both declare, by the loader's rule that a root shadows its include; `aom14.Archetype` is the one place the BASE form reaches.
- The AM Release-1.4 schemas and the AOM 1.4 BMM disagree in about twenty places, and the OPTs tools write follow the schemas: three class names (`C_CODE_PHRASE`, `C_DV_ORDINAL`, `C_DV_QUANTITY` for the BMM's `C_CODED_TEXT`, `C_ORDINAL`, `C_QUANTITY`), `ARCHETYPE_TERM.code` as an attribute and its `items` as a list, the ontology's definition and binding sets, the date and time constraints' `pattern` against the BMM's validity flags, `C_QUANTITY_ITEM.precision`, `C_DV_SCALE` and `C_DV_STATE` in the schema only, and `units_system` and `units_display_name`, which neither declared until [specifications-ITS-XML PR 15](https://github.com/openEHR/specifications-ITS-XML/pull/15) and [specifications-AM PR 48](https://github.com/openEHR/specifications-AM/pull/48). Of the corpus's 74 OPTs, 65 validate against the ITS-XML `master` schemas once the legacy `match_negated` element is removed; all 74 validate as written against the current pin, an upstream integration branch that merges the open specifications-ITS-XML pull requests [15](https://github.com/openEHR/specifications-ITS-XML/pull/15), [16](https://github.com/openEHR/specifications-ITS-XML/pull/16) and [17](https://github.com/openEHR/specifications-ITS-XML/pull/17).
- The RM BMM misspells `TRANSLATION_DETAILS.accreditation` as `accreditaton`; the AM Release-1.4 and BASE schemas and ITS-JSON spell it right, so the generated encoder writes an element the schemas refuse. The fix is upstream, [specifications-RM PR 43](https://github.com/openEHR/specifications-RM/pull/43), and reaches the pin only through ITS-BMM's sync and a re-pin.

**The forces.** Wherever this knowledge lives, REQ-041 keeps it out of hand-written Go; the OPT classes need the codecs every other class has; and each published schema will be re-pinned, closing some differences and leaving others. Two mechanisms exist already: the loader lets a root schema's class shadow an include's class of the same name ([ADR 0002 D2](0002-bmm-codegen-decisions.md#d2--descendant-shadows-ancestor-bmm-include-merge)), and the generator reads the ITS-XML schemas for the XML binding (D10). The first form of [PR 346](https://github.com/Cadasto/openehr-sdk-go/pull/346) took a third route, bridging five differences with three tables in the generator and a decoder stand-in.

**Why this is a fork.** Where the SDK's knowledge of what the published schemas lack lives decides the shape of the generator, generic over a BMM and the ITS-XML schemas or a bridge for one model, the names the generated AOM 1.4 types carry, and what a re-pin of a published schema means. Each is repeated in every generated file.

## Decision

**Each generation target's root is a P_BMM schema the SDK authors, which includes the pinned openEHR schema and declares only what the pinned ones lack or get wrong; the generator stays generic.** [§ REQ-041 *SDK-authored root schemas*](../specifications/bmm-conformance.md#sdk-authored-root-schemas) states the rules: what a root may declare, that every declaration names its reason and its upstream reference, that a correction leaves the root in the commit that pins the upstream fix, and what the roots are. The AOM 1.4 target's root, `openehr_operational_template_1.4.0`, declares the operational template classes from `Template.xsd`, binds `AUTHORED_RESOURCE` to the RM `common.resource` form, and restates each AOM 1.4 class whose AM Release-1.4 schema type differs from the pinned BMM in the schema's form, including the three class names, so a generated type, its `_type` and its `xsi:type` carry one name and the BMM-named class is left out. The RM target's root carries the `accreditation` spelling until the RM schema is re-pinned. [§ REQ-176](../specifications/clinical-modeling.md#req-176--adl-14-operational-template-model) states the contract the OPT model meets: a schema-valid OPT decodes with no unmatched content and encodes back to a schema-valid document of the same content, with `match_negated` the one element read and dropped.

The generator takes from the ITS-XML schemas what the BMM cannot say about the XML binding, as a generic rule over every class: child order, as ADR 0002 D10 already has it, and which members are XML attributes, which D10 now covers in place of the generator's name check on `archetype_node_id`. It carries no table about a named class, so a model declared in P_BMM gets the same codecs as every other class, with no generator feature beyond what any BMM member needs.

**Not taken.** Bridging tables in the generator: every difference becomes a row of generator code, the generator becomes a special case of one model, and the knowledge it carries is the out-of-band knowledge REQ-041 keeps out of hand-written code. A hand-written model, in `aom14` or a package of its own: it contradicts REQ-041 and needs codecs that repeat the generated codecs' rules. Editing a pinned schema in place, which `make bmm-check` refuses and which would hide the divergence a re-pin has to resolve. Waiting for upstream before decoding OPTs at all: the OPT model has no upstream to wait for, and the pull requests that converge the AM 1.4 schemas and BMM take their own time.

## Consequences

- **Easier:** a schema-valid OPT decodes into generated types with the codecs every other class has, and encodes back without loss. Closing a difference between the schemas and the BMM is an edit to one JSON schema under review, with its reason beside it, not generator code. A correction and its upstream reference travel together, so a re-pin deletes exactly the rows upstream closed, and the OPT root is, in form, the model openEHR never published, which can be proposed upstream as it stands.
- **Harder:** the SDK owns a model that diverges from the published BMM, by design and per class, so a reader of the generated code reads the root to learn why a class differs from the specification's table. A re-pin of the AM or RM schema can collide with a shadow the root still carries; the gate shows it and the shadow goes. The roots are hand-written sources, so the BMM checker runs on them in the gate, where the pinned files have only their hashes checked. Canonical XML has to model `Hash` members, which it skipped, so `rm`'s resource classes gain that shape too.
- **Permanently constrained:** the AOM 1.4 Go types carry the AM Release-1.4 schema names where the BMM names a class otherwise, `aom14.CCodePhrase` and not `CCodedText`, which no non-test package imports today and which the pre-1.0 policy allows. `openehr/rm` holds the RM form of the classes BASE and RM both declare; the BASE form, which AOM 2 uses, goes into AOM 2's own package when that target is wired in, and the `aom14 → rm` import stays one-way (D5).
- **Left open:** what becomes of the OPT parser of REQ-100 once the model reads the same documents losslessly (STRAND-17), decided on the model's decode cost and the parser's consumers, not here; and STRAND-15's capture question, which this decision does not touch: `match_negated` is dropped, not kept.
