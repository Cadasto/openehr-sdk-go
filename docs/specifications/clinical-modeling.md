# Clinical modeling

**Status:** Draft

Normative contract for the SDK's clinical-modeling artefacts: operational templates (OPT), templated composition assembly, validation against templates, and AQL path semantics on templated trees. Covers REQ-100 onwards.

The "clinical modeling" band sits above the openEHR Reference Model and below the REST clients: it consumes RM types from `openehr/rm/` and AOM 1.4 constraint types from `openehr/aom/aom14/`, and produces typed building blocks usable by `openehr/composition/`, `openehr/validation/`, and `openehr/aql/`.

---

## REQ-100 — ADL 1.4 operational template (OPT) parse and paths

The SDK **MUST** ship a parser for ADL 1.4 **operational templates** (OPT) as a building-block package: `openehr/template/`. Authoring-time templates (`.oet`) are out of scope in v1.

### Scope

In openEHR terminology, "template" without qualification often means the authoring template (`.oet`). In this SDK v1, **"template" in package and REST names means operational template (OPT)** unless explicitly stated otherwise.

- **Input format:** ADL 1.4 OPT XML — root element `<template>` in namespace `http://schemas.openehr.org/v1` (the canonical Ocean Template Designer XSD form), wire `application/xml` (same as `definition.FormatADL14` in `openehr/client/definition/`). The parser **MUST** accept `<?xml ?>` declarations, BOM-prefixed UTF-8, and namespaced XSD-typed children (`xsi:type` discrimination on `attributes` and `children`). A document whose root is `<OPERATIONAL_TEMPLATE>`, as some tools export, is refused with `ErrInvalidOPT`; a caller renames the root before parsing.
- **File extension:** `ParseFile(path string)` **MUST** reject paths that do not end in `.opt` (case-insensitive) with `ErrNotOPTFile` to keep the v1 surface unambiguous. `ParseOPT(io.Reader)` accepts any reader and applies no path check.
- **Output:** `*OperationalTemplate` carrying the parsed wrapper fields (template id, concept, uid, language) plus the definition tree (`Node` interface).

### Identity fields

`*OperationalTemplate` **MUST** expose at least:

- `TemplateID() string` — the value of `<template_id>/<value>` (e.g. `vital_signs`).
- `Concept() string` — the value of `<concept>` (machine-readable concept slug).
- `UID() string` — the value of `<uid>/<value>` when present; empty string otherwise.
- `Language() string` — the value of `<language>/<code_string>` (ISO 639-1) when present; empty string otherwise.
- `Root() Node` — the root definition node. Its `RMTypeName()` is the composition RM class (conventionally `COMPOSITION`). The concrete type is `*ArchetypeRoot` when the OPT `<definition>` carries an explicit archetype id (the typical Ocean Template Designer shape) and `*ComplexObject` otherwise. A caller that descends into attributes handles both, through a type switch, through `ObjectNode`, the supertype of `*ComplexObject` and `*ArchetypeRoot`, or through `NodeAt`.

### Provenance metadata (optional)

`*OperationalTemplate` **MAY** additionally expose top-level OPT provenance for auditing and editor tooling:

- `Description() *Description` — parsed `<description>` block; nil when omitted. The returned `*Description` exposes `LifecycleState() string`, `OriginalAuthors() map[string]string`, and `OtherDetails() map[string]string`. The returned maps are defensive copies — mutation by the caller does not affect the underlying template.
- `Annotations() map[string][]Annotation` — parsed `<annotations path="...">` blocks keyed by the path attribute (empty string when no path). Returns nil when the OPT carries no annotations. The returned map is a defensive copy.

### Node taxonomy

The parsed definition tree is a closed taxonomy. `Node` is a sealed interface implemented by:

| Concrete | OPT XML shape | Carries |
|---|---|---|
| `ComplexObject` | `xsi:type="C_COMPLEX_OBJECT"` | `RMTypeName()`, `NodeID()`, `NodeName()` (template-level node name — the fixed `C_STRING` pinned on the `name` attribute, `""` when absent; [REQ-116](#req-116--template-level-node-naming-and-name-predicated-paths)), child `Attribute` list, optional occurrences |
| `Attribute` | `xsi:type="C_SINGLE_ATTRIBUTE"` or `C_MULTIPLE_ATTRIBUTE"` | `Name()` (RM attribute name), `Cardinality()` (single vs multiple), child `Node` list |
| `ArchetypeRoot` | `xsi:type="C_ARCHETYPE_ROOT"`, or `T_ARCHETYPE_ROOT`, which some exporters write for the same shape, Code24's among them (openEHR [`Template.xsd`](https://github.com/openEHR/specifications-ITS-XML/blob/master/components/AM/Release-1.4/Template.xsd) defines only the former) | `ArchetypeID()` (e.g. `openEHR-EHR-OBSERVATION.blood_pressure.v1`), `TemplateID()` (the optional `<template_id>/<value>` that `Template.xsd` allows on an archetype root, which may differ from the template's own `TemplateID()`, `""` when absent), plus the same surface as `ComplexObject` |
| `Slot` | `xsi:type="ARCHETYPE_SLOT"` | `Includes()` / `Excludes()` archetype-id assertion lists (lists may be empty) |

Concrete primitive constraints (`C_CODE_PHRASE`, `C_PRIMITIVE_OBJECT`, `C_DV_QUANTITY`, etc.) appear as **leaf `ComplexObject`** values (`RMTypeName()` returns the RM class name, no attribute children). The typed primitive-constraint surface lives on `ComplexObject.PrimitiveConstraint()` and is enumerated under REQ-103.

In its default and its strict mode alike, the parser **MUST** read `xsi:type="T_ARCHETYPE_ROOT"` as `C_ARCHETYPE_ROOT`, with its archetype id, term definitions and subtree, and an `<attributes>` whose `rm_attribute_name` is `null_flavor`, on a node whose `rm_type_name` is `ELEMENT`, as the attribute `null_flavour`, unless that node also declares an attribute named `null_flavour`. The first is a recognised spelling of the same node, never an unknown type, so lenient mode does not reduce it to a leaf and strict mode does not refuse it. The second is the US spelling some OPTs write, which no RM class declares; read so, its constraint applies to the RM attribute `ELEMENT.null_flavour`, as EHRbase and FerroEHR both accept such a template and FerroEHR applies its constraint under the RM name. Where the node declares both, `null_flavor` is kept as written, so the node does not declare `null_flavour` twice: the `null_flavour` constraint applies, and the compile marks `null_flavor` ([§ REQ-111](#req-111--public-compiled-template-bridge) *Attributes the RM does not have*). `null_flavor` is the only attribute name the parser reads otherwise than as written.

Both modes **MUST** read each identifier the OPT writes without its leading and trailing white space, as Unicode defines it (XML's space, tab, carriage return and line feed among it), as they read codes, terminology ids and list entries: the `xsi:type` of an `<attributes>`, a `<children>` or an `<item>`, each `rm_attribute_name`, `rm_type_name` and `node_id`, the `<value>` of an `archetype_id` or a `template_id`, and the `path` of an `<annotations>`. A pretty-printed OPT can break the line inside such an element, writing `<rm_attribute_name>defining_code` with `</rm_attribute_name>` on the next line, and no identifier holds white space at either end. An identifier that holds only white space therefore reads as an empty one, and a name this section says the parser keeps as written is kept without that white space.

The parser keeps every other attribute name as written, whether or not the node's RM class has it, since it does not import the RM ([module-layout.md § REQ-013](module-layout.md#req-013--building-block-independence)). The compile step marks each declared attribute no instance of the node's class can carry ([§ REQ-111](#req-111--public-compiled-template-bridge) *Attributes the RM does not have*).

### Path syntax (subset)

The parser **MUST** accept the following openEHR path subset and reject anything else with `ErrPathSyntax`:

- Absolute paths only — leading `/`.
- Segments are RM attribute names: `/content`, `/data/events/data/items`.
- Optional **archetype node predicate** on a segment: `/content[openEHR-EHR-OBSERVATION.blood_pressure.v1]` or `/items[at0001]`.
- Multiple predicates on the same segment are **NOT** supported in v1 (e.g. no `[at0001,name="Systolic"]`).
- Trailing slash is **NOT** permitted.
- AQL projection syntax (`/value/magnitude`, `[name='...']`) is **NOT** part of this REQ — that surface belongs to `openehr/aql/`.

### Resolution semantics (`NodeAt`)

Given a parsed `Path`, `NodeAt`:

- Walks `Root()` → child attributes → child nodes recursively.
- Matches segment names against `Attribute.Name()` (exact, case-sensitive).
- Matches segment predicates against `Node.NodeID()` (at-codes) **or** `ArchetypeRoot.ArchetypeID()`.
- Returns `ErrPathNotFound` if no node matches a segment.
- Returns the first matching node when a segment has multiple candidates without a predicate (deterministic by document order).

`NodeAt` accepts variadic `ResolveOption` values. `WithStrictPaths()` switches to strict resolution: a predicate-less segment that matches an attribute with more than one candidate child returns `ErrAmbiguousPath` instead of silently selecting the first child. The default (no option) preserves the first-match behaviour above. `ValidatePath(p Path, opts ...ResolveOption) error` is a shorthand for `NodeAt` that discards the resolved node — convenience for code-generator preconditions.

### Intervals

The parser **MUST** read every interval it parses by [wire.md § REQ-169](wire.md#req-169--interval-boundary-flag-defaults), the `occurrences`, `existence` and `cardinality` intervals, the numeric ranges of `C_INTEGER`, `C_REAL` and `C_DV_QUANTITY`, and the temporal ranges of `C_DATE`, `C_TIME`, `C_DATE_TIME` and `C_DURATION`, and return every `Multiplicity`, which carries the first three and counts whole items, closed on each bounded side: an excluded end becomes the closed end it denotes (`0..<3` is `0..2`, `>0..*` is `1..*`). An interval that closing leaves empty, such as `>2..<3`, and an excluded end whose closed end the parser's integer cannot hold (`>` the largest integer on a lower side, `<` the smallest on an upper one), which would otherwise wrap around, **MUST** be refused like an inverted one. An unbounded side keeps no bound whatever its included flag says. A numeric range keeps its included flags as `NumericRange` does, and a temporal range as `TemporalRange` does (REQ-103).

### Strict parse mode (optional)

The default `ParseOPT` / `ParseFile` entry points are forward-compatible: they admit an unknown child `xsi:type` as a leaf `*ComplexObject`, and read a value the OPT's schema does not allow in a weaker form. `ParseOPTStrict` / `ParseFileStrict` opt into strictness, for validators and code generators that surface unsupported shapes rather than silently truncate them. Strict mode refuses an unknown child `xsi:type` that carries nested `<attributes>` with `ErrUnsupportedNode` (§ Error taxonomy), since the default mode, which admits it as a leaf, drops a non-trivial subtree there. Each shape below **MUST** make the strict entry points fail with the sentinel it names, and be read by the default ones, without an error, in the weaker form it names:

- a `CONSTRAINT_REF` with no `reference`, or a blank one: strict mode fails with `ErrInvalidOPT`, and the default mode reads it with an empty `Reference`, as it keeps a weaker constraint elsewhere. Either mode reads a `CONSTRAINT_REF` as a leaf carrying its `ConstraintRef` primitive constraint (REQ-103), with its `reference`;
- an `<attributes>` or `<children>` element inside `<definition>`, or an `<item>` of a `C_PRIMITIVE_OBJECT`, that carries no `type` attribute in the XSI namespace (`http://www.w3.org/2001/XMLSchema-instance`): one with no `type`, an empty one, or one whose prefix is bound to another namespace, such as a misspelt one. Strict mode fails with `ErrInvalidOPT`: ITS-XML makes `C_ATTRIBUTE`, `C_OBJECT` and `C_PRIMITIVE`, the declared types of those elements, abstract ([`Archetype.xsd`](https://github.com/openEHR/specifications-ITS-XML/blob/master/components/AM/Release-1.4/Archetype.xsd)), so a valid document names a concrete type on each; `<definition>` itself is declared `C_ARCHETYPE_ROOT` by `Template.xsd` and needs none. The default mode reads such an `<attributes>` as `C_SINGLE_ATTRIBUTE`, such a `<children>` as `C_ARCHETYPE_ROOT` where it carries an archetype id and as `C_COMPLEX_OBJECT` otherwise, and such an `<item>` as no constraint, losing any constraint its type would have carried;
- the constraint values [§ REQ-103](#req-103--primitive-constraint-introspection) *Validate contract* names: a `timezone_validity` that names no `VALIDITY_KIND`, a mandatory one on a `C_DATE`, and a temporal range bound that is not ISO 8601 text of its type. Strict mode fails with `ErrInvalidOPT`, and the default mode reads each as that section says.

Beyond these shapes and the unknown child type above, strict mode refuses what the default mode refuses and no more: it does not check a missing `language` with `original_language` in its place, a top-level archetype id, or empty description fields.

### Error taxonomy

The package **MUST** expose these typed sentinel errors:

| Sentinel | Triggered by |
|---|---|
| `ErrInvalidOPT` | malformed XML, missing required wrapper element (template_id, definition), unsupported root element, and in strict mode a `CONSTRAINT_REF` with no `reference`, an `<attributes>` or `<children>` inside `<definition>` with no type in the XSI namespace, and an `<item>` of a `C_PRIMITIVE_OBJECT` with none, and the constraint values [§ REQ-103](#req-103--primitive-constraint-introspection) *Validate contract* refuses in strict mode: a temporal range bound that is not ISO 8601 text of its type, a `timezone_validity` that names no `VALIDITY_KIND`, and a mandatory one on a `C_DATE` |
| `ErrNotOPTFile` | `ParseFile` called with non-`.opt` path |
| `ErrPathSyntax` | path string fails the grammar subset above |
| `ErrPathNotFound` | parsed path traverses through an unknown attribute or unmatched predicate |
| `ErrAmbiguousPath` | strict mode (`WithStrictPaths`) — predicate-less segment matches an attribute with multiple candidate children. Never returned by the default first-match behaviour. |
| `ErrUnsupportedNode` | encountered an `<attributes>` element whose `xsi:type` is outside the v1 attribute taxonomy (`C_SINGLE_ATTRIBUTE`, `C_MULTIPLE_ATTRIBUTE`). Unknown **child** `xsi:type` values are not surfaced through this sentinel by default — they are admitted as leaf `*ComplexObject` nodes (forward-compatible escape hatch). In strict mode (`ParseOPTStrict` / `ParseFileStrict`), an unknown child `xsi:type` that carries nested `<attributes>` is rejected via this sentinel. |

All errors wrap context with `fmt.Errorf("...: %w", err)`; callers compare with `errors.Is`.

### Out of scope (v1)

- **OET** (`.oet` authoring/design-time templates) — no parse, no OET→OPT compile.
- **ADL 2 operational templates** — covered by a later REQ when consumer demand surfaces.
- **Full Archie-style linker** — archetype slot resolution against an external archetype repository. v1 reads only the OPT-embedded constraint tree.
- **Terminology expansion** — external terminology calls.
- **Runtime template registry** — the CDR owns the deployment registry; this package interprets bytes.

- **Probes:** PROBE-022 (path resolution against fixture OPT)

## REQ-108 — Untrusted document bounds

Clinical-modeling and codec entry points **MUST** bound how much untrusted input they read and how deeply they recurse, so hostile OPT XML, BMM JSON, uploaded templates, or crafted canonical JSON cannot exhaust memory or CPU before the caller's own policy kicks in. Two threats need no guard beyond these bounds. Go's `encoding/xml` does not expand DTD entity declarations and refuses an undeclared entity, so OPT parsing is open to neither external-entity injection nor entity expansion. `C_STRING` patterns compile with Go's `regexp` (RE2, linear time), so a crafted pattern cannot backtrack catastrophically.

The size limit **MUST** be 32 MiB for an OPT, an uploaded template and a BMM document, the depth limit 128 levels for the OPT tree and its path walk, and the decode depth limit 512 levels below the document root for an RM value: each leaves wide room above real templates, schemas and records while still bounding memory and recursion.

### OPT parse and path walk (`openehr/template/`)

- `ParseOPT` and `ParseFile` **MUST** refuse an input larger than the size limit with an error wrapping `ErrInvalidOPT` whose message says `input exceeds N bytes`.
- The tree build and the path walk **MUST** refuse nesting deeper than the depth limit, wrapping `ErrInvalidOPT` on a parse and `ErrPathNotFound` on a path walk.

### BMM load (`openehr/bmm/`)

- `bmm.Load` **MUST** refuse an input larger than the size limit with `bmm.ErrInputTooLarge`. See also REQ-045.

### Definition template upload (`openehr/client/definition/`)

- `UploadTemplate` **MUST** apply the OPT parse's size limit before it forwards bytes to the CDR.

### Polymorphic JSON decode (`openehr/rm/typereg/`)

- An RM value that opens deeper than the decode depth limit below the document root **MUST** be refused with `typereg.ErrMaxDepthExceeded` on every canonical-JSON decode route, `Registry.Decode`, `canjson.Unmarshal`, `canjson.Decoder`, and a bare `encoding/json/v2` or v1 `encoding/json` caller of the generated methods; on the two routes that buffer a value, `Registry.Decode` for its document and a polymorphic slot for its value, so is any bracket of that value deeper than the limit. Nesting below which no RM value opens, inside a declared array, an `any` or map member, or an undeclared member, counts toward the limit only on those two routes; outside a buffered value, `jsontext`'s own limit of about 10 000 levels bounds it. See [ADR 0002](../adr/0002-bmm-codegen-decisions.md) and REQ-040.

## REQ-103 — Primitive constraint introspection

The SDK **MUST** expose every OPT primitive constraint as a typed value attached to its leaf node, so validators and composition-builder consumers can introspect ranges, allowed lists, patterns, units, and code lists without re-parsing the OPT XML. The `constraints` package does not import the OPT parser, so code generators and downstream validators can use the constraint types alone ([module-layout.md § REQ-013](module-layout.md#req-013--building-block-independence)).

### Scope

The closed set of REQ-103 primitive constraints maps **one-to-one** to ADL 1.4 OPT XSD primitive `xsi:type` values:

| OPT `xsi:type` | Go type (`openehr/template/constraints/`) | Surface |
|---|---|---|
| `C_BOOLEAN` | `CBoolean` | `TrueValid`, `FalseValid`, optional `Default` |
| `C_INTEGER` | `CInteger` | `Range`, optional closed `List`, optional `Default` |
| `C_REAL` | `CReal` | `Range`, optional closed `List`, optional `Default` |
| `C_STRING` | `CString` | `Pattern` (regex), optional `List`, `ListOpen` (closed `List` when false, open when true), optional `Default` |
| `C_DATE` | `CDate` | `Pattern` (ADL 1.4 date pattern, raw), `Range` (`TemporalRange`), `TimezoneValidity` |
| `C_TIME` | `CTime` | `Pattern` (ADL 1.4 time pattern, raw), `Range` (`TemporalRange`), `TimezoneValidity` |
| `C_DATE_TIME` | `CDateTime` | `Pattern` (ADL 1.4 date/time pattern, raw), `Range` (`TemporalRange`), `TimezoneValidity` |
| `C_DURATION` | `CDuration` | `Pattern` (ADL 1.4 duration pattern, raw), `Range` (`TemporalRange`) |
| `C_CODE_PHRASE` | `CodePhrase` | `Terminology`, optional `CodeList`, `External()` predicate |
| `C_DV_QUANTITY` | `DvQuantity` | enumerated `Units` (each with magnitude / precision `NumericRange`), optional `Property` (CodedTermRef), `PropertyUnits` (the UCUM units the property admits, primary units first) |
| `C_DV_ORDINAL` | `CDvOrdinal` | `Values` (closed list of `(int, CodedTermRef)` pairs) |
| `CONSTRAINT_REF` | `ConstraintRef` | `Reference` (the `ac` code that names the value set; the node's `RMTypeName()` is the RM type it constrains, typically `CODE_PHRASE`). The value set is external terminology, so `Validate` reports no violation for a value of that RM type ([§ REQ-102](#req-102--composition-validation) *Terminology binding value-set*) |

Each type implements the sealed interface `constraints.PrimitiveConstraint`:

```go
type PrimitiveConstraint interface {
    Validate(value any) []Violation
    isPrimitive()              // unexported — closes the interface
}
```

The set is closed by `isPrimitive()`; new primitive shapes appear in the `constraints` package only, behind their own REQ.

### Accessor

- `template.ComplexObject.PrimitiveConstraint() constraints.PrimitiveConstraint` — returns the typed value when the wire `xsi:type` was a primitive; returns nil for non-primitive nodes (composition root, archetype roots, slots, plain complex objects).
- `templatecompile.CompiledNode.PrimitiveConstraint() constraints.PrimitiveConstraint` — same value, threaded through the compile step unchanged.

### Validate contract

`Validate(value any) []Violation` returns nil when the input satisfies every clause of the constraint, or one `Violation` per failing clause (range, list, pattern, …). Validators **MUST** be pure functions with no I/O, and the reflection rule of [idiom.md § Generics and reflection](idiom.md#generics-and-reflection) applies to them unchanged. Each accepts a small fixed set of Go input types. Concretely:

- Integer / real validators accept any Go integer kind (`int`, `int8`..`int64`, `uint`, `uint8`..`uint64`). `uint` and `uint64` values exceeding `math.MaxInt64` return `CodeWrongType` rather than silently wrapping. `CReal.Validate` additionally accepts `float32` / `float64`.
- String, date, time, date-time, duration validators accept Go `string`.
- `CString.Validate` **MUST** match `Pattern` against the whole string, as if written `^(?:Pattern)$`, so a value that only contains a match is a `CodePatternMismatch`: the AOM leaves the match mode open, and the SDK reads the pattern as whole-string because the specification's own examples (`/.+/`, `/km\/h|mi\/h/`) read most naturally that way and Archie, a widely used AOM implementation, matches with Java `String.matches`, which is whole-string.
- `CString.ListOpen` carries the AOM 1.4 `C_STRING.list_open` attribute, "True if the list is being used to specify the constraint but is not considered exhaustive" (AOM 1.4, class `C_STRING`). When it is true, `CString.Validate` **MUST NOT** report a value outside `List`, since the list is not exhaustive; it still checks `Pattern` when one is set. When it is false, `List` is closed, and a value outside a non-empty `List` is a `CodeNotInList`. AOM 1.4 makes the attribute mandatory, but the ITS-XML AM 1.4 schema (`Archetype.xsd`, complex type `C_STRING`) makes the `list_open` element optional and gives it no default, so the parser **MUST** read an absent or empty element as false: a list stays closed unless the OPT opens it. Text that is not a boolean fails the parse, as it does for the `C_BOOLEAN` flags. With a `List`, open or closed, `ExampleValue` returns the first entry that `Pattern` matches, in the whole-string reading `Validate` applies, or the first entry when no `Pattern` is set. When `Pattern` matches no entry, a closed list admits no value at all, so it has no example `Validate` accepts (§ *Example value emission*); `ExampleValue` then still returns the first entry. An open list bounds nothing: with no `Pattern` set `Validate` accepts its example, as it accepts any string.
- `CDate`, `CTime` and `CDateTime` **MUST** report a value their `Pattern` does not admit as a `CodePatternMismatch`. They read the pattern as ADL 1.4 reads a date, time or date/time pattern (ADL 1.4, *Constraints on Dates, Times and Durations*, *Patterns*), its letters in either case, since OPTs write both (`yyyy-mm-ddTHH:MM:SS`). A field written in its letters, or as a literal number (`1995-??-XX`), is mandatory, and a literal requires that value. A field written `??` is optional, and one written `XX` is not allowed. A fraction is allowed wherever seconds are. A trailing timezone pattern makes a zone mandatory: `Z` admits `Z` only, and `±hh`, `±hh:mm` or `±hhmm`, signed `+`, `-` or `±`, admits any zone the RM parse accepts, `Z` included, and without one a zone is optional. ADL 1.4 reads `±hh` as an hours-only zone and `±hh:mm` as a full one; the SDK requires a zone but does not hold it to the shape the suffix writes, so `±hh:mm` admits `+01` and `±hh` admits `+05:30`. The ITS-XML pattern grammars of `C_TIME` and `C_DATE_TIME` (`Archetype.xsd`) carry no zone suffix, so only an OPT that breaks that schema, or a constraint built in code, reaches the suffix. An empty `Pattern` constrains nothing. A pattern outside that grammar, or one that breaks its validity rules for `??` and `XX`, is malformed (below).
- `CDate`, `CTime` and `CDateTime` carry as `TimezoneValidity` the `timezone_validity` that the ITS-XML `C_DATE`, `C_TIME` and `C_DATE_TIME` (`Archetype.xsd`) write beside `pattern`, a `VALIDITY_KIND` (`1001` mandatory, `1002` optional, `1003` disallowed). The parser **MUST** read `1001` as mandatory and `1003` as disallowed, and `1002`, an absent element or an empty one as optional, the zero value. Any other text is a shape strict mode refuses ([§ REQ-100](#req-100--adl-14-operational-template-opt-parse-and-paths) *Strict parse mode*): `ParseOPTStrict` fails with `ErrInvalidOPT` on it, and `ParseOPT` reads it as optional, as it reads a malformed range bound as unbounded. `CTime.Validate` and `CDateTime.Validate` **MUST** report a value with no zone under mandatory, and a value with a zone under disallowed, as a `CodePatternMismatch`: the rule is the zone part of the pattern, which ADL 1.4 writes as a suffix. A date-time with no time has no zone. Where `Pattern` writes a zone suffix as well, both rules apply. A date has no zone, so on a `C_DATE` optional and disallowed admit every date and mandatory admits none. The SDK reads mandatory there as an OPT defect, since AOM 1.4 gives `C_DATE` no `timezone_validity` and only the ITS-XML schema does: it is a shape strict mode refuses, so `ParseOPTStrict` fails with `ErrInvalidOPT` on it and `ParseOPT` reads it as optional, and on a `CDate` built in code it is malformed (below), as a `TimezoneValidity` outside the three values is on any constraint built in code.
- `CDuration` **MUST** report a value that carries a designator its `Pattern` does not name as a `CodePatternMismatch`. It reads the pattern as ADL 1.4 reads a duration pattern (ADL 1.4, *Constraints on Dates, Times and Durations*, *Duration Constraints*): the letters before `T` name `Y`, `M`, `W` and `D`, those after it `H`, `M` and `S`, in either case, and the value may carry any one or more of them. A value of either sign is admitted, and a fraction wherever `S` is. A pattern outside the grammar of the ITS-XML `DurationConstraintPattern` (`Archetype.xsd`), read in either case, or one that names no designator, is malformed (below).
- `CDate`, `CTime`, `CDateTime` and `CDuration` carry the AOM 1.4 `range` as a `TemporalRange`: `Lower` and `Upper` as ISO 8601 text of the constrained type, with the included and unbounded flags of a `NumericRange` (§ *Numeric range*). Its zero value constrains nothing. `Validate` **MUST** report a value outside the range as a `CodeOutOfRange`, judging it only against a bound it is ordered against, in the order the RM's `Compare` gives: durations by BASE `Iso8601_duration.to_seconds`, which `rm.DVDuration.Magnitude` computes, and dates, times and date-times by the `magnitude()` of [REQ-123](rm-functions.md#req-123--temporal-data-value-helpers). In that order a partial value stands for the start of the period it names: a missing month or day reads as 1, and a missing minute or second as 0. A time or a date-time is ordered against a bound as [§ REQ-112](#req-112--template-less-reference-model-validation-floor) *DV_INTERVAL* orders two DV_TIME or two DV_DATE_TIME values: by those magnitudes when the two are written with one zone designator, or both with none; as instants, each by its magnitude less its zone's offset from UTC, when both carry a zone and the designators differ; and not at all when one carries a zone and the other does not, so such a bound draws no `CodeOutOfRange`. So a `CTime` with the range `>09:30:00+02:00` admits `08:00:00Z`, which is 10:00 at `+02:00`, and `09:00:00`, which has no zone. ADL 1.4 asks a closed interval to give a zone on both bounds or on neither (*Intervals*); the SDK does not check that, and orders the value against each bound on its own. A bound that the ISO 8601 parse of the constrained type refuses is a shape strict mode refuses: `ParseOPTStrict` fails with `ErrInvalidOPT` on it, and `ParseOPT` reads that side as unbounded; on a `TemporalRange` built in code, such a bound on a side that is not unbounded is malformed (below).
- `CBoolean.Validate` accepts Go `bool`.
- `CodePhrase.Validate` accepts either a bare `string` (treated as the code under the constrained terminology) or a `constraints.CodedTermRef`.
- `ConstraintRef.Validate` accepts a bare `string` or a `constraints.CodedTermRef` and reports no violation for either, since the value set it names is external terminology; any other Go type is `CodeWrongType`.
- `DvQuantity.Validate` accepts a `constraints.QuantityValue` `{Magnitude, Units, Precision}` triple. It **MUST** judge units by `Units` where that list is non-empty and by `PropertyUnits` only where it is empty, reporting a value whose units the list in force does not hold as a `CodeUnitUnknown`: with entries listed, a value whose units no entry lists is refused and `PropertyUnits` is not consulted, so a listed unit the property does not admit is accepted; with an empty `Units` list, a value whose units are not in a non-empty `PropertyUnits` is refused, as the specifications-CNF conformance schedule's case `CONT-DV_QUANTITY-validate_property` rejects `mg` under the property `openehr::122` (length); with both empty, any units are accepted. The parser **MUST** fill `PropertyUnits` when `Property` is an `openehr` code that the property-unit table of [rm-modeling.md § REQ-034](rm-modeling.md#openehr-terminology-vocabulary-req-034) (TERM `PropertyUnitData.xml`) lists, with that property's UCUM units, its primary units first and each part in source order, and **MUST** leave it empty for any other terminology or code. The table is closed: a UCUM code that measures the property but that the table does not list for it is a `CodeUnitUnknown`, such as `ml` under `openehr::129` (volume), where the table lists `mL`. With an empty `Units` list, `ExampleValue` returns magnitude 0 in the first entry of `PropertyUnits`, or `{0, "1"}` when that is empty too.
- `CDvOrdinal.Validate` accepts either an `int` (ordinal value) or a `constraints.OrdinalSymbol` `(value, symbol)` pair. An `OrdinalSymbol` **MUST** match a listed pair when the values and the code strings are equal and the terminologies are equal or either is empty, the rule `CodePhrase.Validate` applies to a terminology, so a listed symbol whose OPT names no terminology admits the one the instance carries. An empty `Values` list constrains the type only: `Validate` **MUST** accept any `int` or `OrdinalSymbol` against it, because an OPT that names `DV_ORDINAL` and lists no pairs leaves the value open, and it **MUST** refuse any other Go type with `CodeWrongType`.

A value whose Go type is not in the accepted set returns a single `CodeWrongType` violation; this is a contract failure on the caller side, not a constraint failure.

A constraint that carries a malformed value of its own **MUST** report a `CodeInvalidValue` on every value, as an unparseable `CString` pattern does. Its malformed values are a date, time, date-time or duration pattern the bullets above call malformed and, on a constraint built in code, a `TimezoneValidity` outside the three values or mandatory on a `CDate`, and a `TemporalRange` bound the ISO 8601 parse of its type refuses on a side that is not unbounded, which a parse never leaves on a constraint ([§ REQ-100](#req-100--adl-14-operational-template-opt-parse-and-paths) *Strict parse mode*).

### Violation taxonomy

Every `Violation` carries a typed `ViolationCode`. The closed set is:

| Code | Triggered by |
|---|---|
| `CodeOutOfRange` | numeric value outside a `NumericRange`, or temporal value outside a `TemporalRange` |
| `CodePatternMismatch` | string fails a regex / pattern (matched against the whole string) |
| `CodeNotInList` | value is not a member of a closed list (strings, codes, ordinals, etc.) |
| `CodeWrongType` | input Go type cannot be coerced to the constraint's expected type |
| `CodeUnitUnknown` | DV_QUANTITY units string is not in the enumerated allowed list, or, with no list, not among the units of the constraint's property |
| `CodeInvalidValue` | constraint or input is malformed (e.g. unparseable regex in the OPT, malformed date string) |

`Violation.Detail` carries a human-readable message; a consumer that builds structured diagnostics dispatches on `Code`, not on `Detail`. The class of each `Violation` field, and where the value goes, are in [§ REQ-168](#req-168--value-free-validation-diagnostics) and not restated here.

### Numeric range

`NumericRange` is the inclusive / exclusive interval shape used by `CInteger`, `CReal`, `DvQuantity.Magnitude`, and `DvQuantity.Precision`:

- `Lower` / `Upper` (float64; lossless for INTEGER up to 2^53)
- `LowerInclusive` / `UpperInclusive` (the parser reads a flag the OPT omits by [wire.md § REQ-169](wire.md#req-169--interval-boundary-flag-defaults): true on a bounded side, false on an unbounded one; a caller building a range sets the flags itself, since the struct's zero value is *exclusive* on both sides)
- `LowerUnbounded` / `UpperUnbounded` (when true, the corresponding bound is ignored)

The zero-value `NumericRange{}` (no fields set) is treated as "any value accepted" by `Contains` and `IsBounded` — a no-op constraint. AOM 1.4 also gives `C_DURATION` eight per-component allowed-flags (`years_allowed`, `months_allowed`, …, `fractional_seconds_allowed`). The ITS-XML `C_DURATION` an OPT follows carries none of them: its `pattern` string encodes them, and the parser reads that pattern (§ *Validate contract*).

### Out of scope (this REQ)

- **External terminology lookup** — [§ REQ-111](#req-111--public-compiled-template-bridge) *Term definitions and bindings* surfaces the bindings an OPT carries; `Validate` calls no remote terminology service.
- **AOM 2 `tuple_constraint`** — not used by ADL 1.4.
- **UCUM dimension analysis** — the specifications-CNF conformance schedule's case `CONT-DV_QUANTITY-validate_property` notes that "all units for the `property` are allowed" and that the validation is to look "into UCUM for all the possible units of measure" of that physical property. That is the fuller reading: any UCUM code of the property's dimension. v1 checks the closed TERM property-unit table instead, with exact matching (§ *Validate contract*).

### Example value emission (REQ-107 hook)

Every `PrimitiveConstraint` additionally exposes `ExampleValue() any` — a minimal-valid Go example value in the shape `Validate` accepts. For bounded constraints (closed lists, bounded ranges, enumerated units, a property's units) that admit a value, `Validate(c.ExampleValue())` **MUST** return an empty `Violation` slice. An unbounded primitive, and a temporal constraint for which no candidate below is accepted, **SHOULD** give a fixed sentinel of its type (e.g. `"example"`, `int64(0)`; for the temporal types `"2020-01-01"`, `"12:00:00"`, `"2020-01-01T12:00:00Z"` and `"P0D"`), so the example is a well-formed value of its type that stays the same from call to call. A constraint that admits no value has no example `Validate` accepts and is outside the first rule: a closed `CString` list whose `Pattern` matches no entry gives its first entry (§ *Validate contract*), and a temporal constraint that no value satisfies gives its sentinel (below). A temporal constraint is bounded by its `Pattern`, its `Range` and, for a time or a date-time, its `TimezoneValidity`. Its `ExampleValue` is the first value `Validate` accepts of these candidates, in turn: its sentinel written to the pattern; the range's lower bound as written, then written to the pattern and moved inside the range; and the upper bound likewise. So the sentinel stays wherever it satisfies both. A date, time or date-time written to the pattern keeps the fields the pattern allows, without a fraction of a second, keeps its zone, takes `Z` where the pattern or `TimezoneValidity` asks for a zone it lacks, is read in UTC where the pattern asks for `Z` and it has another zone, and drops its zone where `TimezoneValidity` disallows one; a lower bound then moves up by one unit of its last field where writing it dropped a part of it or the range excludes it, and an upper bound moves down by one unit where the range excludes it and writing it dropped nothing. A duration written to the pattern is its length counted in a designator the pattern names, one candidate for each designator in turn, and the sentinel is zero, in days or in the pattern's first designator when it names no days; a lower bound's count is rounded up and an upper bound's down, then moved one further where the range excludes the bound and the count equals it. Where none is accepted, as when no value satisfies both or the pattern or a bound is malformed, it is the sentinel. A pattern that writes a field after the first as a literal number, beside a range, is an exception to the rule for bounded constraints: written to the pattern, a bound takes the literal, which can move it out of the range, so the example can be the sentinel that `Validate` refuses although a valid value exists. `CDate{Pattern: "yyyy-06-dd"}` with the range `<=2004-05-20` gives `"2020-01-01"`, though `"2003-06-01"` is valid. The ITS-XML pattern grammars admit no literal number and the parser keeps a pattern as written, so only an OPT that breaks that schema, or a constraint built in code, reaches the exception. A range that only a value with a fraction of a second satisfies, or, for a `CTime`, only a time in another zone, is a second exception: no candidate carries a fraction or changes its zone, so the example is the sentinel that `Validate` refuses. `CTime` with the range `>23:59:59` gives `"12:00:00"`, though `"23:59:59.5"` is valid, and with the range `>23:59:59Z` and a mandatory zone, though `"23:00:00-02:00"` is valid; `CDuration` with the range `>PT0S` and `<PT0.5S` gives `"P0D"`, though `"PT0.25S"` is valid. An OPT can reach this exception, through an excluded bound less than a second from the other bound or from the end of the day. The factory is the leaf primitive of the REQ-107 template-driven instance generator and stays on the sealed interface so the closed type-switch remains the only entry point for new primitive shapes, with no reflection ([idiom.md § Generics and reflection](idiom.md#generics-and-reflection)). See § REQ-107 for the generator contract.

### Slot assertions

The SDK **MUST** parse the ADL 1.4 `ARCHETYPE_SLOT` include and exclude assertion subset that slot-fit checks in validators and in instance synthesis need: the `archetype_id matches {regex}` form, written either as plain text in the OPT XML (`archetype_id matches {/openEHR-EHR-OBSERVATION\.body_weight\..*/}`) or as the OPT XML expression tree in which operator `2007` (`matches`) binds `archetype_id/value` to a `C_STRING` `<pattern>` (the Ocean Template Designer shape).

An assertion that does not parse is kept on `Slot.Includes` or `Slot.Excludes`, and the structured matcher ignores it; when every include fails to parse, the slot widens to the RM-type-prefix rule below, which `SlotRules.IncludesDroppedUnparsed` reports.

- `constraints.SlotAssertion` carries a compiled Go `regexp` and exposes `MatchesArchetypeID(string) bool`.
- `constraints.SlotRules` holds a slot's includes and excludes. `AllowsArchetypeID` applies the excludes first, then requires a match against at least one include when includes are present; when no include was parsed it **MUST** fall back to the RM-type-prefix rule (`openEHR-EHR-<rmType>.`). A catch-all exclude (`.*`) is **ignored when includes are present**: template editors generate it as the complement of a closed includes list, so applying it literally would reject the slot's own includes.
- The parsed `Slot` exposes `ParsedIncludes`, `ParsedExcludes`, `AllowsRMType` (the prefix rule), `AllowsArchetypeID` and `SlotRules`.
- `CompiledNode` copies the parsed rules at compile time and exposes `AllowsArchetypeID` and `ExampleSlotFillArchetypeID` for the validators and the instance generator ([§ REQ-111](#req-111--public-compiled-template-bridge)).

- **Probes:** PROBE-024 (primitive constraint validation against fixture inputs)

## REQ-102 — Composition validation

The SDK **MUST** ship a `ValidateComposition(comp *rm.Composition, c *templatecompile.Compiled) Result` entry point that walks a parsed RM `Composition` against a compiled OPT and returns a `Result` aggregating every issue found in a single pass.

### Contract

- **Pure function.** No I/O and no goroutines, and the reflection rule of [idiom.md § Generics and reflection](idiom.md#generics-and-reflection) applies unchanged. Stateless — concurrent callers share `c` safely.
- **Collect-all, not fail-fast.** Validators emit one `Issue` per failing clause; the walk completes regardless of how many issues fire. UIs and CI consumers need the full list.
- **Result shape:**
  ```go
  type Result struct {
      OK       bool      // true when no Error-severity issue (Warnings alone leave OK true)
      Issues   []Issue
      Coverage Coverage  // what the result does not prove; § REQ-171 Coverage
  }
  type Issue struct {
      Path     string               // openEHR path of the offending node, § Issue paths (empty for global issues)
      Code     string               // stable programmatic identifier — see code taxonomy below
      Layer    Layer                // template or RM; § REQ-171 Finding identity
      Rule     string               // the clause evaluated; § REQ-171 Finding identity
      Detail   string               // human-readable message; field class in REQ-168
      Severity Severity             // Error for normative violations; Warning for advisories
      Value    constraints.Redacted // value-bearing field; see REQ-168
  }
  type Severity int
  const (
      Error   Severity = iota
      Warning              // advisory; does not flip Result.OK ([ValidateAQL] emits these)
  )
  ```

### Roots beyond COMPOSITION

The walker is value-source-generic: the compiled OPT drives the traversal, and the root is read attribute by attribute through the generated access of [§ REQ-171](#req-171--validation-engine) *Structural access*. The SDK **MUST** expose it for every archetypeable RM root, not only `COMPOSITION`: the demographic PARTY hierarchy and the EHR-IM container roots, so a demographic or directory OPT validates through the same machinery as a clinical template.

```go
// Generic entry — root is any RM LOCATABLE concrete the walker recognises.
func Validate(root any, c *templatecompile.Compiled, opts ...ValidateOption) Result

// Typed convenience wrappers (delegate to Validate; they take no option):
func ValidateComposition(comp *rm.Composition, c *templatecompile.Compiled) Result
func ValidateDemographic(party rm.Party, c *templatecompile.Compiled) Result        // PERSON/ORGANISATION/GROUP/AGENT/ROLE
func ValidateFolder(folder *rm.Folder, c *templatecompile.Compiled) Result
func ValidateEHRStatus(status *rm.EHRStatus, c *templatecompile.Compiled) Result
```

Every entry point includes the RM rules (§ *RM floor*). `ValidateComposition` keeps its `nil_composition` guard, then delegates. A nil or typed-nil root yields `nil_root` (or the wrapper's `nil_party`, `nil_folder` or `nil_ehr_status`); a root whose concrete RM type does not match the OPT root draws `rm_type_mismatch` at `/`, never a silent pass.

The covered roots are the demographic PARTY hierarchy, `PERSON`, `ORGANISATION`, `GROUP`, `AGENT` and `ROLE`, with the archetypeable parts walked in place or as roots (`ADDRESS`, `CONTACT`, `PARTY_IDENTITY`, `PARTY_RELATIONSHIP`, `CAPABILITY`), and the EHR-IM roots `FOLDER` (directory trees, recursing `folders`) and `EHR_STATUS`. Two limits remain: a round-tripped `DV_INTERVAL` with no bound present carries no `T` to check, so it matches any `DV_INTERVAL<T>` node (*Structural — RM type match* below); and reference-typed attributes (`PARTY.roles`, `FOLDER.items` → `OBJECT_REF`/`PARTY_REF`) are addressable for existence and cardinality, but their targets are not descended.

### Trust model

The validator treats the **compiled OPT as authoritative for structure** and the **composition as the instance under test**. Structural traversal is template-driven: for each compiled OPT node, the walker reads the corresponding RM property by `rm_attribute_name`, enforces existence / cardinality / alternatives, and recurses into matched RM children. A declared attribute no instance can carry is left out, as [§ REQ-171 *One walk*](#req-171--validation-engine) says. `Issue.Path` is written by § Issue paths below. Composition-supplied predicates never form lookup keys, so missing nodes are reported instead of silently bypassed.

### Validation dimensions

| Dimension | Implementation |
|---|---|
| **Structural — root archetype match** | comp.ArchetypeNodeID matches the OPT root's archetype id |
| **Structural — required attributes (composition root + recursive)** | RM-mandatory attrs at the root (Category, Composer, Language, Territory); template-driven existence checks at every OPT node whose attribute existence lower bound is ≥ 1, on a multi-valued attribute only where the template asks for a member there too: its cardinality lower bound, or the occurrences lower bound of a child it allows, is ≥ 1, or the list is one the floor holds non-empty once present (*An existence lower bound alone asks for no member* below) |
| **Structural — prohibited attributes** | an OPT child whose occurrences upper bound is 0 is not allowed, and the OPT prohibits an attribute whose existence upper bound is 0, or that has at least one OPT child and allows none of them, as [§ REQ-107](#req-107--template-driven-rm-instance-example-generator) *Visit rule* defines them; a prohibited attribute that is present (a single-valued attribute that holds a value, a multi-valued one that holds at least one item) is reported as `prohibited` at the attribute's path, and the template walk does not walk into it. | **Structural — child cardinality** | for each C_MULTIPLE_ATTRIBUTE of an object the instance carries, other than a list the template prohibits or one whose items are primitive values, whose children are never counted (*A mandatory child under an optional list* below), the items bound to each child are counted against its `Occurrences()`; on a list that is absent or empty, only the children *A mandatory child under an optional list* below names are counted, each holding no item; and the RM child count against the parsed `CompiledAttribute.ChildMultiplicity()` interval when the list holds an item or is present and the template requires it by its existence; a list the template requires by its existence that the instance does not carry fails existence alone (*A mandatory child under an optional list* below) |
| **Structural — alternatives (C_SINGLE_ATTRIBUTE)** | The value is checked against the attribute's child constraints. Within the first tier that admits the value, validators **MUST** bind it to a child under whose constraints it validates, where one does, and otherwise to the first child of that tier, reporting the findings it draws there. A value validates under a child when walking it under that child reports no finding that makes `Result.OK` false and, at a slot child, the slot's assertions admit its archetype id; the walk tries the children in OPT order and binds to the first under which the value validates. This trial is the validators' alone: the builder ([§ REQ-101](#req-101--generic-opt-driven-composition-builder) *Type enforcement*) and the generator ([§ REQ-107](#req-107--template-driven-rm-instance-example-generator) *What a visit writes*) bind by the tiers alone, to the first child of the first tier that admits the type. When no tier admits the value: exactly one child → `rm_type_mismatch`; two or more children → `alternative_mismatch` |
| **Structural — RM type match** | the RM instance's concrete type conforms to the OPT child's `RMTypeName`: equal to it, or a descendant of it in the pinned RM BMM's class hierarchy, whether that ancestor is abstract or concrete (a `DV_CODED_TEXT` satisfies `DV_TEXT`, a `PARTY_REF` satisfies `OBJECT_REF`). A `DV_INTERVAL<T>` child matches a typed instantiation by its parameterised name, and a round-tripped interval that decodes as the bare `DV_INTERVAL` by the runtime types of its bounds, each present bound having to be a `T`; an AOM 1.4 primitive short name admits its canonical DV wrapper, the type the [REQ-107](#req-107--template-driven-rm-instance-example-generator) generator builds for it (`DURATION` → `DV_DURATION`, `DATE` → `DV_DATE`, `TIME` → `DV_TIME`, `DATE_TIME` → `DV_DATE_TIME`, `BOOLEAN` → `DV_BOOLEAN`, `INTEGER` → `DV_COUNT`). Single-child attributes surface failures as `rm_type_mismatch` at the attribute path |
| **Identity — archetype / node id pinning** | LOCATABLE.archetype_node_id is checked against the matched OPT child's `ArchetypeID()` (for archetype roots) or `NodeID()` (for inner at-codes) |
| **Structural — binding items (C_MULTIPLE_ATTRIBUTE)** | A LOCATABLE item binds among the non-slot children whose `ArchetypeID()` (archetype root) or `NodeID()` equals its `archetype_node_id`, else to the first slot whose assertions admit that id. Where two or more non-slot children carry the id, as when a template reuses one archetype under several template-level names ([REQ-116](#req-116--template-level-node-naming-and-name-predicated-paths)), the item's `name` value ranks them: first those whose pinned name equals it; failing any, those that pin no name; failing any, all of them. The item binds among the children of the first rank that holds one. Among the children of one rank, validators **MUST** bind the item to a child that has room and under whose constraints the item validates, as *Structural — alternatives* reads it, where one does; failing that, to the first of them that has room; failing that, to the first of them, whose occurrences or name constraint then reports the mismatch. The walk tries them in OPT order and binds to the first that has room and under which the item validates. A child has room while the items of the same list bound to it before, in item order, number fewer than its occurrences upper bound; one that states no upper bound always has room. The item's `name` decides the binding only and never reaches a path or a message ([REQ-168](#req-168--value-free-validation-diagnostics)). Items that are not a LOCATABLE bind by RM type (§ *Items that are not a LOCATABLE*) |
| **Primitive constraints** | REQ-103 `PrimitiveConstraint.Validate` runs at every primitive leaf the OPT declares; bound to the RM value found by the structural walk. A part of a value that the RM rules report as absent or empty is theirs to report, not the constraint's: the RM's `required` at that part stands for the constraint's finding there, beside any finding of an RM rule's own (§ REQ-112 *Coded invariants*; [§ REQ-171](#req-171--validation-engine) *One finding per defect*). The parts are the `code_string` of a CODE_PHRASE, a DV_CODED_TEXT's defining code included, whose terminology the constraint still judges; the `units` of a DV_QUANTITY, which leaves the constraint nothing to judge, its ranges being per unit; the `value` of the DV_DATE, DV_TIME, DV_DATE_TIME or DV_DURATION an AOM 1.4 short name binds; and the code string of a DV_ORDINAL's `symbol`, when the validator passes the `value` alone for the constraint to judge. When the walk stops before the RM rules report the part, at the depth limit or the visit limit, the constraint judges it as it judges any value, so the part is reported either way. The constraint **MUST** still judge a CODE_PHRASE's terminology; a DV_ORDINAL's `value`, which the validator passes alone when the RM rules report the symbol's code string; a part the RM rules let be blank, such as a DV_SCALE symbol's `code_string`; and a part the RM does not require, such as an optional String, which it judges as any value. At a DV_ORDINAL bound to a `C_DV_ORDINAL` whose symbol's defining code carries a code string, a symbol that does not match its value **MUST** be reported: the validator passes the `value` and that code together as one `constraints.OrdinalSymbol`; a code that names no terminology matches a listed pair under § REQ-103's rule, and the RM rules report the missing terminology. A `CONSTRAINT_REF` leaf constrains nothing the walker can check locally, so the walker still checks the RM-mandatory attributes of the value it binds there (a CODE_PHRASE's `terminology_id` and `code_string`), as at a node the OPT leaves unconstrained |
| **Slot fit — assertion grammar** | § REQ-103 *Slot assertions*: `CompiledNode.AllowsArchetypeID` (includes / excludes with RM-type-prefix fallback when no includes parsed) |
| **Extra RM nodes not declared in OPT** | not flagged |
| **Terminology binding value-set** | not checked: it needs a live external terminology; [§ REQ-111](#req-111--public-compiled-template-bridge) *Term definitions and bindings* surfaces the bindings the OPT carries |

| `cyclic_value` | a value that contains itself, reported where it recurs ([§ REQ-171 *One walk*](#req-171--validation-engine), REQ-112 *Driver*) |
| `invalid_shape` | input that does not decode into the root handed to `ValidateJSON`, `ValidateXML`, their `Validator` methods or the deprecated `ValidateRMEHRStatusBytes`: malformed canonical JSON or XML, or a JSON root that is not an object (REQ-112 floor, *Value-typed mandatory presence*) |
| `rm_type_unknown` | a Go value outside the v2 closed RM set handed to `ValidateRM` (REQ-112 floor) |
| `nil_root` / `nil_folder` / `nil_ehr_status` / `nil_ehr_access` / `nil_party` | global guards: a nil argument to `ValidateRM` or a typed RM-floor wrapper (REQ-112 floor) |
| `nil_composition` / `nil_template` | global guards — caller supplied a nil argument |

Existence and child-count cardinality are **independent constraints** on a list: existence says whether the container exists, and cardinality how many members it holds. So a multi-valued attribute with `existence.lower ≥ 1` and `cardinality.lower ≥ 1` whose list is present and empty fails both, and validators **MUST** report both `required` and `cardinality` at its path, as collect-all makes natural; a consumer that de-duplicates for display can treat the pair as one failure at that path. A list's own `cardinality` is also reported, where it fails, while the list holds an item. Validators **MUST NOT** report it while the list is absent, nor while the list is present and empty and the template leaves it optional by its existence (*A mandatory child under an optional list* below). A list the template requires by its existence, its existence lower bound bounded and at least 1, that the instance does not carry, absent as [§ REQ-171 *Structural access*](#req-171--validation-engine) reads presence, fails existence alone: there is no container to count, so the `occurrences` of its children **MUST NOT** be reported either.

**An existence lower bound alone asks for no member.** On a multi-valued attribute, existence says whether the container exists and cardinality how many members it holds (ADL 1.4, *Attribute constraints*, *Existence*), so a container with no member meets an existence lower bound of 1 where the counts allow none. An empty container commonly travels as a missing one: canonical JSON leaves out a present empty list the RM makes optional where the field is the list itself, as `ITEM_LIST.items` is ([wire.md § REQ-052](wire.md#req-052), *An absent mandatory member*; [bmm-conformance.md § Property → Go field](bmm-conformance.md#property--go-field)), and canonical XML writes no element for an empty list the RM gives a cardinality lower bound of 0 ([wire.md § REQ-056](wire.md#req-056)), so validators judge an absent list and an empty one alike on existence. Validators **MUST NOT** report `required` on the template layer for the existence of a multi-valued attribute whose list is absent, or present and empty, unless the template asks for a member there. Where it does, and the existence lower bound is bounded and at least 1, the template layer reports `required` there, rule `existence`. The template asks for one where its cardinality lower bound, or the occurrences lower bound of a child it allows, is bounded and at least 1, or where the list is one the floor holds non-empty once present. A child that states no occurrences, or occurrences with an unbounded lower bound, asks for none here, although the generator builds a member of it ([§ REQ-107](#req-107--template-driven-rm-instance-example-generator) *What a visit writes*). The lists the floor holds non-empty once present are those [§ REQ-112 *Non-empty lists*](#req-112--template-less-reference-model-validation-floor) evaluates: `COMPOSITION.content`, `EVENT_CONTEXT.participations`, `INSTRUCTION.activities`, `SECTION.items` and `ATTESTATION.items`, and `HISTORY.events` while the HISTORY has no `summary`: the rules [§ REQ-112 *Non-empty lists*](#req-112--template-less-reference-model-validation-floor) evaluates refuse such a list that is present and holds no item, and a HISTORY with neither an event nor a summary, so the container its existence asks for cannot exist without a member. The RM gives other lists the same rule, `ENTRY.other_participations`, `ACTOR.roles` and `PARTY.contacts` among them; the floor does not evaluate it there, so their existence asks for no member. `LOCATABLE.links` is one of them that the floor does evaluate, and it reports a `links` that is present and holds no item ([§ REQ-112 *LOCATABLE links and EVENT_CONTEXT location*](#req-112--template-less-reference-model-validation-floor)), but it is not among the lists the floor holds non-empty for the template's sake, so the existence of `links` asks for no member either. On a list the floor holds non-empty once present, where its existence lower bound is bounded and at least 1, validators **MUST** report `required` on the template layer, rule `existence`, both when the list is absent and when it is present and empty, and that finding stands for the RM rule that reads the list ([§ REQ-171](#req-171--validation-engine) *One finding per defect*). Such a list with no member is reported as the paragraph above says, so an absent one draws `required` alone, whatever asks for the member; the RM layer still reports an RM-mandatory container ([§ REQ-171](#req-171--validation-engine) *One finding per defect*). So an `ITEM_LIST` or `ITEM_TREE` whose `items` carry existence `1..1`, cardinality `0..*` and no allowed child validates with no items.

**A mandatory child under an optional list.** On an object the instance carries, validators **MUST** count against its occurrences each allowed child, not a slot, of an attribute the OPT declares multi-valued, both words as [§ REQ-107](#req-107--template-driven-rm-instance-example-generator) *Visit rule* defines them, whether the list holds items, is present and empty, or is absent, with three exceptions. An absent list the template requires by its existence fails existence alone (above). A list whose items are primitive values, such as a DV_MULTIMEDIA's `data`, has items the walk counts but binds to no child, so its children are counted neither when it holds items nor when it holds none. A list the template prohibits (*Structural — prohibited attributes* above) leaves its children nothing to count: holding an item, it draws `prohibited` alone and is not entered, and holding none, absent or present and empty, it draws nothing from its children, so that an instance that leaves it out validates. The children of a list the OPT writes as a single-valued attribute, as some OPTs write a `COMPOSITION`'s `content` under a `C_SINGLE_ATTRIBUTE`, are alternatives that attribute's existence decides (§ REQ-107 *Visit rule*), so an absent such list draws nothing from them. An absent list holds no item, so each such child whose occurrences lower bound is bounded and at least 1 draws its occurrences finding, `cardinality` with rule `occurrences`, at the path § *Issue paths* writes for a node the OPT requires and the instance lacks: the child's own predicate below the list's path, or the list's path for a child that declares no id. ADL 1.4 calls such a child mandatory in its container and leaves an optional container to its existence; that the child also asks for its container is the reading § REQ-107 *Visit rule* chooses, so that a list `Generate` leaves out under `Required` is one validators accept as absent. On a list the template leaves optional by its existence, the list's own `cardinality` is not reported when the list is absent, since ADL 1.4 makes such a container "optional, but if present" bound by its cardinality (*Cardinality*), nor when it is present and empty, since canonical JSON carries an empty optional list as an absent one (*An existence lower bound alone asks for no member* above): an absent and an empty optional list draw the same template findings, as they do on existence.

**Open multi-valued attributes** — when a C_MULTIPLE_ATTRIBUTE declares no `<children>` (the OPT pinned only existence / cardinality, not membership), validators MUST accept any RM item under that attribute without firing `slot_fill`. The constraint surface is the attribute itself; the items inside are unconstrained. This admits the OPT idiom "items here, any shape allowed" — e.g. a SECTION whose /items is open to any archetype-root content.

**Items that are not a LOCATABLE** — an item of a C_MULTIPLE_ATTRIBUTE that is not a LOCATABLE (a PARTICIPATION under `participations` or `other_participations`, a TERM_MAPPING, a REFERENCE_RANGE, a DV_IDENTIFIER, a PARTY_REF) carries no `archetype_node_id`, so it cannot be matched by id. Validators **MUST** bind such an item to a non-slot child whose `RMTypeName` admits the item's RM type, by the same conformance rule and the same three binding tiers a C_SINGLE_ATTRIBUTE uses, choosing among the children of the first tier that admits it as *Structural — binding items* chooses among those of one rank, never report it as `slot_fill`, and report one that no child admits at its own path, as `rm_type_mismatch` if the attribute has exactly one child and as `alternative_mismatch` if it has two or more. A bound item counts toward its child's occurrences like any other item. A nil item (a nil element, or a nil pointer) under an attribute that declares children has no RM value to bind, so validators **MUST NOT** bind it to any child, an untyped one included. It is reported as `slot_fill`, like a LOCATABLE whose `archetype_node_id` is empty, when it is a nil pointer to a LOCATABLE class or a nil element of an attribute whose declared item type is a LOCATABLE, and as `rm_type_mismatch` or `alternative_mismatch` by the rule above otherwise. An attribute that declares no children admits a nil item like any other item (*Open multi-valued attributes* above), so the template reports nothing for it and the RM rules report it, as [§ REQ-112 *Driver*](#driver) says; a nil item the template refuses is reported by the rule above alone ([§ REQ-171](#req-171--validation-engine) *One walk*).

### Issue paths

`Issue.Path` is an openEHR path from the validated root: RM attribute names joined by `/`, with a predicate on each item of a multi-valued attribute and none on a single-valued one. The template-driven validators (this REQ) and the floor ([REQ-112](#req-112--template-less-reference-model-validation-floor)) **MUST** build it by one rule, so one node has one path whichever validator reports it. An item's predicate is:

- `[atNNNN]`, its `archetype_node_id` (an archetype id on an archetype root), when no other item of the same attribute carries that id;
- `[atNNNN, 'name']` when another item shares the id and the OPT node the item binds to pins a name ([REQ-116](#req-116--template-level-node-naming-and-name-predicated-paths)) that tells it apart, the name single-quoted with `'` and `\` escaped by a backslash;
- `[n]`, the item's 1-based position in the attribute, in every other case: an item with no `archetype_node_id`, or one whose id is shared and whose OPT node pins no telling name.

An entry of a hash attribute ([§ REQ-171 *Structural access*](#req-171--validation-engine)) **MUST** be written `[n]`, its 1-based position in ascending key order, never with its key: a key is instance data, and the quoted-key form ODIN shows in its examples (`["en"]`) would carry it into the path.

A node the OPT requires and the instance lacks is written with the OPT child's own predicate, since no item exists to number; a child that declares no id has none and is written at the attribute's path. The floor binds no OPT node, so on its own it never writes a name predicate; inside a template-driven validation the RM rules run in the walk that binds the template ([§ REQ-171 *One walk*](#req-171--validation-engine)), so a node they judge carries the path that walk wrote for it, its name predicate included.

A path carries no value from the instance, as [REQ-168](#req-168--value-free-validation-diagnostics) requires of every value-free field: a name predicate is always a name the OPT pins, never the instance's own `name`. A path with no positional predicate is a valid AQL path; the AQL grammar has no positional predicate, so one with `[n]` is an openEHR path but not AQL.

### RM floor

Every entry point of this REQ, `ValidateComposition`, `Validate` and the typed wrappers of § *Roots beyond COMPOSITION*, **MUST** apply the [REQ-112](#req-112--template-less-reference-model-validation-floor) rules in the walk that applies the template and return their findings in the same `Result` ([ADR 0025](../adr/0025-template-validation-includes-the-rm-floor.md), [ADR 0027](../adr/0027-template-admission-before-rm-rules.md)): on every node the template admits, the nodes it does not constrain included, and on no content it refuses. [§ REQ-171 *One walk*](#req-171--validation-engine) orders the steps at each node and says which layer reports an attribute both layers find missing or empty, so that absence is one finding; an RM rule's own finding at the same path, such as a code outside its terminology group, is reported beside it. No option leaves the RM rules out of these entry points; `ValidateRM` and its typed wrappers are the entries for the RM rules alone.

### Sentinels

The package **MUST** expose typed sentinels callers compare via `errors.Is` for programmatic dispatch. Issues bridge to sentinels via `Issue.Err() error`:

| Sentinel | Triggered by |
|---|---|
| `ErrCardinality` | `cardinality` code |
| `ErrRequired` | `required` code |
| `ErrProhibited` | `prohibited` code |
| `ErrTypeMismatch` | `rm_type_mismatch`, `alternative_mismatch`, `archetype_id_mismatch`, `node_id_mismatch` |
| `ErrPrimitive` | any `primitive_*` code |
| `ErrSlotFill` | `slot_fill` code |
| `ErrAQLSyntax` | `aql_syntax`, `aql_empty` codes — the AQL lint surface (REQ-109) |

Caller pattern:

```go
for _, i := range r.Issues {
    if errors.Is(i.Err(), validation.ErrRequired) {
        // typed handling for missing required attributes
    }
}
```

Global guard codes (`nil_composition`, `nil_template`) return `nil` from `Issue.Err()` — they represent caller-side argument errors, not validation failures of a structurally-present composition.

### Out of scope (this REQ)

- **AQL lint** (`ValidateAQL`) — a separate entry point under REQ-109; it does not change the composition-validation surface.
- **Validating wire bytes / canonical JSON** — callers decode first, validate second ([REQ-013](module-layout.md#req-013--building-block-independence)).
- **External terminology lookup** — value-set membership against SNOMED CT / LOINC / external services. REQ-103 closed-code-list checking is the v1 ceiling.
- **A coded text's `value` against its code's term text** — no RM invariant ties a DV_CODED_TEXT's `value` to the term text of its `defining_code`, so the template validator does not compare them, although some CDRs do; the generator writes the term text ([§ REQ-107](#req-107--template-driven-rm-instance-example-generator)).
- **Cross-archetype slot-fill resolution** — no federated archetype repository; slot fit is local to the parsed slot assertions of § REQ-103, with RM-type-prefix fallback only when no include assertions were parsed.
- **Full ADL2 / AOM 2 validation semantics.**

- **Probes:** PROBE-025 (composition validation against fixture OPT + composition); PROBE-026 (missing required node, cardinality, alternative_mismatch, rm_type_mismatch, and primitive negative cases); PROBE-074 (template-driven validation of non-COMPOSITION roots: the issue-code multiset per (OPT, root) shape)

## REQ-107 — Template-driven RM instance example generator

**Status:** Draft.

The SDK **MUST** ship a template-authoritative RM instance synthesiser at `openehr/instance/`: given a compiled OPT, produce a conformant RM object graph whose structure and primitive leaves satisfy the same template-driven contract REQ-102 validates against. The generator is the inverse of validation: the same compiled-OPT walk, in the opposite direction.

### Scope

The generator is the single skeleton-and-populate engine the composition builder (REQ-101), tests, examples, and data seeding all consume. The root is whatever RM class the OPT's root `rm_type_name` declares: an archetype-root class (`COMPOSITION`, an ENTRY, a `PARTY`, …), a content or structure class (`SECTION`, `GENERIC_ENTRY`, `CLUSTER`, `ELEMENT`, an item structure, …), a `PARTY_RELATIONSHIP`, a data value or a `CODE_PHRASE`. Output is **synthetic example data**: valid as § Contract below says, not clinically meaningful.

### Contract

Public entry point:

```go
package instance

type Policy int

const (
    Medium   Policy = iota // the default: required attributes and those with an allowed OPT child, one optional archetype per attribute
    Required               // required attributes and a composition's context, each OPT child up to its occurrences lower bound
    Large                  // every attribute the visit rule allows, a member of each optional archetype and of each use of one

    Minimal  = Required // alias
    Complete = Large    // alias, until a complete level of its own lands
)

func ParsePolicy(name string) (Policy, error)

type Options struct {
    Policy      Policy
    Language    string                  // ISO 639-1; empty = Compiled.Language(), then "en"
    Territory   string                  // ISO 3166-1; required for a COMPOSITION root
    Composer    rm.PartyProxy           // required for a COMPOSITION root
    Now         time.Time               // clock for unconstrained date-times; zero = current time
    UIDSource   func() *rm.HierObjectID // uids and reference ids (nil = crypto/rand)
    ValueFill   ValueFill               // ExampleFill (default) or RandomFill
    ValueSource mrand.Source            // seeds RandomFill; nil = auto-seeded global
}

func UIDsFrom(src mrand.Source) func() *rm.HierObjectID // a UIDSource of version-4 UUIDs drawn from src; nil src = nil

func Generate(ctx context.Context, c *templatecompile.Compiled, opts Options) (any, error)
func AsComposition(v any) (*rm.Composition, error)
func AsObservation(v any) (*rm.Observation, error)
// … and AsEvaluation, AsInstruction, AsAction, AsAdminEntry, AsCluster, AsSection, AsGenericEntry, AsElement
```

**Levels and names.** `Medium` is the zero value, so `Options` with no `Policy` builds the medium level. `Minimal` and `Complete` are aliases, the same values as `Required` and `Large`, so every rule here for `Required` and `Large` holds for them, and `Policy.String` **MUST** return `required` for `Required`, `medium` for `Medium` and `large` for `Large`, so an alias prints its target's name, and `unknown` for any other value. `ParsePolicy` **MUST** map the names `required`, `minimal`, `medium`, `large` and `complete`, compared without regard to case, to those values, and return an error wrapping `ErrUnsupportedPolicy` for any other text, the empty string included.

**Output.** Under each policy above (`Large`, `Medium` and `Required`) and both `ValueFill` values, every root `Generate` returns, and so every skeleton `composition.NewSkeleton` returns and `composition.NewBuilder` seeds, **MUST** satisfy the OPT's structural rules and REQ-103 primitive constraints, which the template validator (REQ-102) checks, pass the RM floor (`validation.ValidateRM`, [REQ-112](#req-112--template-less-reference-model-validation-floor)), and satisfy every RM invariant the floor does not evaluate, such as ELEMENT `Inv_null_reason_valid` (a `null_reason` only on an ELEMENT with no `value`). The cases § [Exceptions and known gaps](#exceptions-and-known-gaps) lists are the only ones outside this rule. Two rows of the floor's catalogue need generator work: every ELEMENT carries exactly one of `value` and `null_flavour` (`Inv_null_flavour_indicated`), and no primitive leaf holds a placeholder its RM type rejects, so an ISO 8601 temporal `value` is always a valid date, time, date-time or duration (`Value_valid`).

**Inputs.** `Generate` **MUST** return an error wrapping `ErrUnsupportedPolicy`, and no root, for an `Options.Policy` that is none of `Large`, `Medium` and `Required`, before it builds anything, at every root type and either `ValueFill`, and, for a `COMPOSITION` root, `ErrComposerRequired` when `Options.Composer` is nil and `ErrTerritoryRequired` when `Options.Territory` is empty. For a `COMPOSITION` root it **MUST** write `Options.Composer` as the root's `composer`, as given, whatever the OPT constrains there. An empty `Options.Language` **SHOULD** be read as `Compiled.Language()`, and as `en` when that is empty too, and a zero `Options.Now` as the current time, so that a caller who sets neither gets a root in the template's own language, stamped with the time it was built.

**Visit rule.** Under every policy, `Generate` does not visit an attribute that no serialization carries, a BMM function among them, the set `rminfo.IsNonStorableAttr` names and [§ REQ-112 *Driver*](#driver) lists; an attribute the compile marks as one the node's RM class does not have (`CompiledAttribute.NotInRM`, [§ REQ-111](#req-111--public-compiled-template-bridge) *Attributes the RM does not have*), such as `ISM_TRANSITION.name`, whatever existence the OPT gives it, since no instance can carry it and the template validator leaves it out and lists its path in its coverage ([§ REQ-171 *One walk*](#req-171--validation-engine)); a DV_MULTIMEDIA's `data`, whose octets bind to no OPT child ([§ REQ-102](#req-102--composition-validation) *A mandatory child under an optional list*) and which *RM defaults* below write instead; or a locatable's `uid`, which *Identity* below governs. Under every policy, `Generate` does not visit an attribute the generator has no writer for (§ [Exceptions and known gaps](#exceptions-and-known-gaps), *Known gap: attributes the generator cannot write*) unless it is required, as defined below, by more than its cardinality lower bound alone, which does not ask for the container (below), and is not a list that only its existence asks a member of (*What a visit writes*), so that a root without it would fail the template validator; where the walk would visit one, `Generate` returns the error § [Errors](#errors) names for it. An OPT child is *allowed* unless its occurrences upper bound is 0, and the OPT *prohibits* an attribute whose existence upper bound is 0, or that has at least one OPT child and allows none of them; `Generate` does not visit an attribute the OPT prohibits unless an RM rule needs it (§ [Precedence](#precedence)). An attribute is *required* when the BMM marks it mandatory or its existence or cardinality lower bound is bounded and at least 1, or when the OPT declares it multi-valued and an allowed OPT child of it that is not a slot has an occurrences lower bound that is bounded and at least 1, unless the RM types the list's items as primitive values, such as a DV_MULTIMEDIA's `data`, to which no item binds ([§ REQ-102](#req-102--composition-validation) *A mandatory child under an optional list*). ADL 1.4 calls such a child mandatory in its container (*cADL*, *Occurrences*: the `PERSON` whose occurrences are `{1}` "is mandatory in the `GROUP`"), as AOM 2 does (validity rule VACMCO, "every mandatory child object"), and leaves an optional container to its existence. That the child also asks for its container, so that the attribute holding it is required, is the reading this specification chooses; EHRbase and FerroEHR read the template the same way when they refuse a composition that leaves such a list out, and the validators read it so too ([§ REQ-102](#req-102--composition-validation) *A mandatory child under an optional list*). The child of a single-valued attribute never makes the attribute required: ADL 1.4 says the attribute's existence already decides how often that child occurs (*Occurrences*). A child that states no occurrences, or occurrences with an unbounded lower bound, makes no attribute required, as the validators ask such a child for no member ([§ REQ-102](#req-102--composition-validation) *An existence lower bound alone asks for no member*), although an attribute visited for another reason gives it one (*What a visit writes*). Under `Large` and `Medium`, `Generate` does not visit an attribute whose members would all be undescribed or need undescribed content (§ [Slot fills](#slot-fills): a slot fill, a LOCATABLE built from a BMM type, or an object of an archetype-root class for which the OPT names no archetype id, or a node that would hold one of them in a required attribute that can hold nothing else, such as an `EVALUATION` whose `data` the OPT leaves without a child), where that attribute is not required or only its cardinality lower bound requires it, except a `COMPOSITION`'s `context`, which *RM defaults* writes under every policy. A cardinality lower bound does not ask for the container (below), so this rule reads such a list as `Required` reads it: a `SECTION`'s `items` at existence `0..1` and cardinality `1..*` whose only child is an optional `ADMIN_ENTRY` the OPT names no archetype id for, a `COMPOSITION`'s `content` at that existence and cardinality whose only child is an optional `SECTION` that requires such an entry, or an `ITEM_TREE`'s `items` at that existence and cardinality whose only children are slots, whose members would be slot fills, or that has no allowed child, whose members would be ELEMENTs built from its BMM type, is left out under every policy, and validators accept it absent ([§ REQ-102](#req-102--composition-validation) *A mandatory child under an optional list*). Under every policy, `Generate` does not visit a single-valued attribute that is not required, as defined above, where the value a visit would write (*What a visit writes*) is an item structure that would hold no item: an `ITEM_TREE` or `ITEM_LIST` whose `items`, or an `ITEM_TABLE` whose `rows`, would get no member, because the structure's OPT node does not carry that attribute, the walk under the policy in force does not visit it, or the visit gives it no member (*What a visit writes*). A list whose cardinality upper bound is less than the members its allowed children ask for is not one the visit gives no member: the walk visits it, and § [Errors](#errors) refuses the root. The generator decides this by what the walk would write once the rules here and in *What a visit writes* have left children out, not by the OPT alone: an optional `protocol`, `state` or `other_context` whose `ITEM_TREE` holds no child, only slots, or only optional children that need undescribed content is left out, while one whose `ITEM_TREE` holds an optional `ELEMENT` is visited under `Large` and `Medium`, which build that `ELEMENT`. An `ITEM_SINGLE` and a `CLUSTER` always hold an item, since the BMM marks their `item` and `items` mandatory. That an optional structure with no item is left out is the reading this specification chooses, as such a structure carries no data the RM or the OPT asks for. A structure the RM or the OPT requires, as the BMM requires `EVENT.data`, or as an OPT requires a `protocol` it gives an existence lower bound of 1, is written, with no item where the walk gives it none. Under `Large`, `Generate` **MUST** visit every other attribute the compiled node carries. Under `Medium`, it **MUST** visit every other attribute that is required or that has an allowed OPT child, and no other. Under `Required`, it **MUST** visit every other attribute that is required, except one that only its cardinality lower bound requires, and no other, an attribute with an allowed OPT child included. Under every policy, `Generate` **MUST** write a `COMPOSITION`'s `context`, the one exception to those three rules, and build it under the OPT's constraints as `Medium` does. A cardinality lower bound counts the members of a container that exists and does not ask for the container, which its existence decides (AOM 1.4, *Attribute Node Types*: existence "says whether the container object will be there (at all)", cardinality "how many items" the container holds; ADL 1.4, *Cardinality*: "optional, but if present, is a container"). So `Required` leaves out an optional list that only its cardinality asks a member of, such as a `COMPOSITION`'s `content` at existence `0..1` and cardinality `1..*` whose children are all optional, and the bound counts the members of a list `Required` visits for another reason (*What a visit writes*). The three follow the levels of the ITS-REST template example's `detail_level` ([`definition-validation.openapi.yaml`](../../resources/its-rest/definition-validation.openapi.yaml)): `Required` builds its `required` level, the data points the template makes mandatory and a composition's `context`; `Medium` its `medium` level, with at most one optional archetype under an attribute (*What a visit writes*); and `Large` a member of every optional archetype the template names that needs no undescribed content (§ [Slot fills](#slot-fills)), and of every use of one, named or not, short of the `complete` level; until that level lands, `Complete` is another name for `Large` (§ [Primitive-leaf value fill](#primitive-leaf-value-fill), *Deferred*). An attribute the BMM marks mandatory that a compiled node does not carry, as under `templatecompile.WithoutImplicitAttributes`, is visited as if the node carried it with no OPT child.

**What a visit writes.** A visited single-valued attribute takes the RM type its first allowed OPT child names, or, where that child names an abstract RM class or an AOM 1.4 primitive short name, the concrete type the generator builds for it (a concrete descendant of the abstract class, the *RM defaults* below where one applies; for a short name, its canonical DV wrapper, § REQ-102 *RM type match*), built under the constraints of the child the binding tiers of [§ REQ-102](#req-102--composition-validation) *Structural — alternatives* bind a value of that type to: the first child, unless a later one names that type exactly or is the AOM 1.4 short name that type wraps. That child is the first of its tier and the value built under it validates under it, so the validator, which tries the children of the tier in OPT order, binds what the generator built to the child whose constraints built it. When the attribute has no allowed OPT child, it takes a value built from its BMM type. A visited multi-valued attribute gets, in OPT order, `max(occurrences.lower, 1)` members of each allowed OPT child that is not a slot under `Large` and `Medium`, except an optional child (occurrences lower bound 0) that needs undescribed content (§ [Slot fills](#slot-fills)), and `occurrences.lower` members under `Required`, so that an optional child (occurrences lower bound 0) gets none of its own there; a child the OPT gives no occurrences, or occurrences with an unbounded lower bound, is not optional and gets one member under every policy; it gets no more members in all than its `cardinality.upper` when that is bounded, and within that bound the room goes first to the members asked for by the children whose occurrences lower bound is bounded and at least 1, which fit wherever § [Errors](#errors) does not refuse the list: any other child, before or after them, gets only the room they leave, and the members still stand in OPT order, so `CLUSTER.items` at cardinality `0..1` over an optional `at0001` and a required `at0002` holds the `at0002` member alone; under `Medium`, where one optional archetype per attribute is the rule, an optional child (occurrences lower bound 0) whose identity a required sibling, before or after it, or an earlier optional sibling carries gets no member of its own (the top-up below can still build one). Under `Large`, such a child gets its members as any other optional child does, so a `Large` root holds a member of every sibling of one identity that needs no undescribed content, whether the OPT pins a name on it or not, within the cardinality bound above; the validator binds those members by room and by trial ([§ REQ-102](#req-102--composition-validation) *Structural — binding items*), each to the sibling whose constraints built it wherever that sibling comes first among those with room (§ *Exceptions and known gaps*). A child's identity is its archetype id when it is an archetype root and its `node_id` otherwise, and a child with neither has no identity and is never skipped; a sibling other than a slot carries an identity when it is that sibling's archetype id or `node_id`, as [§ REQ-102](#req-102--composition-validation) *Structural — binding items* binds a LOCATABLE member. So under `Medium` an optional child that is not an archetype root gets no member when an archetype root before it has its `node_id`, while under `Large` the optional archetype roots under one attribute each get their members, of one archetype or of several. Under `Medium`, an optional archetype root after the first optional archetype root of the attribute that needs no undescribed content, in OPT order, gets no member of its own either, whatever its archetype, so the attribute holds at most one optional archetype. A name the OPT pins on a child is not part of this identity, although the validator also tells siblings apart by it: under `Medium`, optional named siblings of one archetype after the first get no member, and under `Large` each gets its members, except one that needs undescribed content (§ [Slot fills](#slot-fills)), as any optional child does, such as a named sibling whose required attribute holds only slots. When that leaves the attribute with fewer members than it needs (its cardinality lower bound, or one member when the BMM or its existence requires it), it is topped up to that count one member at a time, in OPT order, from a child that still has room: a child has room while the members built of it, its own and the top-up's, number fewer than its occurrences upper bound, or where it states no upper bound, the room by which the validator binds an item ([§ REQ-102](#req-102--composition-validation) *Structural — binding items*), and a slot always has room, since the parser does not read its occurrences (*Known gap: slot occurrences*). Each member is one of its first allowed child with room that needs no undescribed content (§ [Slot fills](#slot-fills)) and whose identity no earlier sibling with room carries, a child that gets no member of its own under `Large` or `Medium` included, else of its first allowed child with room that is not a slot, else a fill of its first slot, and, where it has no allowed child, a member built from its BMM type. So `CLUSTER.items` at cardinality `3..*` over an `at0001` at occurrences `1..1` and an `at0002` at `0..*` holds one `at0001` member and two `at0002` members under every policy. Only where no allowed child has room, as in an OPT whose cardinality lower bound exceeds what its children's occurrences allow (§ [Exceptions and known gaps](#exceptions-and-known-gaps)), is the member one of its first allowed child, past that child's occurrences. Where only its existence asks for that member, because the BMM does not mark the attribute mandatory, neither its cardinality lower bound nor the occurrences lower bound of a child it allows is bounded and at least 1, and it is not a list that [§ REQ-102](#req-102--composition-validation) *An existence lower bound alone asks for no member* names as one the RM makes non-empty once present, the top-up takes only its first source, a member of the first allowed child with room that needs no undescribed content and whose identity no earlier sibling with room carries, and the attribute gets no member where it has no such child, since, as that section says, a list with no member meets its existence. A list the RM makes non-empty once present does not meet it so. A HISTORY's `events`, while the HISTORY has no `summary`, are left to § [Precedence](#precedence) 2, which gives a HISTORY left with neither one of them. Any other such list whose existence lower bound is bounded and at least 1 is topped up to one member from all four sources above, as a list its cardinality asks a member of is, so that it holds a member or `Generate` returns the error § [Errors](#errors) names for the member it cannot build: `ErrArchetypeIDMissing` for an object of an archetype-root class the OPT names no archetype id for, and `ErrSlotFillUnsupported` for a slot whose includes cannot be satisfied. So, at that existence, an `ITEM_LIST` or `ITEM_TREE` whose `items` the OPT leaves without a child, or with slots only, holds no items: it is written with none where the RM or the OPT requires the structure, as the BMM requires `EVENT.data`, and left out where the attribute that holds it is not required (*Visit rule*), a `COMPOSITION`'s `content` whose only child is a slot gets that slot's fill, and a `SECTION`'s `items` the OPT leaves without a child is refused with `ErrArchetypeIDMissing`, since the member its BMM type gives is an archetype root. An attribute the RM declares multi-valued that the OPT writes as a single-valued one, such as `COMPOSITION.content` or `ITEM_TREE.items` under a `C_SINGLE_ATTRIBUTE`, is written as the list the RM declares, as the template validator reads it ([§ REQ-171](#req-171--validation-engine) *Structural access*): the value a visit builds from its allowed children, as for any single-valued attribute, is its one member, so such an `ITEM_TREE.items` over an `ELEMENT` holds that `ELEMENT`. With no allowed child, where the BMM does not mark it mandatory and it is not a list the RM makes non-empty once present whose existence lower bound is at least 1, only its existence asks for a member, so it gets none, and `Generate` **MUST NOT** refuse it with `ErrArchetypeIDMissing`; where it is such a list, or the BMM marks it mandatory, as it does `PERSON.identities`, it is topped up as above, from its BMM type. An optional multi-valued attribute with no allowed OPT child gets no member, so nothing archetype-rooted appears without its `archetype_details`. The generator never builds an archetype root from a BMM type: where it would, an optional attribute gets nothing, and a required one makes `Generate` return `ErrArchetypeIDMissing` (§ [Errors](#errors)).

**Identity.** Under every policy, the generator **SHOULD** give a `uid`, from `Options.UIDSource` or from its random fallback when `UIDSource` is nil, to a locatable it writes only where the OPT requires its `uid` (an existence lower bound of at least 1), and to no other locatable, a `COMPOSITION`, an ENTRY, a `GENERIC_ENTRY`, a `PARTY` and a `PARTY_RELATIONSHIP` included, as a slot fill and a locatable built from a BMM type are: the server that stores a top-level object gives it its version id, and the RM recommends that a top-level object's `uid` copy that id, while paths, not uids, identify the nodes inside it, so the `uid` "will usually be empty in most EHR data" (RM Common IM, *Unique Node Identification*). That a `PARTY` and a `PARTY_RELATIONSHIP` are left without a `uid`, as a `COMPOSITION` and an ENTRY are, is the reading this specification chooses, so that the server that stores a generated object assigns its id; a `PARTY` then breaks `Uid_mandatory` until it does (§ [Exceptions and known gaps](#exceptions-and-known-gaps)). When an `OBJECT_REF` the generator writes, a `PARTY_RELATIONSHIP`'s `source` and `target` included, carries no id value, the generator **SHOULD** give the id a value in its class's form, so that the reference's mandatory id holds a well-formed value: the value of a uid drawn the same way for a HIER_OBJECT_ID, a GENERIC_ID, a TEMPLATE_ID or a TERMINOLOGY_ID; that value followed by `::example::1`, a creating system `example` and the first trunk version, for an OBJECT_VERSION_ID; and `openEHR-EHR-CLUSTER.example.v1` for an ARCHETYPE_ID. Every `ARCHETYPED` the generator writes **MUST** carry `rm.Release`, the RM release the SDK is generated from, as its `rm_version` ([bmm-conformance.md § Generator output conventions](bmm-conformance.md#generator-output-conventions)). The template root's `ARCHETYPED`, when it has one, **MUST** carry the template id, and the generator **MUST NOT** write the template id in any other.

**Reproducible uids.** `UIDsFrom(src)` **MUST** return a uid source that draws each uid from `src` as an RFC 9562 version-4 UUID, its version and variant bits set and its other 122 bits taken from `src` ([RFC 9562 §5.4](https://www.rfc-editor.org/rfc/rfc9562.html#section-5.4)), so two sources in the same state give the same uids in the same order, and a nil source for a nil `src`, so the random fallback applies. Two `Generate` calls on one compiled OPT, neither with its context done, under any policy and either `ValueFill`, whose options are the same, a non-zero `Now` included, except that each call's `UIDSource`, from `UIDsFrom`, and, under `RandomFill`, its `ValueSource` are built on sources in the same state, **MUST** either both return a root, the two equal value for value, or both return no root and an error wrapping the same one of the errors *Inputs* above and § [Errors](#errors) name. The generator **MUST NOT** draw a uid from `ValueSource`: with `UIDSource` nil, every uid comes from the random fallback, whatever `ValueSource` holds. A source shared between `ValueSource` and `UIDsFrom` stays reproducible, but each uid drawn from it shifts the leaf values drawn after it; a separate source keeps the leaf values those of a run with no `UIDSource`. The source `UIDsFrom` returns is not safe for concurrent use, as a `Source` is not, so each concurrent `Generate` takes its own. The composition builder surfaces it as `composition.WithUIDSource` ([§ REQ-101](#req-101--generic-opt-driven-composition-builder)).

**Generic and untyped types.** An OPT-declared `DV_INTERVAL` instantiation (e.g. `DV_INTERVAL<DV_QUANTITY>`) is built as that typed interval, and `DV_INTERVAL<DV_ORDERED>` as an interval whose bounds can be any ordered value. One over another abstract parameter, such as `DV_INTERVAL<DV_QUANTIFIED>`, is built over a concrete descendant of that parameter (*What a visit writes*): the type the OPT names for its lower bound, else for its upper bound, where that type descends from the parameter, and otherwise the first concrete descendant in name order, so `DV_INTERVAL<DV_QUANTIFIED>` with no bound is built as `DV_INTERVAL<DV_COUNT>`, which the template validator admits. An untyped OPT child, one with no `rm_type_name`, is built as the type the BMM declares for the attribute that holds it, or the concrete type the generator builds for that type, so an untyped child of an `ELEMENT`'s `value` is built as a `DV_TEXT`. Another generic `rm_type_name` is a known gap (below).

**Intervals.** When both sides of an interval are bounded and its two bounds are two DV_QUANTITY, or two DV_PROPORTION, the generator, before it orders them, gives them one unit, or one type, that both sides admit, where there is one, so that the two are strictly comparable (RM `DV_INTERVAL.Limits_consistent`); the same holds in a `DV_INTERVAL<DV_ORDERED>` whose two bounds are both of one of those types. The generator tries the lower bound's units, then the upper bound's, then the units the lower side lists, and then those the upper side lists. Of these, it takes the first that both sides admit and in which an ordered pair fits both sides' OPT constraints, as the next paragraph puts a pair in order, and, where no unit both sides admit has such a pair, the first that both sides admit. So two bounds that share their units keep them, unless an ordered pair fits both sides only in another unit. A side admits the units its OPT constraint accepts: its C_DV_QUANTITY ([§ REQ-103](#req-103--primitive-constraint-introspection)), or the C_STRING on the bound's `units` where the OPT builds the bound attribute by attribute; a side the OPT leaves without a constraint on units admits any. A side lists the units of its C_DV_QUANTITY's entries; where its C_DV_QUANTITY constrains a `property` and lists no entry, the units § REQ-103 gives that property (`PropertyUnits`), which are the units such a side admits; and where the OPT builds the bound attribute by attribute, the list of the C_STRING on its `units`. A side whose C_DV_QUANTITY lists units takes, in a new unit, the magnitude `ExampleValue` gives for the first entry in that unit, and any other side keeps its magnitude. The type is chosen in the same way, among the lower bound's type, then the upper bound's, then every kind in code order, and a side admits a type where its bound can be settled as that kind inside its OPT constraints, as § [Precedence](#precedence) 4 settles a kind, and is then so settled. A side whose bound carries a `normal_range` of its own admits only its bound's own units and type. Where the two sides admit no one unit or type, the generator leaves the pair as generated; it leaves two bounds of different classes as generated too.

When both sides of an interval are bounded, the generator puts the two bounds in order (BASE `Interval.Limits_consistent`) where it can compare them and an ordered pair fits both sides' OPT constraints, and leaves any other pair as generated. A bound that carries a `normal_range` and a `normal_status` of its own fits its side only with a value that keeps its own `Normal_range_and_status_consistency` (§ [Precedence](#precedence) 3). The pairs it can compare are two DV_COUNT; two DV_QUANTITY with equal `units`; two DV_PROPORTION of one `type`, by ratio; two DV_ORDINAL, by `value`; and two DV_DATE, two DV_TIME or two DV_DATE_TIME values the REQ-123 parse accepts, in the order [§ REQ-112](#req-112--template-less-reference-model-validation-floor) *DV_INTERVAL* gives them: by magnitude, a partial value standing for the start of the period it names, and two times or date-times written with different zone designators as instants. The same holds in a `DV_INTERVAL<DV_ORDERED>` whose two bounds are one of those types. No other pair is one it can compare, for example, a zoned against a zoneless time or date-time, a value the REQ-123 parse refuses, or two DV_DURATION.

#### Precedence

Where the rules above meet the OPT or the RM, the generator decides as follows.

1. The OPT wins over an RM default. Where the OPT's own constraint on an attribute rejects a default, as a `C_CODE_PHRASE` that names another terminology does (an OPT can name a `DV_MULTIMEDIA` media type in terminology `openEHR`), or a `C_STRING` on a coded text's `value` that rejects the rubric, the generator keeps the value the walk wrote, which that constraint admits, where item 4 gives it no other. Where the OPT prohibits an attribute that no RM rule needs, the generator writes nothing there, neither a default nor a `uid`.
2. An RM rule that needs an attribute present or absent wins over the OPT and over the visit rule. Present: an attribute the BMM marks mandatory; an ELEMENT's `value` when the OPT prohibits its `null_flavour` and the walk wrote no value, and its `null_flavour` when it has no value (`Inv_null_flavour_indicated`); a `PARTY_IDENTIFIED`'s `name` when it has no `name`, `identifiers` or `external_ref` (`Basic_validity`), as the text `example` where the OPT gives it no allowed child; a `DV_MULTIMEDIA`'s `uri` when it has neither `uri` nor `data` (`Not_empty`); and a `HISTORY`'s `events`, or else its `summary`, when it has neither (`Events_valid`). The generator writes such an attribute as a visit writes it (§ Contract *What a visit writes*), whether the OPT prohibits it or the policy would not visit it: from its first allowed OPT child where it has one, and from its BMM type where it has none. Two take a value of their own instead, where the OPT names no allowed child for them: a `DV_MULTIMEDIA`'s `uri` the one *RM defaults* gives and a `PARTY_IDENTIFIED`'s `name` the text `example`. A `PARTY`'s `uid`, which `Uid_mandatory` needs, is not in this list: *Identity* above governs it (§ [Exceptions and known gaps](#exceptions-and-known-gaps)). A `HISTORY`'s two are tried in this order: a member of `events` built from its first allowed child that needs no undescribed content (§ [Slot fills](#slot-fills); a slot always needs it); a `summary` built from its first allowed child that needs no undescribed content; a member of `events` built from its BMM type, where the OPT names no child under `events`; a `summary` built from its BMM type, where the OPT names no child under `summary`; a member of `events` built from its first allowed child that is not a slot; a `summary` built from its first allowed child that is not a slot. So a child that needs undescribed content is passed over for a `summary` or a BMM type the OPT allows, and is built only where neither is allowed. An attribute the OPT prohibits, and an `events` whose cardinality upper bound is 0, allow none of them. The generator writes the first of the six the OPT allows, and neither where it allows none (§ [Exceptions and known gaps](#exceptions-and-known-gaps), *An OPT that contradicts itself*). Absent: an ELEMENT with a `value` carries no `null_flavour` and no `null_reason` (`Inv_null_flavour_indicated`, `Inv_null_reason_valid`); a bound of a REFERENCE_RANGE's `range` carries no `normal_range` and no `other_reference_ranges` (`Range_is_simple`); where the OPT allows both a `value` and a `null_flavour`, the `value` gives way when the OPT requires the `null_flavour` or the `null_reason` but not the `value`, and wins otherwise.
3. An RM rule that narrows a value the OPT leaves open wins over the leaf's `ExampleValue` and a `RandomFill` draw. These are the rules the generator narrows by, and the only ones (item 4 names those that keep a value within a set): BASE `Type_validity` narrows a PARTY_REF `type` to a party class name and an ACCESS_GROUP_REF `type` to `ACCESS_GROUP`, `Match_valid` a TERM_MAPPING `match` to `>`, `=`, `<` or `?`, `Magnitude_status_valid` a `magnitude_status` to `=`, `<`, `>`, `<=`, `>=` or `~`, `Accuracy_is_percent_validity` with `Accuracy_validity` a percentage `accuracy` to more than 0 and at most 100, or, where the OPT admits no such accuracy, its `accuracy_is_percent` to false where the OPT admits that, `Normal_range_and_status_consistency` an ordered value whose `normal_status` is `N` into its `normal_range` and one with another `normal_status` out of it, where the value and the range's bounds are a pair § Contract *Intervals* says the generator can compare, the 32-bit range of an RM `Integer` a `C_INTEGER` that reaches past it and the values a `C_DV_ORDINAL` lists past it, and the lower bound -1 of a `DV_QUANTITY`'s or `DV_PROPORTION`'s `precision` ([§ REQ-112](#req-112--template-less-reference-model-validation-floor)) a precision range that reaches below it.
4. An RM rule that keeps a value within a set the OPT's constraint can reach past wins over the leaf's `ExampleValue` and a `RandomFill` draw where that constraint admits a member of the set, and gives way to the OPT where it admits none. These rules are the code set or openEHR terminology group each row of the *Coded invariants* table of [§ REQ-112](#req-112--template-less-reference-model-validation-floor) ties a coded attribute to, DV_PERIODIC_TIME_SPECIFICATION `Value_valid` (`HL7:PIVL` or `HL7:EIVL`), and the rules of a DV_PROPORTION's kind (`Type_validity`, `Unitary_validity`, `Percent_validity`, `Fraction_validity`, `Precision_validity`, `Valid_denominator`). A value the walk wrote that the rule accepts stays. Otherwise the generator writes, without a draw, the RM default § Contract gives where the OPT admits it, a coded default with its rubric, and else the first value the OPT's constraint names that the rule accepts: for a coded attribute the first one the constraint lists, for a formalism the first of `HL7:PIVL` and `HL7:EIVL` the constraint admits, and for a DV_PROPORTION the first kind, in code order, whose rules the OPT's constraints on its parts let it meet. Where there is none, the value the walk wrote stays and the root breaks the rule (§ [Exceptions and known gaps](#exceptions-and-known-gaps)), as it does where the OPT admits a coded value of the set that it does not list.

#### Errors

An object the walk reaches, of a class the floor treats as an archetype root ([§ REQ-112](#req-112--template-less-reference-model-validation-floor) *Archetype roots*) for which the OPT names no archetype id, whether an OPT node without one (a slot excepted, which § Slot fills governs), a required attribute with no allowed OPT child (a list that only its existence requires asks for no member, § Contract *What a visit writes*), or the template root itself, **MUST** make `Generate` return an error wrapping `instance.ErrArchetypeIDMissing` that names the RM type and the OPT path, at every policy, either `ValueFill`, and through the builder; the generator invents no archetype id for it. An OPT node of that kind, such as an `ADMIN_ENTRY` an OPT defines inline under a `SECTION`, is undescribed content, as a slot nothing can fill is (§ [Slot fills](#slot-fills)), so the walk reaches it only where the OPT or the RM requires it: as a child the OPT does not leave optional, or as the member a top-up of a required attribute takes (§ Contract *What a visit writes*). Under `Large` and `Medium`, an optional child of that kind gets no member, and an attribute whose members would all need it is not visited where that attribute is not required or only its cardinality lower bound requires it (§ Contract *Visit rule*), so `Generate` returns a root there; under `Required`, an optional child gets no member of its own. Where the walk leaves such a node out, the defect is the OPT's, and the generator does not report it.

`Generate` **MUST** return no root and an error wrapping `instance.ErrConstraintUnsatisfiable` that names the RM type, the attribute and the OPT path in each of these cases, so it never writes a value the constraint rejects:

- no value can satisfy a primitive leaf's constraint (for example a STRING whose pattern and list admit no string the generator can derive), or none the generator can derive is left once an RM rule § [Precedence](#precedence) 3 names narrows it (for example a C_STRING on a TERM_MAPPING `match` that admits none of the four match codes);
- the walk visits an attribute the OPT declares multi-valued whose cardinality upper bound is bounded and less than the sum of the occurrences lower bounds, each bounded, of its allowed children that are not slots, so that no instance holds every member those children ask for within that bound (ADL 1.4 *cADL*, validity rule VCOC: the interval from "the sum of all occurrences minimum values" to "the sum of all occurrences maximum values" lies "inside the interval of the cardinality"; AOM 2 validity rule VACMCO: "one instance of every mandatory child object" is "to be included within the cardinality range"). A child that states no occurrences, or occurrences with an unbounded lower bound, adds nothing to that sum, as it asks a list for no member ([§ REQ-102](#req-102--composition-validation) *An existence lower bound alone asks for no member*);
- the walk would visit an attribute the generator has no writer for (§ Contract *Visit rule*): no value it can derive satisfies the OPT there.

A required slot whose includes cannot be satisfied makes `Generate` return `ErrSlotFillUnsupported`, as § [Slot fills](#slot-fills) says.

An error `Generate` returns **MUST NOT** wrap more than one of `ErrArchetypeIDMissing`, `ErrConstraintUnsatisfiable` and `ErrSlotFillUnsupported`, so a caller tells a missing archetype id, an unsatisfiable constraint and an unfillable slot apart with `errors.Is`: `ErrSlotFillUnsupported` is kept for slots, and `ErrArchetypeIDMissing` for archetype roots.

### Exceptions and known gaps

A root `Generate` returns can break § Contract's output rule in these cases, and in no other:

- **An interval pair left as generated** (§ Contract *Intervals*) can break `DV_INTERVAL.Limits_consistent`, which the floor reports for a pair it orders whose bounds are out of order and for a pair it reads as not strictly comparable (§ REQ-112 *DV_INTERVAL*): bounds of two classes, and two DV_QUANTITY or two DV_PROPORTION whose two sides admit no one unit or type; an ordered value that forms no pair § Contract *Intervals* lists with the bounds of its `normal_range` is left as generated too (§ [Precedence](#precedence) 3), so it can break `Normal_range_and_status_consistency`.
- **An OPT constraint that admits no value an RM rule accepts**, where § [Precedence](#precedence) 3 does not name that rule, or that admits a coded value a rule of § [Precedence](#precedence) 4 accepts without listing it, such as an RM default that yields to the OPT (§ [Precedence](#precedence) 1), or a PARTICIPATION `mode` the OPT codes in `local`, breaks that RM rule.
- **An OPT that contradicts itself** in a way § [Errors](#errors) does not refuse, such as one that requires an attribute and prohibits every child of it, or requires a list and gives it a cardinality upper bound of 0, gets whichever side § Contract writes; one whose `HISTORY` allows none of the events and summaries § [Precedence](#precedence) 2 tries gets neither, and breaks `Events_valid`. One whose list's cardinality lower bound exceeds the members its allowed children's occurrences upper bounds admit, none of them a slot, gets the members its top-up adds past its first allowed child's occurrences (§ Contract *What a visit writes*). One whose children's occurrences lower bounds add up past the cardinality upper bound of their list gets no root where the walk visits that list (§ [Errors](#errors)); where the walk does not, as under `Required`, which builds no member of an optional child that holds the list, the root holds no instance of the list and the contradiction does not reach it.
- **A value the caller supplies** through `Options` (a language, a territory, a composer, a uid from `UIDSource`) is written as given, valid or not.
- **An RM invariant that relates the object to another**, such as PARTY `Relationships_validity` or PARTY_RELATIONSHIP `Source_valid` and `Target_valid`, which a single generated object cannot meet, is not kept.
- **A placeholder code on an attribute an RM rule ties to a code set or terminology group** for which § Contract gives no default, such as a `normal_status`, or a DV_MULTIMEDIA `compression_algorithm` or `integrity_check_algorithm`, can break that rule.
- **An attribute the OPT prohibits that an RM rule needs, a list the BMM requires a member in whose cardinality upper bound is 0, or an attribute the OPT requires that an RM rule needs absent** (§ [Precedence](#precedence) 2), such as `CLUSTER.items` or a PARTY's `identities` at cardinality `0..0`, or a `normal_range` on a bound of a REFERENCE_RANGE's `range`, breaks the OPT's prohibition, bound or requirement.
- **An earlier sibling with room that carries a later, required one's identity, where neither pins a name** (§ Contract *What a visit writes*): the validator binds an item to the first of them that has room and under whose constraints it validates ([§ REQ-102](#req-102--composition-validation) *Structural — binding items*), so the earlier sibling takes the member built for the later one wherever that member validates under it. Under `Medium` an optional earlier sibling gets no member of its own and takes the later one's. Under `Large` it gets a member of its own, unless the list's cardinality upper bound leaves it no room once the later sibling has its members (§ Contract *What a visit writes*): it then gets none and takes the later one's, as under `Medium`, as an optional `at0001` before a required `at0001` in `CLUSTER.items` at cardinality `1..1` does. Its own member fills it where its occurrences upper bound is 1; where that occurrences bound leaves it room for a second member, as a bound above 1, or none, does, it takes the later one's as well. A required earlier sibling with no occurrences upper bound always has room and takes the later one's member beside its own, under every policy. A root can then fail the template validator by the later sibling's occurrences.
- **A `PARTY` without a `uid`** (§ Contract *Identity*): the generator writes a `PARTY`'s `uid` only where the OPT requires it, so a `PARTY` it writes otherwise breaks `PARTY.Uid_mandatory`, which the floor does not evaluate ([§ REQ-112](#req-112--template-less-reference-model-validation-floor) *What the floor does not evaluate*). The object the server stores meets the rule once the server assigns its id.
- **A slot whose occurrences the OPT constrains** (below) can be filled where the OPT prohibits it, or left empty where the OPT requires it.

The known gaps below describe the generator as it is; they are informative.

**Known gap: attributes the generator cannot write.** The generator has no writer for a LOCATABLE's `links` and `feeder_audit`, for an EHR_ACCESS's `settings`, whose RM type ACCESS_CONTROL_SETTINGS has no concrete class, or for a list whose items the RM types as primitive values other than a DV_MULTIMEDIA's `data`, such as its `integrity_check`; the RM requires none of them. So `Generate` leaves such an attribute unwritten where it is not required as § Contract *Visit rule* defines it, whatever the OPT puts under it, and where it is a list only its existence requires, since a list with no member meets its existence; it returns `ErrConstraintUnsatisfiable` and no root where it is required otherwise, as an optional `links` that holds a mandatory LINK is (§ Contract *Visit rule*, § [Errors](#errors)). A DV_MULTIMEDIA's `data` is an array of octets that no OPT child describes, so the walk does not visit it, and the inline `data` § Contract gives a DV_MULTIMEDIA is written instead.

**Known gap: other generic types.** An OPT node whose `rm_type_name` is a generic type other than a `DV_INTERVAL` instantiation, such as `POINT_EVENT<ITEM_TREE>` or `REFERENCE_RANGE<DV_QUANTITY>`, cannot be built, and `Generate` returns an error. Nor can a `DV_INTERVAL` over a type that is no `DV_ORDERED` class, such as `DV_INTERVAL<DV_TEXT>`, which the RM does not admit as its parameter; a `DV_INTERVAL` over an abstract `DV_ORDERED` class is built as *Generic and untyped types* above says.

**Known gap: slot occurrences.** The parser does not read an `ARCHETYPE_SLOT`'s occurrences, so the generator cannot tell a slot the OPT prohibits (an occurrences upper bound of 0) or requires (a lower bound of at least 1) from an optional one: a top-up whose only allowed children are slots can fill a prohibited one, and a required slot is not filled where it sits beside a non-slot child, or under a list that only its existence otherwise requires (§ Contract *What a visit writes*). The template validator reads the same compiled tree, so it cannot count a slot's occurrences either and reports neither case.

### Primitive-leaf value fill

`Policy` selects *which* nodes are materialised; an orthogonal **`ValueFill`** selects *how* primitive leaves are valued. The SDK **MUST** offer two fills, and read a `ValueFill` other than `RandomFill` as `ExampleFill`, with no error: `ExampleFill` (default) populates each leaf with its REQ-103 `PrimitiveConstraint.ExampleValue` — a single representative value, byte-identical across calls for one OPT; `RandomFill` draws each leaf from within its constraint (in-range magnitudes, value-set-member codes, enumeration entries), valid by construction and varying between calls.

`RandomFill` reproducibility is caller-controlled via **`Options.ValueSource`** (a `math/rand/v2.Source`): a fixed source makes leaf values byte-reproducible (§ Contract *Reproducible uids*); `nil` draws from the auto-seeded package global so successive calls differ — mirroring the `UIDSource` determinism seam. A `Source` is not safe for concurrent use, so each concurrent `Generate` takes its own source, or leaves it `nil` for the concurrency-safe global. The composition builder surfaces the seam as `composition.WithValueFill` / `composition.WithValueSource`.

**Deferred.** `Complete` is an alias of `Large`. A complete level of its own, the ITS-REST `detail_level=complete` (every data point the template allows, as reference guidance, not expected to be committable), is planned but not delivered and not a priority; when it lands, `Complete` becomes its own value. That level is **not** part of the v1 `Policy` contract. Tracked in the roadmap.

### Trust model

The compiled OPT is **authoritative for structure**. The RM graph is assembled attribute-by-attribute from compiled metadata; the generator never guesses paths from an empty composition. Primitive leaves are valued from their constraint as § [Primitive-leaf value fill](#primitive-leaf-value-fill) says; REQ-103 guarantees `Validate(ExampleValue()) == nil` for bounded constraints. Compile captures an OPT `<assumed_value>` into the constraint's `Default` field, but the generator does not read it: the value the `ValueFill` gives stands.

The generator is **sound** (every root it returns meets § Contract's output rule, apart from § [Exceptions and known gaps](#exceptions-and-known-gaps)), not **complete** (it does not enumerate every valid instance — different policies may produce different but equally valid trees). Sound × validator-aligned ⇒ PROBE-027 cross-checks the contract.

### Slot fills

A member is *undescribed* when no OPT node describes it: a slot fill, or a LOCATABLE built from the BMM type of an attribute with no allowed OPT child. An OPT node, not a slot, of a class the floor treats as an archetype root ([§ REQ-112](#req-112--template-less-reference-model-validation-floor) *Archetype roots*) for which the OPT names no archetype id describes no member the generator can build either, since the generator invents no archetype id (§ [Errors](#errors)): this specification reads it as undescribed content, as a slot nothing can fill is. A node *needs undescribed content* when it is a slot or such an archetype-root node, or when an attribute on it that is required (§ Contract *Visit rule*) can be given no member but an undescribed one: it has no allowed OPT child and its member would be a LOCATABLE, every allowed OPT child of it is a slot or such a node, or it is single-valued and the child that builds its member (§ Contract *What a visit writes*) is a slot or such a node. § Contract applies the term: under `Large` and `Medium` an optional child (an occurrences lower bound of 0) that needs undescribed content gets no member of its own, the first optional archetype root `Medium` keeps is the first that needs none (*What a visit writes*), and an attribute whose members would all be undescribed or need undescribed content is not visited where that attribute is not required or only its cardinality lower bound requires it (*Visit rule*). The rule reads the node's own attributes only: below a child the OPT or the RM requires, the walk builds what § Contract says, undescribed members included where the BMM, a child's occurrences, or the cardinality of a list that one of those or its existence requires asks for a member, so the described content around them is kept; an attribute that only its existence requires, which a list the RM makes non-empty once present never is, gets no undescribed member, and is left with none where it has no other (*What a visit writes*). Such an attribute still counts as required in the definition above, so a node whose attribute of this kind can be given no member but an undescribed one still needs undescribed content, and is still left out where it is optional. So a slot the OPT leaves open, and an attribute it leaves without a child, get content only where the BMM, the OPT's counts, or the existence of a list the RM makes non-empty once present (*What a visit writes*) ask for a member of a node the RM or the OPT requires, never because the policy builds an optional node that holds nothing else, and never for any other existence or for a cardinality lower bound alone.

A *required slot* is one the walk fills: one a top-up fills, or the first allowed child a visited single-valued attribute takes (§ Contract *What a visit writes*). The walk stamps a required slot, at every policy and through the builder, with an archetype id drawn from the parsed include grammar of [§ REQ-103](#req-103--primitive-constraint-introspection) *Slot assertions* when a safe example can be synthesized; when the OPT carried no parseable includes, the id **SHOULD** be `openEHR-EHR-<RMType>.example.v1`, which the validator's RM-type-prefix rule admits. A required slot whose includes cannot be satisfied **MUST** make `Generate` return `ErrSlotFillUnsupported`, and the generator invents no archetype id for it.

### Out of scope

- **Clinically realistic distributions** (plausible names, plausible vitals, FHIR Synthea-style synthetic patient data).
- **FLAT / STRUCTURED example strings** — REQ-053.
- **Encoding to wire bytes** — callers run `canjson` or `canxml` themselves.
- **Authoring-time templates (OET)** — REQ-100 is OPT-only in v1.
- **Generating every valid instance** — combinatorial coverage is out of scope.
- **Writing to a CDR** — caller's `openehr/client/ehr/` responsibility.
- **Validating during generation** — separate `validation.ValidateComposition` call (cross-checked by PROBE-027).
- **Runtime federated slot-fill repository** — same compromise as validation.
- **Multi-language term translation** — caller seeds `Options.Language`.

- **Probes:** PROBE-027 — `instance.Generate` checked with `validation.ValidateComposition` (COMPOSITION roots) or `validation.Validate`, and with `validation.ValidateRM`, across the vendored OPTs that compile.

## REQ-101 — Generic OPT-driven composition builder

**Status:** Draft.

The SDK **MUST** ship a composition-specific authoring layer at `openehr/composition/` that produces an in-memory `*rm.Composition` graph driven by a compiled OPT. REQ-101 owns the composition options and path-first authoring API; REQ-107 owns the skeleton-synthesis engine. The composition builder is a thin shim over `openehr/instance` — no second OPT walker lives here.

### Scope

Two entry points:

1. **`NewSkeleton(ctx, c, opts...) (*rm.Composition, error)`** — produces a structurally-conformant default composition whose leaves hold REQ-107's example values. Delegates to `instance.Generate` with the policy `WithPolicy` selects, `Medium`, the instance package's default, when none is given, and unwraps the root via `instance.AsComposition`.
2. **`NewBuilder(ctx, c, opts...) (*Builder, error)`** — seeds a `Builder` from a `Large` skeleton, then accepts `Set(path, value)` calls. `Build()` returns the populated graph and aggregates per-path errors.

### Contract

- **Composition-specific options** — `WithLanguage(code)`, `WithTerritory(code)`, `WithComposer(p)`, `WithCategory(c)`, `WithNow(t)`. The first four translate to fields on `instance.Options` and pin `Composition.language` / `.territory` / `.composer` / `.category`. `WithNow` injects the clock used for `EVENT.time` and `EventContext.start_time` defaults so tests stay deterministic.
- **Uid source** — `WithUIDSource(src)` **MUST** pass `src` to `instance.Options.UIDSource`, for `NewSkeleton` and `NewBuilder` alike, so every uid the skeleton carries comes from `src` ([§ REQ-107](#req-107--template-driven-rm-instance-example-generator) *Identity*); a nil `src`, or no `WithUIDSource`, leaves the generator's random fallback in force. With `instance.UIDsFrom` on a fixed source, `WithNow` and, under `instance.RandomFill`, `WithValueSource`, a skeleton is reproducible as REQ-107 *Reproducible uids* says.
- **Skeleton policy** — `WithPolicy(p)` selects the [§ REQ-107](#req-107--template-driven-rm-instance-example-generator) `instance.Policy` `NewSkeleton` passes to `instance.Generate`. With no `WithPolicy`, `NewSkeleton` **SHOULD** use `Medium`, the zero value, so a skeleton holds what `instance.Generate` builds from default `Options`. `Set` routes a value into a node the skeleton already holds and does not build a missing one, so it needs a member of every optional archetype and of every named use of one, which only `Large` builds. A later use of one identity that pins no name ([§ REQ-107](#req-107--template-driven-rm-instance-example-generator) *What a visit writes*: its archetype id or `node_id`) has the compiled path of the first, so `Set` reaches the first use's member alone, and the member `Large` builds for the later use keeps the values the skeleton gave it. `NewBuilder` therefore **SHOULD** build on `Large` when no `WithPolicy` is given, and it **MUST** accept only `Large` (and so `Complete`): it refuses `Medium` and `Required` (and so `Minimal`) with an error that wraps `composition.ErrUnsupportedPolicy` and not `instance.ErrUnsupportedPolicy`, since REQ-107 defines both, and returns no `Builder`, before it builds a skeleton; an explicit `WithPolicy(instance.Medium)` is refused like any other, though `Medium` is the zero value. `NewSkeleton` **MUST** accept all three. Both **MUST** refuse a `Policy` value that is none of the three the same way, with an error that also wraps `instance.ErrUnsupportedPolicy`, since REQ-107 defines no other.
- **Path-first API** — `Set(path string, v any) error` looks up the compiled node via `Compiled.NodeAt(path)` and routes the assignment through the parent attribute. Typed helpers `SetText`, `SetQuantity`, `SetCodedText` wrap the most common DV shapes. A path is a canonical OPT path as the compile step produces it, predicate-bracketed segments included where the OPT pins archetype roots or at-codes.
- **Type enforcement** — `Set` **MUST** accept a value whose type the binding tiers of [§ REQ-102](#req-102--composition-validation) *Structural — alternatives* bind to a node the template allows at the path, one whose occurrences are not 0..0: the node `Compiled.NodeAt(path)` returns, or another alternative the OPT lists at the same path under the same attribute (the tiers bind by the type alone, to the first node of the first tier that admits it; the trial within a tier is the validator's); and one the RM attribute the path writes can hold, its RM type conforming to that attribute's type in the pinned RM BMM, or, where that type is a generic parameter the template leaves open, to the parameter's constraint (`DV_ORDERED` for the bounds of a bare `DV_INTERVAL`). So a `*rm.DVCodedText` is accepted at a DV_TEXT path; a concrete data value at a node the OPT types as an abstract class or leaves untyped; a `*rm.DVDuration` at an ELEMENT value the OPT types with the AOM 1.4 short name `DURATION`; a `DV_INTERVAL<DV_COUNT>` at a `DV_INTERVAL<DV_ORDERED>` node; and a `*rm.DVQuantity` at an ELEMENT value the OPT allows as DV_CODED_TEXT or DV_QUANTITY. `Set` **MUST** return `ErrTypeMismatch` for any other value: one that binds to no such node (e.g. a `*rm.DVText` passed at a DV_QUANTITY path), one the attribute cannot hold (e.g. a `*rm.DVDuration` at the `DURATION` primitive under `DV_DURATION.value`, which holds a String), one at a path below the root that writes no RM attribute (a template may constrain a BMM function, such as `DV_PROPORTION.is_integral`, as if it were one), one that is not an RM value, and a nil or typed-nil value. `Set` **MUST** return `ErrUnknownPath` for a path the template does not have. The root path writes no attribute and is not settable: `Build` **MUST** refuse a value set there with `ErrInvalidPath`. Each wraps its context with `fmt.Errorf("...: %w", err)`, so a caller compares it with `errors.Is`.
- **Aggregated errors** — `Set` records errors against the builder but does NOT short-circuit; subsequent assignments still attempt. `Build()` returns the populated `*rm.Composition` plus the aggregated error (joined via `errors.Join`) so callers can recover every faulty path in one round-trip rather than chasing one error at a time.
- **TemplateID propagation** — `Builder.TemplateID()` returns the OPT's `Compiled.TemplateID()`, suitable for the REST `composition.WithTemplateID` option so the CDR validates against the same template.

### Trust model

REQ-101 trusts REQ-107 for the skeleton walk: every implicit RM attribute, every primitive default, every LOCATABLE identity stamp comes from `instance.Generate`. The builder's own part is to translate its options into `instance.Options` and to route each value along its path to the attribute it writes.

### Out of scope

- **Per-template generated Go structs.** v1 stays generic — consumers do not import codegen'd vital-signs structs through this package. OET-driven authoring is a follow-up.
- **FLAT / STRUCTURED ingest.** Caller decodes externally (REQ-053) and feeds the resulting `*rm.Composition` through validation.
- **Slot resolution against a federated archetype repository.** Same compromise as REQ-102 / REQ-107: pinned slot fills come from the OPT.
- **Encoding to wire bytes.** Callers run `canjson.Marshal` / `canxml.Marshal` themselves ([REQ-013](module-layout.md#req-013--building-block-independence)).
- **Validating during Build.** A `Build()` result is validated by a separate `validation.ValidateComposition` call; the builder is sound by construction but not a validator.

- **Probes:** PROBE-023 — `composition.NewBuilder` + `Set` → `Build` → `canjson.Marshal` → `canjson.Unmarshal` → re-marshal round-trip preserves values at key paths.

## REQ-109 — AQL static lint

The SDK **MUST** ship a building-block parse + lint pipeline for hand-written, imported, or `aql.NewQuery(literal)` AQL, so CI validators, MCP tools, and pre-flight checks can catch defects before a query reaches the CDR — without replacing the typed builders (REQ-055) or the CDR as the execute-time semantic authority (PROBE-021).

The lint runs three layers and **MUST** be collect-all (return every issue, not fail-fast), matching REQ-102.

### Syntax floor — the SDK grammar profile

The parse layer **MUST** validate against the **SDK-maintained grammar profile**, not a live pull from specifications.openehr.org: foundation openEHR AQL (QUERY Release-1.1.0) plus the documented `SDK-AQL-NNN` deltas in [`resources/aql/grammar/DIVERGENCES.md`](../../resources/aql/grammar/DIVERGENCES.md) (ADR [0007](../adr/0007-aql-antlr-grammar-profile.md)). Deltas are classed **relaxation** (admits more than official AQL, e.g. `SELECT *`) or **correction** (fixes a foundation weak spot).

**Lint-clean is not spec-conformance, and not execute-success.** Because the profile deliberately admits relaxations and the CDR is the path authority, a query the SDK lints clean can still be rejected on execution; conversely the lint targets only the contract below.

The profile **MUST** admit every query the foundation grammar admits. A query that a conformant engine answers and the profile refuses therefore lies outside foundation AQL, as an engine grammar extension, and [PROBE-107](conformance.md#probe-107--upstream-aql-suite-admissibility-corpus) records it by name, with that reason, as a decline; an unexplained refusal is a defect in the profile. Recording a decline never widens the profile: admitting an engine extension is a separate `SDK-AQL-NNN` relaxation.

### Layer 1 — Syntax

- Empty / whitespace-only input **MUST** yield code `aql_empty` (before parse).
- Input that does not parse as `selectQuery` per the profile **MUST** yield code `aql_syntax`.
- The `aql_syntax` `Detail` **SHOULD** carry the parser's `line:column` when the parser reports a position, and **SHOULD NOT** invent one when it does not, because a reader takes a printed coordinate for a real one: a `parse.SyntaxError` whose `Position` is zero prints no `0:0` from `Error()`, and its `Detail` carries no `L:C:` prefix.
- `parse.Parse` returns a `*parse.SyntaxError` wrapping the building-block sentinel `aql.ErrSyntax`; the `validation.ValidateAQL` bridge maps `aql_syntax` / `aql_empty` to `validation.ErrAQLSyntax` via `Issue.Err()`.

### Layer 2 — Shape (AST walk, no CDR)

| Check | Code | Severity | Rule |
|---|---|---|---|

Fires once per query carrying a `TOP`. |

Reachable only when the caller supplies `Options.Query`, and keyed on its `Fetch` alone: an `Offset` **MUST NOT** raise it, the exclusion naming the row limit only. Fires in addition to `aql_deprecated_top`. `Build()` also refuses an envelope `Offset` beside a `TOP` ([§ REQ-163](#req-163--aql-write-side-expressivity-parity)), because it declines to author two row bounds; the lint reads a query it did not author, so it reports only the exclusion the Query API states. |
| Bare / mixed `SELECT *` | `aql_select_star` | Warning | A projection carrying a `*` item **SHOULD** raise this code, and `COUNT(*)` **MUST NOT**: it uses the SDK-AQL-002 relaxation, and official QUERY 1.1.0's only use of `*` is `COUNT(*)`. |

The three `TOP` codes **MUST** key on the `TOP` clause's presence in the source, not on a decoded count: a count too large to represent leaves no bound to read ([§ REQ-113](#req-113--execution-oriented-parsed-aql-ast)'s residual), and the query carrying it still draws them. The other half of each pair is read from its own channel: the in-text `LIMIT` clause for `aql_top_with_limit`, the request envelope's `Fetch` for `aql_top_with_fetch`.

SELECT-present-with-≥1-projection and FROM-present are guaranteed by a successful parse (the grammar requires both), so they raise no Layer-2 issue.

Layer 2 additionally carries the semantic and portability check groups of [§ REQ-161](#req-161--aql-semantic-and-portability-lint) and the path-shape group of [§ REQ-164](#req-164--aql-path-shape-and-paging-lint), additive codes whose severities and firing rules are specified once there.

Two grammar-admitted, server-executable shapes resolve without `aql_unknown_alias`:

- An `ORDER BY` key that is a bare identifier (no path tail, no predicate) and names no FROM alias **MUST** be resolved against the SELECT `AS` aliases (`SELECT x/y AS score … ORDER BY score`) before `aql_unknown_alias` is raised. FROM/CONTAINS is consulted first, and nothing else resolves through a SELECT alias: an identifier matching neither, an `AS` alias with a path tail (`score/magnitude`), and a `WHERE` path rooted on an `AS` alias each raise `aql_unknown_alias`.
- A bare `true` / `false` keyword in a value position (a comparison operand such as `WHERE s/is_queryable = true`, a SELECT item, a function-call argument) **MUST** be read as a boolean literal, not as a path root, by the lint and by the structured AST of [§ REQ-113](#req-113--execution-oriented-parsed-aql-ast) alike, so a consumer reads the construct the same way in every clause. With a predicate or a path tail (`true/nested`), or as an `ORDER BY` key (`orderByExpr` admits no literal), the keyword is a path and keeps its alias check.

### Layer 3 — Path & template (only when a compiled OPT is supplied)

| Check | Code | Severity | Rule |
|---|---|---|---|
| Archetype membership | `aql_archetype_not_in_template` | Error | Each literal archetype HRID in FROM/CONTAINS **MUST** be present in the compiled OPT (`Compiled.AllByArchetypeID`). |
| Path in template | `aql_path_not_in_template` | Warning | Each identified path **SHOULD** resolve under its alias's archetype subtree. |

A `$param` archetype predicate (`[$name]`, `parse.ClassExpr.ParamArchetype`) is not a literal HRID, so it **MUST NOT** raise `aql_archetype_not_in_template`, and it anchors no `aql_path_not_in_template` resolution: there is no literal subtree to walk, and the CDR resolves the bound scope at execution ([PROBE-021](conformance.md#probe-021--aql-parse-error-mapping)).

`aql_path_not_in_template` resolution walks the archetype-scoped compiled subtree (predicate-aware first-child descent) and warns only on high-confidence structural divergence: a path segment naming an attribute that does not exist on a node that has modelled attributes. It stays silent on unmodelled RM-leaf attributes (e.g. `/value/magnitude`) and on descent below the modelled tree, because the CDR, not the OPT index, is the path authority (PROBE-021). A path through a non-mandatory RM attribute the OPT did not constrain can still warn, which is why the check is a Warning.

### Issue model and entry points

- `openehr/aql/lint` owns its own `lint.Issue` / `lint.Result` / `lint.Severity`. `lint.Result.OK()` is true when no **Error**-severity issue is present (Warnings do not make a result not-OK).
- `lint.LintString(q, *Options)` is the raw-AQL entry; `lint.Lint(doc, *Options)` lints an already-parsed `*parse.Document`. `Options{Compiled, Query, Relation}` is nilable, but the three fields do not gate alike: nil `Compiled` drops Layer 3 and nil `Query` drops the parameter-binding checks, whereas nil `Relation` selects the REQ-160 default rather than switching anything off, so the REQ-161 semantic group always runs ([§ REQ-161 § Relation supply](#relation-supply)).
- `validation.ValidateAQL(q aql.Query, c *templatecompile.Compiled) validation.Result` is the seam: it parses `q.Q`, runs the layers, and maps `lint.Issue` → `validation.Issue` (code and severity carried verbatim) so callers already using `ValidateComposition` get one uniform `Result`.
- `validation.ValidateAQLWithTypeRelation(q, c, rel *contain.TypeRelation) validation.Result` is the same seam with the containment relation supplied by the caller, and `ValidateAQL(q, c)` is its nil call. [§ REQ-161 § Relation supply](#relation-supply) states the obligation to offer it and the bound on what a supplied relation changes.
- A published lint code is never re-pointed at another rule: consumers filter and gate on `Code`, so a code keeps its meaning for as long as it exists. `aql_contains_redundant_step` in particular **MUST NOT** be re-pointed at another rule.

### Value-free lint diagnostics

`lint.Issue` names a finding's location by quoting it: `Detail` is free text and `Path` is a path spelling. Its fields **MUST** follow the two-class rule of [§ REQ-113 § Value-free structured drop records](#value-free-structured-drop-records), classed as follows:

| Field | Class |
|---|---|
| `Code`, `Severity`, `Span` | **value-free**: never carries source text |
| `Detail`, `Path` | **value-bearing**: may embed query spellings |

`Path` is value-bearing deliberately: a path spelling carries its own predicates, so `o/data[at0001, 'Systolic']` is a path *and* a value. A consumer that treats `Path` as safe because it looks structural is the failure this classification exists to prevent. Naming `Detail` and `Path` value-bearing is what lets a disclosure boundary drop them deliberately instead of scrubbing them in hope.

`Issue.Span` is populated from the token positions lint already visits, and is zero when the issue is not attributable to a position. It **MUST** be the same type as the drop record's span (`lint.Span` re-exports `parse.Span`), so a consumer compares a lint span with a drop-record span directly.

### Out of scope (v1)

- **Terminology** (`TERMINOLOGY()` / `MATCHES` value-set membership), function signatures, `ORDER BY` type checking, and version-predicate **value** semantics beyond parse. Predicate *presence* on a `VERSION` operand is [§ REQ-161](#req-161--aql-semantic-and-portability-lint)'s `aql_version_no_predicate`.
- **CDR-grade path resolution**: full AQL-path-to-canonical-path mapping (node-id-on-structural-attribute vs canonical placement) is PROBE-021 territory; Layer 3 is best-effort, hence `aql_path_not_in_template` is a Warning.
- **Re-emission / pretty-printing**: canonical re-emission from the structured AST is [§ REQ-113](#req-113--execution-oriented-parsed-aql-ast)'s `(*parse.Query).Emit`.

- **Probes:** PROBE-028 — lint fixed query strings against the grammar profile (+ a compiled OPT for Layer 3) and assert a stable issue-code multiset; [PROBE-107](conformance.md#probe-107--upstream-aql-suite-admissibility-corpus) — every query the vendored upstream suites send and an engine answers parses under the profile, or is a recorded decline.

## REQ-111 — Public compiled-template bridge

The compiled-template form (`templatecompile.Compiled`) is the argument every template-driven entry point takes: the composition builder (REQ-101, `NewBuilder` and `NewSkeleton`), the RM instance synthesiser (REQ-107, `Generate`), the validator (REQ-102, `Validate` and its typed wrappers), and the AQL static lint (REQ-109, `lint.Options.Compiled`).

The SDK **MUST** ship a public constructor that turns a parsed OPT into that compiled form without exposing any `internal/` package, so external consumers can drive the full parse → compile → build → validate pipeline through public packages alone.

### Surface

```go
// Package github.com/cadasto/openehr-sdk-go/openehr/templatecompile

// Compiled is the public, externally-constructable compiled template.
// It is a type alias of the internal compiled form, so values returned
// by Compile are accepted as-is by composition, instance, validation
// and aql/lint, with no conversion.
type Compiled = <internal compiled form>

func Compile(opt *template.OperationalTemplate, opts ...Option) (*Compiled, error)

type Option func(*config)
func WithRMInfo(l rminfo.Lookup) Option       // custom RM-info source
func WithoutImplicitAttributes() Option        // OPT-declared attributes only

var ErrInvalidInput error  // re-export; errors.Is works across the boundary
var ErrPathNotFound error

// Introspection tree — also public, for form generation, path discovery,
// and custom mapping/validation. Aliases of the engine node types.
type CompiledNode = <internal compiled node>
type CompiledAttribute = <internal compiled attribute>
```

The committed public surface is `Compile`, `Compiled`, the introspection tree (`CompiledNode` / `CompiledAttribute`), the functional `Option`s, and the two sentinel errors — all aliases of the engine types, so a downstream package can navigate the compiled template (`Compiled.Root` / `NodeAt` → `CompiledNode.Attributes` → `CompiledAttribute.Children`) and hold the node types in its own signatures. Pre-1.0 the one area expected to change is multi-language term resolution (`CompiledNode.Term`'s `lang` parameter, § *Term definitions and bindings* below); the surface is otherwise stable. Everything reachable as a method on `Compiled` / `CompiledNode` / `CompiledAttribute` is committed (including the slot accessors `SlotIncludes` / `SlotExcludes` / `SlotRules` / `AllowsArchetypeID` / `ExampleSlotFillArchetypeID`); the compile engine and free helpers that are not methods on the exported types (e.g. `IsAOMPrimitiveShortName`) stay internal.

The consuming packages name the public `*templatecompile.Compiled` in their **exported** signatures, so the rendered API docs link the public package; because `Compiled` is a type alias, the public and the engine name denote the identical type and no conversion is needed.

### Term definitions and bindings

The SDK **MUST** expose structured accessors for the archetype term definitions and the external terminology bindings an OPT carries, without resolving any of them against a live terminology. The parsed OPT holds them as `ArchetypeTerm` and `TermBinding` records, read from `<term_definitions>` and `<term_bindings>`. `Compiled.TermLang(nodeID, lang)` resolves an at-code's term text scoped to the composition root archetype, and `CompiledNode.Term(code, lang)` walks up through the parent archetype roots for a context-sensitive lookup. An ADL 1.4 OPT carries a single document language (`Compiled.Language()`): when `lang` is empty or equals it, the OPT's `Items` map (`text`, `description`, …) is returned, and when `lang` differs and the OPT holds no translation, the document-language term **MUST** be returned, with no error; a caller tells absence by the `ok` result alone. `Compiled.TermBindingsForNode(nodeID)` filters the compile-time flattened binding list to the entries whose `NodeOrPath` equals the at-code, or whose AQL-like locator contains `[nodeID]` or ends with `/nodeID`. Looking a code up in SNOMED CT, LOINC, ICD or another external terminology is out of scope: the SDK surfaces the bindings the OPT carries and no more.

### Attributes the RM does not have

The compile step **MUST** mark, through `CompiledAttribute.NotInRM()`, each attribute the OPT declares whose name is neither a property nor a function of its node's RM class, of an ancestor of that class, or of a descendant of it. The class is read without generic parameters; the properties are those the compile's RM lookup gives, the ancestors and descendants those its class hierarchy (`rminfo.Hierarchy`) gives, and the functions those `rminfo.IsNonStorableAttr` names ([§ REQ-112 *Driver*](#driver)). `ISM_TRANSITION.name` is one. `EVENT.offset`, a function, is not, and nor is `ITEM_STRUCTURE.items`, a property of the descendants `ITEM_TREE` and `ITEM_LIST`. The compile **MUST NOT** mark an attribute of a class the lookup does not know, any attribute when the lookup gives no class hierarchy, or an attribute it injects. No instance of the node's class can carry a marked attribute, so strict mode accepts an OPT that declares one ([§ REQ-100](#req-100--adl-14-operational-template-opt-parse-and-paths)), and the validators leave it out ([§ REQ-171 *One walk*](#req-171--validation-engine)) and list it in `Coverage` ([§ REQ-171 *Coverage*](#req-171--validation-engine)).

### Placement (ADR 0010)

The constructor lives in the sibling package `openehr/templatecompile`, not in `openehr/template` beside `ParseFile`, for two reasons:

1. **Import cycle.** The compile engine imports `openehr/template`; a `Compile` inside `openehr/template` would import the engine, forming `template → templatecompile → template`.
2. **The template parser's import rule.** Compilation needs `openehr/rm/rminfo`, which [module-layout.md § REQ-013](module-layout.md#req-013--building-block-independence) keeps out of `openehr/template`'s import closure.

[ADR 0010](../adr/0010-public-compiled-template-bridge.md) records the placement, which replaced [ADR 0005](../adr/0005-compiled-template-foundation.md) §C2's `template.Compile` / `template.Compiled` proposal.

- **Probes:** none; this is an API-reachability requirement, and the builder round-trip is PROBE-023.

## REQ-106 — WebTemplate JSON export

**WebTemplate** is a consumer-facing, UI-oriented projection of an operational template: a lossy, flattened JSON view listing each node's stable `id`, cardinality, AQL path, and the leaf **inputs** a form renders. It is a **vendor de-facto** serialisation (Better → EHRbase), **not** a normative openEHR artefact — only the downstream FLAT/STRUCTURED *serialization* it enables is standardised (ITS-REST Simplified Formats). The SDK mirrors it from a single locked reference implementation ([ADR 0014](../adr/0014-webtemplate-reference-implementation-lock.md)) and keeps it stable for consumers, as § *Output shape* says.

The SDK **MUST** provide a WebTemplate JSON export that projects a compiled operational template — the public `*templatecompile.Compiled` (REQ-111) — into the **EHRbase `openEHR_SDK` v2.3** WebTemplate shape. The export reads only the compiled form, never `.oet` / `.opt` / `.t.json` authoring artefacts, and **MUST NOT** mutate it.

### Surface

```go
// Package github.com/cadasto/openehr-sdk-go/openehr/template/webtemplate

// Build projects a compiled OPT into the typed WebTemplate tree.
func Build(c *templatecompile.Compiled, opts ...Option) (*WebTemplate, error)

// Marshal is Build followed by deterministic JSON encoding.
func Marshal(c *templatecompile.Compiled, opts ...Option) ([]byte, error)

type Option func(*config) // reserved — no options in the current slice (single-language compiled input; fixed schema version)
```

`Build` returns the typed tree for callers that post-process before encoding; `Marshal` is the common path. A nil or empty compiled input, or an unresolvable default language, **MUST** return an error (never panic).

### Output shape

The exported root **MUST** carry `templateId`, `version` (the string `"2.3"`), `defaultLanguage`, `languages`, and a `tree` of nodes. Each node **MUST** carry `id`, `rmType`, `min`, `max` (with `-1` denoting unbounded), and `aqlPath`; and where the compiled template supplies them, `name` / localized names, `nodeId`, `inputs`, and `children`. JSON field names are camelCase. Encoding **MUST** be deterministic: the same compiled template produces byte-identical output across runs and SDK patch releases (fixed field order; map keys sorted).

The exported tree is **not** a 1:1 mirror of the compiled OPT; it follows the reference implementation's node model. The transform **MUST**: keep `COMPOSITION`, the ENTRY types (`OBSERVATION` / `EVALUATION` / `INSTRUCTION` / `ACTION` / `ADMIN_ENTRY`), `EVENT_CONTEXT`, and `CLUSTER` as nodes; keep the event types (`EVENT` / `POINT_EVENT` / `INTERVAL_EVENT`) as nodes **except** an abstract `EVENT` constrained to at most one occurrence, which is **lifted** — the reference emits no node for such a degenerate wrapper, while retaining its `events[…]` path segment on descendants and its synthesized `time` leaf (a repeating `EVENT`, and any concrete `POINT_EVENT` / `INTERVAL_EVENT` even at `max=1`, stays a node — both halves of the discriminator are measured across the vendored goldens); **collapse** each `ELEMENT` into a single leaf carrying the constrained value type as `rmType`, the ELEMENT's node id as `nodeId`, and the ELEMENT path extended by `/value` as `aqlPath`; **drop** the pure structural wrappers (`HISTORY` and the `ITEM_STRUCTURE` family — `ITEM_TREE` / `ITEM_LIST` / `ITEM_SINGLE` / `ITEM_TABLE`) as nodes while **folding their node predicates into the `aqlPath`** of the descendants they enclose; and emit RM-attribute values that carry data directly (e.g. `EVENT_CONTEXT.start_time` / `setting`, `EVENT.time`, the ENTRY `language` / `encoding` / `subject`, `INTERVAL_EVENT.math_function` / `width`) as leaves whose `id` is the attribute name; and give an ACTION whose template constrains no `ISM_TRANSITION` under `ism_transition` the reference's in-context `ism_transition` node, with no `nodeId`, holding the transition's `current_state` as a leaf, since the RM requires the transition and the format has no other place for it (an ACTION whose template models archetyped `ism_transition[atNNNN]` nodes gets none: those nodes carry its transition). The `aqlPath` therefore carries every archetype-id and at-code node predicate along the retained path.

### `id` generation (ADR 0014)

The node `id` is the FLAT-path segment consumers bind to, so its stability and cross-implementation fidelity are the export's load-bearing property. The `id` **MUST** mirror the locked EHRbase reference: a lower-snake sanitisation of the node's default-language display name. The exact normalisation is **derived from the vendored reference fixture**; a scheme of the SDK's own would break FLAT-path interoperability with existing tooling.

For a node that pins a **template-level name**, that name is the display name the `id` derives from — not the archetype's concept term, which is shared by every occurrence of a reused archetype and so cannot distinguish siblings; see [REQ-116](#req-116--template-level-node-naming-and-name-predicated-paths), which owns the naming rule.

A pinned name is the disambiguator wherever one exists, so no suffixing is needed for it — and none appears in any vendored reference golden. Where siblings would **still** collide — no pinned name, and one shared display name, as two ELEMENTs both sanitising to `dv_text` do in the upstream FLAT-conformance template — the export **MUST** apply the reference's ordinal fallback: the first claimant keeps the bare `id` and the second and later claimants take the next **free** ordinal spelling (`dv_text`, `dv_text2`, `dv_text3`) — "free" because a sibling may legitimately sanitise to `dv_text2` on its own, and renaming onto it would recreate the collision. The two-claimant spelling is fixed by the reference, not chosen: the upstream FLAT bodies for that template key those two nodes `…/conformance_action/dv_text` and `…/conformance_action/dv_text2`; the next-free extension beyond it is this SDK's conservative reading, pinned by table test. Emitting duplicate sibling `id`s is **never** permitted; an export that still cannot make siblings unique **MUST** fail with a typed error rather than emit an ambiguous tree.

### `inputs` (core clinical subset)

Each `ELEMENT` value constraint (via REQ-103 primitive constraints) **MUST** map to `inputs[]` for the core clinical datatypes: `DV_TEXT` (one `TEXT` input; when the value's `C_STRING` carries a `List`, the input carries it as `list`, each entry with the list string as both `value` and `label`, as the `Corona_Anamnese` golden spells it; whenever that `C_STRING` sets `CString.ListOpen` ([§ REQ-103](#req-103--primitive-constraint-introspection)), with a `List` or without one, the input carries the flag as `listOpen`, as the reference reads it; a false `listOpen` is left out, an absent optional field under § *Conformance and deviations*), `DV_CODED_TEXT` (a `code` CODED_TEXT input with `list` / `listOpen` / `terminology`), `DV_QUANTITY` (`magnitude` DECIMAL + `unit` CODED_TEXT with validation), `DV_COUNT` (INTEGER/COUNT), `DV_ORDINAL` (an ordinal `list`), `DV_DATE_TIME` / `DV_DATE` / `DV_TIME` (temporal with pattern validation), `DV_BOOLEAN` (BOOLEAN), `DV_DURATION` (pattern-ordered INTEGER component fields), and `DV_PROPORTION` (`numerator` + `denominator`, with the percent-kind–derived denominator bound). Datatypes outside this subset (e.g. `DV_MULTIMEDIA`, `DV_PARSABLE`, `DV_IDENTIFIER`, `DV_INTERVAL`) **MUST** emit the node **without** `inputs`, and no error — the omission is a documented gap, recorded so consumers can distinguish "no inputs" from "unsupported".

### Conformance and deviations

Conformance against the reference is **structural, not byte-exact**: PROBE-075 compares the SDK output to the vendored EHRbase fixture on the `id` set, `rmType`, `aqlPath`, `min`/`max`, and per-node input `suffix`/`type` extended with coded/ordinal list values, `listOpen`, `terminology`, temporal validation patterns, and numeric validation ranges. Any structural difference on that pinned surface is a failure; the following categories of divergence are **permitted deviations**, which PROBE-075 does not count as failures:

1. **Field-level presentation** — JSON field ordering, absent optional fields, and localized-string packaging (`localizedName` / localized maps emitted for the compiled template's single document language only).
2. **Reference-only node metadata** — `termBindings`, `annotations`, and the `inContext` flag on synthesized RM-attribute leaves.
3. **Input-content omissions** — `defaultValue`; DV_DURATION per-field ranges; DV_QUANTITY `precision`; per-unit and multi-unit magnitude validation; list `label` for external-terminology codes; `localizedLabels` and per-item `termBindings`.
4. **Local terminology** — `terminology` is emitted only for external bindings (e.g. `openehr`); the archetype-internal `local` value is omitted, mirroring the reference.
5. **Fixture-outlier `min` on in-context leaves** — where a vendored golden marks synthesized RM-attribute leaves `min=1` and the OPT constrains no `existence`, the export **MAY** emit `min=0`: the `GECCO_Diagnose` golden is the sole such outlier across the three vendored references (14 nodes), and the other two agree with `min=0`. Tolerated by pinned count, not waived.

The exact per-field enumeration behind these categories — the informative catalogue pinned by the parity tests — is maintained in [`openehr/template/webtemplate/deviations.md`](../../openehr/template/webtemplate/deviations.md) beside those tests. This section is the normative contract; that file elaborates it.

The media type for the format is `application/openehr.wt+json` (documented for consumers). Emitting the export over a REST endpoint / content negotiation is **out of scope** for this REQ — the package produces the bytes only. Also out of scope: the WebTemplate → OPT round-trip (the format is lossy by design); the Better camelCase `id` variant; multi-version output; and the shared simplified-template model abstraction.

Templates that **reuse one archetype under a multi-valued slot** (name-distinguished instances) **are exported**: the compiled template keeps shared-path subtrees, and node identity comes from the template-level node name, with `aqlPath` carrying the matching name predicate ([REQ-116](#req-116--template-level-node-naming-and-name-predicated-paths), [ADR 0014](../adr/0014-webtemplate-reference-implementation-lock.md)), so each reused sibling is distinct by construction instead of colliding on the shared concept term.

- **Probes:** PROBE-075, structural parity against three vendored EHRbase references: `constrain_test` and the two archetype-reuse oracles of REQ-116 ([conformance.md](conformance.md)).

## REQ-116 — Template-level node naming and name-predicated paths

An OPT node may pin its runtime `LOCATABLE.name` by constraining the `name` attribute to a fixed value — in ADL 1.4 XML, a `C_STRING` whose raw wire `list` holds **exactly one non-blank entry** (`<item xsi:type="C_STRING"><list>Husten</list></item>`), taken trimmed, and whose list is closed. Fixedness is a property of what the OPT declared, so it is judged on the wire list *before* any blank-entry normalisation: a multi-entry list is a choice even when all but one entry is blank, and a lone blank entry pins nothing. An open list fixes nothing either: a one-entry list whose `list_open` is true admits names outside it, so it pins no name. The parser reads `list_open` as [§ REQ-103](#req-103--primitive-constraint-introspection) reads it for `CString.ListOpen`, so an absent or empty element leaves the list closed. This **template-level node name** is distinct from the *archetype's* concept term: a template that fills a slot with the same archetype more than once gives each occurrence its own name, while the archetype concept is identical across all of them. It is the only thing that distinguishes those siblings, and both the reference WebTemplate `id` (REQ-106) and the AQL paths addressing them depend on it.

The SDK **MUST** parse the template-level node name, expose it on the parsed OPT node ([REQ-100](#req-100--adl-14-operational-template-opt-parse-and-paths)), carry it through the compiled tree so consumers of the public bridge can read it ([REQ-111](#req-111--public-compiled-template-bridge)), and use it as the disambiguator described below. Where a node constrains no fixed name, the SDK **MUST** treat the name as absent rather than substituting the archetype concept term.

### Name predicates in AQL paths

An AQL node predicate **MAY** carry a name alongside the archetype node id — `[openEHR-EHR-SECTION.adhoc.v1,'Symptome']` — which is how openEHR addresses one of several siblings that share an archetype node id.

Where a node pins a template-level name, the compiled AQL path **MUST** carry the name predicate on that node's segment. The trigger is the **pinned name alone**, not sibling collision: the reference emits the predicate on every named node — including a sole child, and siblings whose archetype node ids already differ — so a rule conditioned on siblings sharing a node id emits too few. Where a node pins **no** name, the SDK **MUST NOT** invent a predicate; this includes siblings that share an archetype node id and pin no distinct names, which legitimately share a path and are distinguished positionally, and whose compiled form **MUST** retain each of them rather than discarding the collision.

Path shape is consumed by the instance generator ([REQ-107](#req-107--template-driven-rm-instance-example-generator)) and FLAT/STRUCTURED path resolution ([REQ-053](wire.md#req-053)). Composition validation does not consume it: its `Issue.Path` follows [REQ-102](#req-102--composition-validation) § Issue paths, which writes a name predicate only where siblings share an archetype id.

- **Probes:** PROBE-075: the two archetype-reuse oracles, `Corona_Anamnese` and `GECCO_Diagnose`, build a Web Template whose node `id` and `aqlPath` sets match their vendored reference goldens, within the documented deviations.

## REQ-112 — Template-less Reference Model validation floor

The validators of REQ-102 are **template-driven**: every entry point takes a `*templatecompile.Compiled` as the authoritative driver. A consumer that persists RM roots binding to no operational template (FOLDER, EHR_STATUS, EHR_ACCESS, and untemplated demographic PARTY on a write path) needs another way to assert RM conformance. A strict `canjson` typed decode proves JSON↔type correctness but **not** RM invariants: mandatory-attribute omissions decode cleanly, as do `DV_INTERVAL` lower>upper, empty `CODE_PHRASE.code_string`, and `DV_QUANTITY.precision < -1`.

The SDK **MUST** expose a **template-less RM validation floor** beneath the OPT-driven path — an entry point that walks any RM root with the BMM as its sole driver and reports `Issue`s for (a) RM-mandatory attribute breaches and (b) per-RM-type invariants on the leaves it touches. The OPT-driven path stays the authoritative template-conformance layer; this floor is what runs when no template applies. The template-driven entry points include this floor ([§ REQ-102](#req-102--composition-validation) *RM floor*, [ADR 0025](../adr/0025-template-validation-includes-the-rm-floor.md)), so a template-valid result is also RM-valid; this floor's own entries run it alone, for a root no template applies to.

### Surface

```go
// Generic entry — any RM concrete in the v2 closed set.
func ValidateRM(root any, opts ...ValidateOption) Result

// Typed convenience wrappers (delegate to ValidateRM):
func ValidateRMFolder(folder *rm.Folder) Result
```

The typed wrappers carry the nil-guard contract of [§ REQ-102](#req-102--composition-validation) *Roots beyond COMPOSITION*: `nil_folder` / `nil_ehr_status` / `nil_ehr_access` / `nil_party` distinguish wrapper-side guards from the generic `nil_root` that `ValidateRM(nil)` emits. A nil guard is a global issue, so its `Path` **MUST** be empty, as on the template-driven guards; `rm_type_unknown` stays at `/`, the root it could not descend. For a non-nil root, `ValidateRM` and the typed wrappers return what a `Validator` built with no options returns from `Validate(root, nil)` ([§ REQ-171](#req-171--validation-engine) *Surface*); a nil root draws the entry's own guard. A caller who needs other limits builds a `Validator`. A Go value outside the v2 closed RM set surfaces `rm_type_unknown` at `/`; the floor cannot descend further but does not panic.

### Driver

The floor is the walk of [§ REQ-171 *One walk*](#req-171--validation-engine) with no template: every attribute is unconstrained, so the walk applies the RM rules alone. It reads values through the generated attribute access of § REQ-171 *Structural access* and takes the structural knowledge from `openehr/rm/rminfo` for the pinned Reference Model. The RM rules **MUST** read the pinned Reference Model's facts whatever `rminfo.Lookup` compiled a template: a lookup given to `templatecompile.WithRMInfo` changes which attributes the compiled template carries, not which attributes the RM makes mandatory.

- `RequiredAttributes(rmType)` drives the per-node required-set check. A single-valued attribute absent (or typed-nil) emits `required`; a multi-valued attribute absent emits `required`, present-but-empty emits `cardinality`. An item of a list that holds no RM value, a nil element or a nil pointer, **MUST** be reported as `required` at the item's own path, on the RM layer with the rule `mandatory`, not walked, and counted toward its list, so a list that holds only such items is present and not empty, and toward the visit limit as one visit, so an item past that limit is reported as `max_nodes` and ends the walk like any value (§ REQ-171 *One walk*). A JSON `null` item decodes to a nil element in a list whose items are polymorphic or held by pointer, such as CLUSTER `items`; in a list of items held by value, such as LOCATABLE `links`, it decodes to an empty item, which the walk enters like any other and reports by its missing attributes. The check leaves out an attribute that no serialization carries ([§ REQ-171](#req-171--validation-engine) *One walk*), the set `rminfo.IsNonStorableAttr` names: every BMM function, which the RM computes, and RESOURCE_DESCRIPTION `parent_resource`, the back-reference to the resource that holds the description, whose type AUTHORED_RESOURCE has no concrete class, so no value can be held there. A function of a class is one the pinned BMM declares on the class or on an ancestor that is a property neither of the class nor of any class descending from it, such as EVENT `offset`, DV_QUANTITY `is_integral` and DV_DURATION `magnitude`; DV_QUANTITY `magnitude`, which DV_QUANTITY declares as a property, is not, and nor is DV_AMOUNT `magnitude`, which its descendant DV_QUANTITY declares as one.
- `AttributeNames(rmType)` enumerates the descend candidates, the per-type attribute list `Lookup` gives.
- `AttributeRMType` / `IsContainer` carry the declared shape for each attribute. The walker recurses into every present attribute of every registered class, as § REQ-171 *Structural access* says, using the value's *runtime* RM type when known so the invariant evaluators dispatch correctly across Liskov substitution (`DV_TEXT` carrying `DV_CODED_TEXT`, a `CONTENT_ITEM` slot carrying an `OBSERVATION`, etc.). BASE `Interval` defines `lower_unbounded` / `upper_unbounded` as marking that boundary open (-infinity / +infinity), so an open side carries no bound value, and every BASE invariant that reads a bound (`Limits_consistent`, `Limits_comparable`) is guarded by the flags. The walk therefore skips an open side whose bound is empty, as [wire.md § REQ-052](wire.md#req-052) defines "empty" (`rm.IsEmptyIntervalBound`), the reading [wire.md § REQ-140](wire.md#req-140--underscore-prefixed-rm-attributes) gives a concrete-typed bound. A non-empty bound on an open side is walked like any bound.
- A value the walk reaches again inside itself, on the path it is walking, is a cycle: each place it recurs is reported as `cyclic_value` at that path and not descended into. A value it reaches again by another path, a pointer shared between two attributes, is validated at each place, so a defect in it is reported at each path ([§ REQ-171 *One walk*](#req-171--validation-engine)). A decoded document holds neither; only a value built in Go can. A value held by value whose list shares its own backing array is no cycle the walk can recognise, so the walk also stops after a number of visits per call, reporting `max_nodes` once at the path where it stops. Past a nesting depth the walk does not descend, and reports `max_depth` once per walk, at the first path where it stopped, as § REQ-171 *One walk* requires. A decoded document can reach either limit: a large one the visit limit, a deeply nested one the depth limit. Both limits are the `Limits` of [§ REQ-171 *Surface*](#req-171--validation-engine), with its defaults, and each path where one stopped the walk is listed in `Coverage.Stopped`.

### Per-RM-type invariant catalogue

The floor **MUST** report every invariant the inventory of [§ REQ-171 *Where the RM rules come from*](#req-171--validation-engine) classifies as evaluated, on every node of a class subject to it that the walk visits, reading it as the entries below say, with the code `rm_invariant` unless an entry names a code of its own. Beside the structural required-set walk above, the entries cover the node-level and leaf invariants that the canjson lenient decode accepts but the RM forbids:

- **CODE_PHRASE** — `code_string` non-empty (`Code_string_valid`). The required-set walk decides this invariant, as § REQ-171 *Where the RM rules come from* says of one another check already decides: an empty `code_string` is an absent RM-mandatory attribute, reported once, as `required` at `…/code_string` with the rule `mandatory`, and not again at the CODE_PHRASE ([§ REQ-171](#req-171--validation-engine) *One finding per defect*). A CODE_PHRASE at a mandatory attribute whose terminology is empty too is itself absent (§ REQ-171 *Structural access*), reported as `required` at its own path and not entered. The one exception is a DV_SCALE's `symbol`: the RM lets a scale value that has no code carry a `symbol` with its `terminology_id` and a blank `code_string`, so the floor **MUST NOT** report a blank `code_string` on a DV_SCALE `symbol.defining_code`, in either form. A DV_ORDINAL's `symbol` has no such allowance.
- **DV_QUANTITY** — `precision`, when set, ≥ -1: per the RM, -1 means no limit (any number of decimal places), so only `precision < -1` is out of range.
- **DV_DATE_TIME / DV_DATE / DV_TIME / DV_DURATION** — `Value_valid`: `value` is a valid ISO 8601 value of its type as the [REQ-123](rm-functions.md#req-123--temporal-data-value-helpers) parse reads it, that is the type's BASE predicate (`valid_iso8601_date_time`, `valid_iso8601_date`, `valid_iso8601_time`, `valid_iso8601_duration`) with the deviations REQ-123 names. The floor reports a non-empty `value` that parse refuses, a placeholder such as `example` included, as `rm_invariant` on the node. An empty `value`, which is also what a JSON `null` decodes to, is an absent RM-mandatory attribute that the required-set walk reports once, as `required` at `…/value`, and this entry does not report it ([§ REQ-171](#req-171--validation-engine) *One finding per defect*).
- **ELEMENT** — `Inv_null_flavour_indicated` (`is_null() xor null_flavour = Void`, where `is_null()` means there is no `value`): exactly one of `value` and `null_flavour` is present. The floor reports an ELEMENT that carries both, and one that carries neither, as `rm_invariant` on the ELEMENT.
- **DV_PROPORTION** — two precision arms and the proportion-kind rules. `precision`, when set, ≥ -1 under the same RM rule as DV_QUANTITY (-1 means no limit); and the RM invariant `Precision_validity` (`precision = 0 implies is_integral`), read through `Is_integral_validity` as whole-number operands, so the floor reports a `precision` of 0 over a non-integral `numerator` or `denominator`. It also reports the proportion-kind rules: a `type` that is not a `PROPORTION_KIND` value, 0 to 4 (`Type_validity`); a `denominator` other than 1 on a unitary proportion (`Unitary_validity`) and other than 100 on a percent (`Percent_validity`); a `numerator` or `denominator` that is not a whole number on a fraction or an integer fraction (`Fraction_validity`, `is_integral` read as for `Precision_validity`); and a `denominator` of 0 (`Valid_denominator`). The *DV_INTERVAL* entry below leaves a pair of bounds unordered when either has a zero denominator.
- **DV_INTERVAL** — `Limits_consistent`: when neither side is unbounded, `lower.is_strictly_comparable_to(upper) and lower <= upper`. The floor reads two bounds as strictly comparable as the RM defines `is_strictly_comparable_to` for their type: two DV_COUNT; two DV_QUANTITY with equal `units`; two DV_PROPORTION of one `type`; two DV_DATE, two DV_TIME, two DV_DATE_TIME or two DV_DURATION. Each of these definitions compares a value with one of its own class, so the floor reads bounds of two classes as not strictly comparable, a DV_COUNT beside another DV_ORDERED included, although DV_COUNT's definition reads `Return True` for any. When neither side is unbounded and each side holds a bound, the floor **MUST** report a pair it reads as not strictly comparable (bounds of two classes, two DV_QUANTITY in different `units`, or two DV_PROPORTION of different `type`), and a strictly comparable pair whose `lower` is above its `upper` by the order below, each as `rm_invariant` at the interval with the rule `DV_INTERVAL.Limits_consistent`. The RM leaves DV_ORDINAL's and DV_SCALE's undefined; the floor reads two of them as comparable when their symbols are coded in one named terminology, and **MUST NOT** report two whose symbols are coded in different terminologies or in none, which it does not order either. The order is the RM's `less_than` for the type: `magnitude` for the quantified types, `value` for DV_ORDINAL and DV_SCALE, and for a temporal value the magnitude the REQ-123 parse gives, except that two DV_TIME or DV_DATE_TIME values in different time zones are ordered as instants, each by its magnitude less its zone's offset from UTC, partial values and leap seconds included, and a zoned value is not ordered against one without a zone. Equal `units` is only part of DV_QUANTITY's `is_strictly_comparable_to`, which also needs a matching `units_system` where one is set. The floor does not compare `units_system`, so it orders a same-units pair whatever its `units_system`, although the RM makes two different systems not strictly comparable. Of the pairs it reads as strictly comparable, it orders none that holds a DV_PROPORTION with a zero denominator or a temporal value the REQ-123 parse refuses, nor a zoned DV_TIME or DV_DATE_TIME against one without a zone, and reports none of them here (see *What the floor does not evaluate* below).
- **Interval flags** — BASE `Lower_included_valid` and `Upper_included_valid` (`lower_unbounded implies not lower_included`, and the same for `upper`). On every interval the walk reaches, a DV_INTERVAL value, a typed `normal_range` and a REFERENCE_RANGE `range` among them, the floor **MUST** report a side marked both unbounded and included as `lower_included_valid` or `upper_included_valid` at the interval's path. Canonical JSON, canonical XML, FLAT and STRUCTURED decode such a side as written ([wire.md § REQ-169](wire.md#req-169--interval-boundary-flag-defaults)), and an RM value built in Go can carry it too, so this entry is where it is reported.
- **OBJECT_REF / PARTY_REF / ACCESS_GROUP_REF / LOCATABLE_REF** — `id` present, and `type` and `namespace` non-empty, each reported as `rm_invariant` at its own path (`…/id`, `…/type`, `…/namespace`). The floor walks into a reference like any node, so the OBJECT_ID a present `id` holds is checked in turn, but its required-set check leaves a reference's `id`, `namespace` and `type` to this evaluator, so a missing part is reported once.
- **PARTY_PROXY family (PARTY_SELF, PARTY_IDENTIFIED, PARTY_RELATED)** — wherever a party proxy sits (a COMPOSITION's `composer`, an EVENT_CONTEXT's `health_care_facility`, an ENTRY's `subject` and `provider`, a PARTICIPATION's `performer`, an EHR_STATUS's `subject`, or the root), the floor walks it, and a present `external_ref` whatever its parts hold, so the entry above checks that PARTY_REF at `…/external_ref/id`, `…/external_ref/type` and `…/external_ref/namespace`. On a PARTY_IDENTIFIED, and on a PARTY_RELATED, which inherits them, the floor reports as `rm_invariant`: `Basic_validity` (none of `name`, `identifiers` and `external_ref` is present) at the node; `Name_valid` (a present `name` that is empty) at `…/name`; and `Identifiers_valid` (a present `identifiers` that is empty) at `…/identifiers`. Presence follows the decoded value, as for DV_TEXT `mappings`: an absent key and JSON `null` both read as absent, so only a decoded `"name":""` or `"identifiers":[]` is present and empty. PARTY_RELATED's RM-mandatory `relationship` falls under the required-set walk, and its `Relationship_valid` under the *Coded invariants* entry below. PARTY_SELF has no invariant of its own; an EHR_STATUS's value-typed `subject` follows § *Value-typed mandatory presence*.
- **PARTICIPATION** — wherever a participation sits (an EVENT_CONTEXT's `participations`, an ENTRY's `other_participations`, or the root), its RM-mandatory `function` and `performer` fall under the required-set walk, which reports an absent one as `required` at `…/function` or `…/performer`, and a `function` whose `value` is empty counts as absent, as a LOCATABLE's `name` does ([§ REQ-171](#req-171--validation-engine) *Structural access*). The `performer` proxy, `mode` and `time` are walked like any other present attribute. `Function_valid` and `Mode_valid`, which tie a coded `function` and the `mode` to openEHR terminology groups, fall under the *Coded invariants* entry below.
- **DV_TEXT / DV_CODED_TEXT** — the floor **MUST** report a present-but-empty `mappings` (`Mappings_valid`) as `mappings_valid`; DV_CODED_TEXT inherits `mappings` from DV_TEXT via embedding, so both dispatch through the same evaluator. The floor cannot distinguish an absent `mappings` key from an explicit JSON `null` — canjson decodes both to a nil slice — so only a decoded literal `"mappings":[]` (a non-nil empty slice) is flagged; null and absent are indistinguishable and both valid. `mappings` is a walked container: each element is a TERM_MAPPING node of its own, checked by the entry below wherever it sits.
- **TERM_MAPPING** — the floor **MUST** report a `match` outside `{'>', '=', '<', '?'}` (`term_mapping_match`) as an invariant violation on the mapping node itself, so the check fires for a mapping under a DV_TEXT / DV_CODED_TEXT `mappings` container, for one nested under a mapping's own `purpose`, and for a TERM_MAPPING handed to `ValidateRM` as the root. The RM-mandatory `match` and `target` (CODE_PHRASE) fall under the required-set walk, and `target`'s and `purpose`'s own invariants apply inside each mapping; an empty `match` therefore reports both `required` and `term_mapping_match` at the same path.
- **Non-empty lists** — `COMPOSITION.Content_valid`, `EVENT_CONTEXT.Participations_validity`, `INSTRUCTION.Activities_valid`, `SECTION.Items_valid` and `ATTESTATION.Items_valid` each read `x /= Void implies not x.is_empty` for the list `x` they name: `content`, `participations`, `activities`, and `items` on the last two. The floor reports such a list that is present and holds no item, presence as [§ REQ-171 *Structural access*](#req-171--validation-engine) reads it, as `rm_invariant` at the list's own path (`…/context/participations`), with the invariant as its `Rule`, as it reports a present-but-empty `mappings`, and not an absent one. `HISTORY.Events_valid` reads `(events /= Void and then not events.is_empty) or summary /= Void`: the floor reports a HISTORY whose `events` is absent or holds no item and whose `summary` is absent as `rm_invariant` at the HISTORY's own path, as it reports the other rules of this catalogue over more than one attribute, `Basic_validity` and `Inv_null_flavour_indicated`, at their node, and not one that carries an event or a summary. Under a template, an existence lower bound of 1 or more on one of these lists asks for a member ([§ REQ-102](#req-102--composition-validation) *An existence lower bound alone asks for no member*), and the template's finding at a list's path or below it, or, for a HISTORY's `events`, at or below its `summary`, stands for the rule that reads it there ([§ REQ-171](#req-171--validation-engine) *One finding per defect*).
- **LOCATABLE links and EVENT_CONTEXT location** — `LOCATABLE.Links_valid` and `EVENT_CONTEXT.location_valid` each read `x /= Void implies not x.is_empty` for the attribute `x` they name, `links` and `location`. The floor reports a `links` that is present and holds no item, on every LOCATABLE it visits, and a `location` that is present and empty, as `rm_invariant` at the attribute's own path (`…/links`, `…/context/location`), with the invariant as its `Rule`, and not an absent one; presence is as [§ REQ-171 *Structural access*](#req-171--validation-engine) reads it, so an absent key and a JSON `null` are both absent, and only a decoded `"links":[]` or `"location":""` is present and empty. `links` is not one of the lists the *Non-empty lists* entry evaluates, so under a template an existence lower bound on it asks for no member ([§ REQ-102](#req-102--composition-validation) *An existence lower bound alone asks for no member*), and the finding is the RM rule's own, as it is with no template. The diagnostic names the class and the attribute, never a value ([§ REQ-168](#req-168--value-free-validation-diagnostics)).
- **DV_EHR_URI** — `Scheme_valid` (`scheme.is_equal (Ehr_scheme)`): the scheme of the `value` is `ehr`. The floor reports a DV_EHR_URI whose `value` does not have the scheme `ehr`, wherever the walk visits one (the `target` of a LINK, an ELEMENT's `value`, an ATTESTATION's `items`), as `rm_invariant` at the DV_EHR_URI itself, as it reports the ISO 8601 `Value_valid` rule at its node. The scheme is the text before the first `:` when RFC 3986 section 3.1 admits it as one, `ALPHA *( ALPHA / DIGIT / "+" / "-" / "." )`, and the comparison ignores letter case, so `EHR://x` keeps the rule and `http://x` breaks it. A `value` with no scheme, such as `example.org/x`, has none equal to `ehr` and breaks it too; an empty one is the required-set walk's (`DV_URI.Value_valid`). The diagnostic names the class and the attribute, never a value, the scheme being part of it, and the issue's `Value` is empty ([§ REQ-168](#req-168--value-free-validation-diagnostics)).
- **Archetype roots (`Is_archetype_root`)** — the class-level `Is_archetype_root` invariant fixes `is_archetype_root` true on every class whose BMM declares it, and together with `LOCATABLE.Archetyped_valid` (`is_archetype_root xor archetype_details = Void`) that makes `archetype_details` mandatory on those nodes even though LOCATABLE declares it 0..1; `Archetyped_valid` alone does not, since a non-root node with no details satisfies it. The declaring classes are COMPOSITION, EHR_ACCESS, EHR_STATUS, PARTY (with its concrete descendants PERSON, ORGANISATION, GROUP, AGENT, ROLE) and ENTRY (with its concrete descendants ADMIN_ENTRY, OBSERVATION, EVALUATION, INSTRUCTION, ACTION). The floor **MUST** report an absent or `null` `archetype_details` as `is_archetype_root` at `…/archetype_details` on a node of such a class, and on no other: classes that declare no `Is_archetype_root` (FOLDER, PARTY_RELATIONSHIP, EXTRACT, GENERIC_ENTRY, the demographic parts PARTY_IDENTITY, CONTACT, ADDRESS and CAPABILITY, and the data-structure classes) leave the attribute optional. This positive set is closed: the floor takes it from the `Is_archetype_root` entries of the inventory of [§ REQ-171 *Where the RM rules come from*](#req-171--validation-engine), and the [REQ-107](#req-107--template-driven-rm-instance-example-generator) generator from a closed list held equal to it and to the vendored BMM's `Is_archetype_root` declarations, so a BMM bump that adds a root class fails the build ([ADR 0001](../adr/0001-bmm-version-bump-runbook.md)). This is a class invariant of the object, not a storage rule, so it holds for a detached object exactly as for a persisted one. Rules that need stored history (`VERSIONED_COMPOSITION.Archetype_node_id_valid`) and requiring `ARCHETYPED.template_id` (0..1 in the RM) stay out of scope.
- **ARCHETYPED** — wherever an `archetype_details` node is present, on any LOCATABLE, its two RM-mandatory attributes `archetype_id` (`ARCHETYPE_ID`) and `rm_version` (`String`) are value-typed, so the value-based walk cannot tell absent from `null` from empty (they decode to the same zero value). On a value validated with no report of missing members, the value-based entries (`ValidateRM` and the typed sugars) **MUST** report an empty `archetype_id.value` as `required` at `…/archetype_details/archetype_id/value` (SDK policy: `OBJECT_ID.value` is RM-mandatory with no non-empty invariant, the `clinical_notes.v0` precedent) and an empty `rm_version` as `rm_version_valid` (`Rm_version_valid: not rm_version.is_empty`) at `…/archetype_details/rm_version`; absent and `null` decode to the same zero values and are reported the same way, and an ARCHETYPED handed to `ValidateRM` as the root is checked the same way, with the findings at `/archetype_id/value` and `/rm_version`. With a decode's report of missing members, an absent or `null` member is `required` at the member itself, `…/archetype_details/archetype_id` or `…/archetype_details/rm_version`, with nothing below it (§ *Value-typed mandatory presence* below). Validating the `ARCHETYPE_ID` grammar is out of scope for this catalogue.
- **Coded invariants** — the floor evaluates each RM invariant in the table below, which ties a coded attribute to a group or a code set of the openEHR terminology, on every node of the listed classes it visits, taking the group, the code set and the membership verdict from the [REQ-034](rm-modeling.md#openehr-terminology-vocabulary-req-034) accessor. An optional attribute is checked only when present, ELEMENT's `null_flavour` only when the ELEMENT has no `value` (the RM states `Inv_null_flavour_valid` as `is_null implies …`), and PARTICIPATION's `function` only when it is a DV_CODED_TEXT (`Function_valid`'s own guard).

  | COMPOSITION | `Language_valid` | `language` | code set *languages* |
  | COMPOSITION | `Territory_valid` | `territory` | code set *countries* |
  | EVENT_CONTEXT | `Setting_valid` | `setting` | group *setting* |

  | INTERVAL_EVENT | `Math_function_validity` | `math_function` | group *event math function* |
  | ISM_TRANSITION | `Current_state_valid` | `current_state` | group *instruction states* |

  A group invariant asks the openEHR terminology itself (`terminology (Terminology_id_openehr).has_code_for_group_id (…)`), so it holds only when the CODE_PHRASE's `terminology_id` is `openehr` and its `code_string` is a member of the group: a setting coded in `local`, or in any terminology other than `openehr`, breaks `Setting_valid` whatever its code string. A code-set invariant holds when the `code_string` is a member of the code set under the accessor's membership rule, which ignores letter case for the ISO and IANA sets; the `terminology_id` is not compared, because the RM's `CODE_SET_ACCESS.has_code` takes the bare code. The CODE_PHRASE an invariant reads is the attribute itself for a CODE_PHRASE attribute, and the attribute's `defining_code` for a DV_CODED_TEXT one. The floor **MUST** report each breach as `code_not_in_value_set` at that CODE_PHRASE's path (`…/language`, `…/context/setting/defining_code`). An empty `code_string` is no member, so on a value validated with no report of missing members `code_not_in_value_set` is drawn by a mandatory value-typed attribute that decoded empty, such as a COMPOSITION `language` the source left out or a PARTY_RELATED `relationship`, beside whatever the walk already reports for it (`required` for an omitted COMPOSITION `language`, `required` at its `code_string` for one that carries a terminology id and a blank code); with the report, an omitted `language` is `required` at `…/language` alone (§ *Value-typed mandatory presence*). The RM's other coded invariants are not in this entry (*What the floor does not evaluate* below).

**Known gap — a bound beside its own open flag.** A bound present on a side whose `*_unbounded` flag is set contradicts BASE `Interval`'s open-boundary meaning. The floor walks it as a bound but does not report the contradiction.

**What the floor does not evaluate.** Every invariant of the pinned RM and BASE BMMs that the floor does not evaluate is an entry of the inventory of [§ REQ-171 *Where the RM rules come from*](#req-171--validation-engine), with its reason: among them BASE `Interval.Limits_comparable`, which `DV_INTERVAL.Limits_consistent` restates and the floor evaluates on a DV_INTERVAL as the *DV_INTERVAL* entry says, but on no BASE `Proper_interval` or `Point_interval`, whose bounds the SDK leaves untyped; and the coded invariants of the change-control and resource-description classes, which the *Coded invariants* table leaves out. A result lists those of the classes it visited in `Coverage.Unevaluated`. The inventory classifies `DV_INTERVAL.Limits_consistent` as evaluated, but the floor leaves parts of it unchecked: the `units_system` of two DV_QUANTITY; the comparability of two DV_ORDINAL or DV_SCALE, which the RM leaves undefined; and the order of a pair it reads as strictly comparable but cannot order, one that holds a DV_PROPORTION with a zero denominator or a temporal value the REQ-123 parse refuses, or a zoned DV_TIME or DV_DATE_TIME against one without a zone.

Most invariants emit `Issue.Code = "rm_invariant"`; the term-mapping checks are the exception (`mappings_valid` on DV_TEXT / DV_CODED_TEXT, `term_mapping_match` on TERM_MAPPING), as are the interval-flag checks (`lower_included_valid`, `upper_included_valid`), the archetype-root check (`is_archetype_root`), the ARCHETYPED check (`rm_version_valid`) and the coded invariants (`code_not_in_value_set`), carrying their own stable codes so consumers can dispatch on the specific violation without parsing `Detail`.

### Trust model

The floor is the structural RM-only layer. It does **not** evaluate:

- archetype-level or template-level constraints (that is REQ-102);
- terminology bindings an OPT declares ([§ REQ-111](#req-111--public-compiled-template-bridge) *Term definitions and bindings*), and codes from terminologies outside the pinned openEHR terminology (SNOMED CT, LOINC, …), which need a terminology service; the closed groups and code sets of the *Coded invariants* entry are the only codes it checks;
- semantic validity beyond the BMM and the explicit invariant catalogue.

These exclusions are by design: a CDR may layer template-driven validation on top of the floor, or run the floor alone for resources where no template applies.

### Value-typed mandatory presence

The required-set walk reads presence from the decoded Go value, as [§ REQ-171 *Structural access*](#structural-access) says: an attribute held by value is absent when it holds its type's zero value, so an omitted DV_ORDINAL or DV_SCALE `symbol`, or an omitted REFERENCE_RANGE `range`, is reported as `required`. What the walk cannot detect is an omitted **value-typed** mandatory attribute whose zero value is itself a valid value: a number or a boolean, such as `DV_QUANTITY.magnitude`, `DV_COUNT.magnitude`, `DV_BOOLEAN.value` or `DV_PROPORTION.denominator`, and a value struct, such as `EHR_STATUS.subject` (typed `rm.PartySelf`, whose only field is optional, so an omitted subject and a valid bare `{"_type":"PARTY_SELF"}` decode to the identical zero value) and an ARCHETYPED's `archetype_id` and `rm_version`. Interface-, pointer- and slice-typed mandatories are unaffected, nil being a reliable absence signal, as are the value-level invariants, which inspect fields rather than presence.

The floor closes this by reading what the decode found missing, which the codecs report as [wire.md § REQ-175](wire.md#req-175--missing-members-on-decode) defines: every RM-mandatory member a document leaves out or sends as `null` (canonical JSON) or as `xsi:nil` or an empty primitive element (canonical XML), each identified by its JSON Pointer in the canonical-JSON form of the instance, in both formats ([ADR 0033](../adr/0033-missing-members-reported-by-decoders.md)).

- Every value-based entry, `ValidateRM`, `Validate` and `Validator.Validate`, **MUST** accept such a report through `WithMissing`, a trailing option, so a caller that decodes with a codec's report option hands the pointers on and validates once; the typed sugars take none and are for a value with no report. A nil option, an empty list and a repeated option are read as the union of what was given.
- `ValidateJSON` and `ValidateXML`, and their `Validator` methods, **MUST** decode `data` into `root`, a non-nil pointer to one registered RM value, read the document's missing members, and validate `root` with that report in one call, returning what `Validator.Validate(root, c, WithMissing(…))` returns: with a nil `c` the RM rules alone, with a compiled template the template rules too ([§ REQ-102](#req-102--composition-validation)), under the entry's own limits. The decode is the codec's default decode: unmatched content is ignored ([wire.md § REQ-170](wire.md#req-170--unmatched-content-on-decode)), and `root` holds the decoded value afterwards, so a caller that wants the value and the result decodes once.
- A reported member **MUST** be read as absent at the node its pointer names, whatever the Go value holds there, inside the one walk ([§ REQ-171 *One walk*](#one-walk)): the walk reports it as it reports any absent attribute, the template's `required` where the template requires it and the RM's `required` with the rule `mandatory` otherwise ([§ REQ-171 *Finding identity*](#finding-identity)), does not enter it and runs no other rule at its path, so its path carries that one finding. An absent `rm_version` is therefore `required` at `…/archetype_details/rm_version`, not `rm_version_valid`, and an absent `archetype_id` is `required` at `…/archetype_details/archetype_id` alone, with nothing at `…/archetype_id/value`. Presence is read at every level, a nested ARCHETYPED and a data value deep in a COMPOSITION included; the root is no exception. Two readings of the Go value remain. A rule of the node that holds the member reads the node's value, where a decode left the member's zero value, and reports at the node's own path as it would without the report: a DV_PROPORTION with no `denominator` draws `required` at `…/denominator` and `Valid_denominator` at the DV_PROPORTION. And the three parts of an OBJECT_REF, which the floor's OBJECT_REF rule checks in place of the required-set check ([§ *Per-RM-type invariant catalogue*](#per-rm-type-invariant-catalogue)), are reported by that rule from the Go value, which a decode leaves empty for a part it reports.
- A pointer that names no attribute the walk visits draws no finding: a node the template refused, a node past a limit, which `Coverage.Stopped` lists, a node the walk does not enter. The walk reports what it visits. A pointer into a value held by a `Hash` is matched by the entry's key, and one into a list by the item's position.
- A value built in Go has no report, so a by-value mandatory member left unset there reads as present, as today; only a decode can say what a document said. The typed wrappers and `ValidateRM` without the option keep that blind spot, which their godoc names.
- On `ValidateJSON` and `ValidateXML`, input that does not decode into `root`, malformed input, a canonical-JSON document whose root is not an object, a canonical-XML document with content before or after its root element or a root that fails its decode, **MUST** surface a single `invalid_shape` at `/` and a not-OK `Result`, with the decode error, whose text may quote the input, in the issue's `Value` and not in its `Detail` ([§ REQ-168](#req-168--value-free-validation-diagnostics)); JSON `null` raises no decode error, so its issue's `Value` is empty. A nil `root`, or one that is no registered RM value, draws the entry's `nil_root` or `rm_type_unknown` guard, as `ValidateRM` does.
- `ValidateRMEHRStatusBytes(data)` is kept as `ValidateJSON(data, new(rm.EHRStatus), nil)` and is deprecated: an omitted or `null` `subject` is `required` at `/subject`, a supplied subject, even the bare form, **MUST NOT** draw a `required`, and its former root-only scope is gone, since presence is now read at every level.

- **Probes:** PROBE-077 (every invariant the inventory classifies as evaluated, on every registered class subject to it, with a breaking and a conforming value); PROBE-081 (the EHR_STATUS root: `subject` and the ARCHETYPED keys); PROBE-110 (missing members at every level, in both canonical formats, and the validators' one answer).

## REQ-168 — Value-free validation diagnostics

A `constraints.Violation`, and an `Issue` from the instance validators, **MUST NOT** repeat the value under validation outside their value-bearing field (§ Field classes). Both travel to places a caller does not choose for clinical data: an HTTP error body, a log line, a monitoring event. The values they describe are clinical data (a date of birth, a measured magnitude, a free-text name), so a message that quotes one carries it to each of those places, in callers that never meant to send it. [§ REQ-113 § Value-free structured drop records](#value-free-structured-drop-records) holds the AQL diagnostics to this line, and [REQ-093](transport.md#req-093--openehr-error-envelope-mapping) holds the transport errors to it. This requirement applies it to [§ REQ-103](#req-103--primitive-constraint-introspection)'s `Violation` and to the `Issue` that [§ REQ-102](#req-102--composition-validation) and [§ REQ-112](#req-112--template-less-reference-model-validation-floor) return; the `Issue` that `ValidateAQL` returns keeps [§ REQ-109](#req-109--aql-static-lint)'s classification. The value stays reachable through `Value.Reveal()` ([§ The redacting carrier](#the-redacting-carrier)).

### Submitted values and structure

A **submitted value** is data taken from the input under validation:

- for `PrimitiveConstraint.Validate`, the argument and each of its fields: a `QuantityValue`'s magnitude, units and precision, a `CodedTermRef`'s terminology and code, an `OrdinalSymbol`'s value and symbol;
- for the instance validators, the content of a data value or a primitive attribute in the instance (a `value`, `magnitude`, `units`, `precision`, `numerator` or `denominator`, an interval bound, a `CODE_PHRASE`'s terminology and code, a `TERM_MAPPING`'s `match`), and the text of an error raised while decoding the instance.

**Structure** is not a submitted value: RM type and attribute names, archetype and node ids, a path, a child count, the Go type name of a wrong-typed argument, and the constraint itself (its allowed list, range, pattern, units and terminology), which comes from the template rather than the instance. Naming the clause a value failed lets a reader infer something about the value: that it lies outside a range, which units entry it matched, which of the two booleans it was. That inference is what a diagnostic is for, and it is not an echo. Copying the value, or any part of it, is.

### Field classes

A field's class is fixed by its type and, for an `Issue`, by the entry point that returned it, which a consumer knows because it made the call. It never depends on an issue's content. The godoc of each type states its fields' classes, so a consumer reads them on the type it holds ([§ REQ-113](#value-free-structured-drop-records)):

| Type and entry point | Value-free | Value-bearing |
|---|---|---|
| `constraints.Violation` | `Code`, `Detail` | `Value` |
| `validation.Issue` from the REQ-102 entry points and the REQ-112 floor entries | `Path`, `Code`, `Layer`, `Rule`, `Detail`, `Severity` | `Value` |
| `validation.Issue` from `ValidateAQL` and `ValidateAQLWithTypeRelation` | `Code`, `Layer`, `Rule`, `Severity`, which carry no source text ([§ REQ-109 § Value-free lint diagnostics](#value-free-lint-diagnostics)) | `Detail` and `Path`, as § REQ-109 classifies them |

A value-free field does not fall back to quoting the value where a value-free wording is hard to find ([§ REQ-113](#value-free-structured-drop-records)'s no-fallback clause): what cannot be said without the value goes in `Value`, or nowhere.

### The redacting carrier

`Value` **MUST** be of the type `constraints.Redacted`, which holds one submitted value and never prints it:

- `constraints.Redact(v)` **MUST** return a `Redacted` holding `v`. The zero `Redacted` holds no value.
- `Reveal()` **MUST** return the held value with its type, or nil when none is held, and be the only method of `Redacted` that returns the value. A value that `==` can compare comes back equal under `==` to the one held, with two exceptions: a floating-point zero may come back with either sign, and a NaN, alone or inside an array or a struct, comes back as a NaN in the same place, though `==` never finds it equal, so a value that holds one never compares equal to the one given. Any other value comes back as the same value.
- Printing, encoding and logging a `Violation`, `Issue`, `Result` or `Redacted` **MUST** behave as follows, so that none of them writes the value:
  - every `fmt` verb other than `%T` and `%p`, `%v`, `%+v` and `%#v` included, prints `[redacted]` for a `Redacted` that holds a value and nothing for one that does not, and `String()` returns the same text, so printing a whole `Violation`, `Issue` or `Result` prints no submitted value;
  - under `%T` and `%p`, and through an unexported field of the caller's own struct, the output contains no value either;
  - `encoding/json`, v1 and v2 alike, leaves the `Value` field of `Violation` and of `Issue` out, so encoding a `Result` writes no `Value` member, and encodes a `Redacted` on its own as JSON `null`;
  - `encoding/gob` encodes a `Violation`, `Issue` or `Result` without an error, a `Redacted` as empty, which decodes as the zero `Redacted`;
  - the text and JSON handlers of `log/slog` write no value.
- `fmt` itself answers `%T` with the type name, and prints a `Redacted` without calling its methods under `%p` and through an unexported field of the caller's own struct. Those paths show memory addresses instead, and equal held values show the same address, so two such lines reveal that their values are equal.
- Tools other than `fmt` that read unexported fields by reflection, such as a diff reporter or a debugger, are outside these rules.
- `Violation` and `Issue` values **MUST** be comparable with `==` without a panic, whatever a `Redacted` holds, and `Redacted` **MUST** have an `Equal(Redacted) bool` method that agrees with `==`, so a comparison library that refuses unexported fields but honours such a method can still compare a `Violation`, `Issue` or `Result`. Two diagnostics that hold equal values **MUST** compare equal under `==`: the SDK puts only comparable values in a `Redacted`, and holds a value that `==` cannot compare, such as a slice, by reference, so only copies of one `Redacted` compare equal.

### What `Value` holds

On a `Violation`, `Value` **MUST** hold the part of the input that the failing clause tested, as this table says, and be empty on `CodeWrongType`, where no clause tested the input and `Detail` names its Go type, and on a violation the constraint causes itself, such as an unparseable `CString` pattern:

| Validator and clause | `Value` |
|---|---|
| `CBoolean`, `CInteger`, `CReal`, `CString`, `CDate`, `CTime`, `CDateTime`, `CDuration`, `CDvOrdinal` | the argument as passed |
| `CodePhrase`, terminology mismatch | the input's terminology id |
| `CodePhrase`, code not in the list | the input's code string |
| `DvQuantity`, magnitude range | the input's `Magnitude` |
| `DvQuantity`, precision range | the input's `Precision` |
| `DvQuantity`, units not enumerated | the input's `Units` |

On an `Issue` from the instance validators, `Value` **MUST** hold what this table names, and be empty on every other `Issue` (an absence, a count, a type or identity mismatch, a guard) and on every `Issue` from `ValidateAQL` or `ValidateAQLWithTypeRelation`:

| Issue | `Value` |
|---|---|
| `primitive_*` | the `Value` of the violation it reports |
| `rm_invariant` on a `DV_QUANTITY` or `DV_PROPORTION` `precision` below -1 | the precision |
| `rm_invariant` on a `DV_PROPORTION` with precision 0 and a fractional operand | the numerator and the denominator, as a `[2]float64` |
| `rm_invariant` on a `DV_PROPORTION` `type` that is not a proportion kind (`Type_validity`) | the type |
| `rm_invariant` on a `DV_PROPORTION` `denominator` its kind rejects, or of 0 (`Unitary_validity`, `Percent_validity`, `Valid_denominator`) | the denominator |
| `rm_invariant` on a fraction or integer-fraction `DV_PROPORTION` with a fractional operand (`Fraction_validity`) | the numerator and the denominator, as a `[2]float64` |
| `rm_invariant` on a `DV_INTERVAL` whose lower bound is above its upper bound | the two compared magnitudes, lower first, as a `[2]float64` |
| `rm_invariant` on a temporal `value` (`Value_valid`) | the `value` string |
| `term_mapping_match` | the `match` |
| `invalid_shape` from a failed decode | the decode error, which carries the literal through unwrapping where one of its causes records it, as a `*json.SemanticError` or a `*strconv.NumError` does ([wire.md § REQ-052](wire.md#req-052)) |

### Compatibility

- This requirement says which fields may carry a submitted value and what `Value` holds; it defines no code, path, severity or finding. `Code`, and on an instance validator's `Issue` also `Path` and `Severity`, are value-free (§ Field classes). Their vocabularies, `Result.OK` and the set of findings are the ones [§ REQ-102](#req-102--composition-validation), [§ REQ-103](#req-103--primitive-constraint-introspection) and [§ REQ-112](#req-112--template-less-reference-model-validation-floor) define. A caller dispatches on `Code`, not on `Detail` text ([§ REQ-103 § Violation taxonomy](#violation-taxonomy), [§ REQ-102 § Issue codes](#issue-codes)).
- The issues of `ValidateAQL` follow [§ REQ-109 § Value-free lint diagnostics](#value-free-lint-diagnostics).

**Acceptance.** For each row of § What `Value` holds, a test plants a marker value that no constraint text contains and checks that `Value.Reveal()` returns what the row names and that no value-free field carries the marker. A `Violation`, an `Issue` and a `Result` holding a marker are rendered with `%v`, `%+v`, `%#v`, `%s`, `%d` and `%p`, directly and through an unexported field, encoded with `encoding/json` v1 and v2 and `encoding/gob`, and logged through the text and JSON handlers of `log/slog`, and the marker appears in none of that output. The empty-`Value` cases (`CodeWrongType`, an unparseable pattern, an absence, an issue from `ValidateAQL`) each have a named test, and `ValidateComposition` over a composition with a marker at a constrained primitive leaf reports the marker in that issue's `Value` and in no other field.

### Out of scope

- Errors the codecs return as `error` values; [wire.md](wire.md) governs their text.
- `lint.Issue` and the AQL drop records, which [§ REQ-109](#req-109--aql-static-lint) and [§ REQ-113](#req-113--execution-oriented-parsed-aql-ast) govern.
- Redaction policy for structure. Whether an archetype id or a path is sensitive in a deployment is the consumer's decision.

## REQ-171 — Validation engine

Template-driven validation ([§ REQ-102](#req-102--composition-validation)) and the Reference Model floor ([§ REQ-112](#req-112--template-less-reference-model-validation-floor)) run as one engine: one validator value, one walk, the template's admission decided before any RM rule at every node, one finding per defect that names its layer and its rule, and a result that says what it did not check ([ADR 0027](../adr/0027-template-admission-before-rm-rules.md), [ADR 0028](../adr/0028-generated-rm-attribute-access.md)).

[§ REQ-102 *RM floor*](#rm-floor) and [§ REQ-112 *Driver*](#driver) cite *One walk* for how the RM rules run, so one home holds each rule.

### Surface

```go
// One validator value; immutable after New, safe to share between goroutines.
type Validator struct { /* unexported */ }
func New(opts ...Option) *Validator

// c == nil: the RM rules alone, which is what ValidateRM returns. opts
// carries a decode's report of missing members (§ REQ-112 Value-typed
// mandatory presence); the decode-aware entries ValidateJSON and
// ValidateXML, and their Validator methods, decode and validate in one call.
func (v *Validator) Validate(root any, c *templatecompile.Compiled, opts ...ValidateOption) Result
func (v *Validator) ValidateJSON(data []byte, root any, c *templatecompile.Compiled) Result
func (v *Validator) ValidateXML(data []byte, root any, c *templatecompile.Compiled) Result

type Limits struct {
    Depth int // nesting depth at which the walk stops descending; 256 by default
    Nodes int // values, and list items holding none, visited per call before the walk stops; 100,000 by default
}
func WithLimits(l Limits) Option
```

- `New` **MUST** take functional options ([idiom.md § Functional options](idiom.md#functional-options)), ignore a nil `Option`, and read a `Limits` field that is zero or negative as its default, so no option disables a limit; the limits are the first options, and a later setting is added as an option, never as a parameter.
- The zero `Validator` and a nil `*Validator` **MUST** behave as one built with no options.
- The value **MUST** hold no per-call state after `New`, so one instance serves every goroutine of a server ([idiom.md § Concurrency](idiom.md#concurrency-req-026)); the compiled template is built once per template and shared. What belongs to one call, a decode's report of missing members, travels as a trailing `ValidateOption` of the call, never as a setting of the value.
- `Validate` **MUST** accept any RM value the registry knows ([rm-modeling.md § REQ-040](rm-modeling.md#type-registry-req-040)) and, given a nil `c`, apply the RM rules alone, so a root that binds to no template is validated by the same walk.
- The package-level entry points of § REQ-102 and § REQ-112 **MUST** behave as a `Validator` built with no options, keeping their nil guards: `Validate(root, nil)` still reports `nil_template`, and `ValidateRM` is the package-level entry for the RM rules alone, returning for a root the issues `Validate(root, nil)` on a `Validator` returns.

### One walk

The walk visits the instance's nodes. At each node it knows the RM class of the value and, where the template reaches, the compiled node the value binds to. The attributes it visits at a node are the union of three sets: the attributes the bound template node declares, the attributes present on the value, and the attributes the RM marks mandatory for the class. That union is what lets one walk find a required node the instance lacks, content outside the template, and an RM omission. A declared attribute that no instance of the value's class can carry **MUST** be left out, with no issue reported for it, its existence included: an attribute no serialization carries, the set [§ REQ-112 *Driver*](#driver) leaves out, and an attribute the compile marks as absent from its node's RM class ([§ REQ-111](#req-111--public-compiled-template-bridge) *Attributes the RM does not have*), whose path *Coverage* lists.

At each attribute, in this order:

1. **Admission.** Where the bound template node prohibits the attribute (§ REQ-102 *Structural — prohibited attributes*) and the attribute is present, the engine reports one issue, code `prohibited`, at the attribute's path, and does not enter the attribute. Where the value of a single-valued attribute, or an item of a multi-valued one, binds to none of the children the template allows under the binding rules of § REQ-102, the engine reports it as that section says (`slot_fill`, `rm_type_mismatch` or `alternative_mismatch`) and does not enter it. Where an item binds to a child the template does not allow, one whose occurrences upper bound is 0 (§ REQ-102 *Structural — prohibited attributes*), the child's occurrences finding of step 3 is the report for it, and the engine does not enter the item. Where the template does not mention the attribute, it is unconstrained: the engine visits it with the RM rules alone.
2. **Presence.** An attribute the template requires or the RM mandates that the instance lacks is reported once, by the layer *One finding per defect* below names. § REQ-102's rule that existence and cardinality both fire on one present, empty list concerns two template clauses and stays.
3. **Counts.** The cardinality of the attribute and the occurrences of each child, as § REQ-102 defines them, on the template layer.
4. **Each admitted item.** Identity and type conformance against its bound child (§ REQ-102); the RM rules of its class (§ REQ-112's catalogue); the template's value constraint where the child is a leaf ([§ REQ-103](#req-103--primitive-constraint-introspection)); then its own attributes by the same steps.

**Refused content.** Content the admission step refuses **MUST** draw its one admission finding and no other: the engine evaluates no RM rule on it and reports no issue from inside it. A rule of an admitted node is still evaluated on that node and reads the node's attributes as the instance holds them, a refused one included, and its finding at the node's own path **MUST** be reported; what it would report at or below the refused content is from inside it.

**One finding per defect.** A defect two checks find **MUST** be reported once, by the check named here:

- an attribute the instance lacks, by `required` on the template layer where the template requires it, and on the RM layer where only the RM mandates it, since a template requirement already implies the RM's;
- an RM-mandatory container that is present and empty, by the template's finding where the template reports that container at the same path, not by the RM layer's `cardinality`;
- a list that holds no item, by the template's finding where the template reports that list at the list's path or at a path below it (the list's path followed by an attribute or a predicate, as where the template reports the occurrences of a child the list allows, `/content[at0001]`), not by the rule of § REQ-112 *Non-empty lists* that reads it, at the list's path or, for a HISTORY's `events`, at the HISTORY's; for a HISTORY's `events`, likewise where the template reports that HISTORY's `summary`, at the summary's path or below it;
- a part of a value a primitive constraint binds that the RM rules report as absent or empty (§ REQ-102 *Primitive constraints*), by the RM rules, unless the walk stops at the depth limit or the visit limit before they report it, when the constraint judges the part as it judges any value;
- an empty CODE_PHRASE `code_string` and an empty temporal `value`, by the required-set walk's `required` (§ REQ-112 *Per-RM-type invariant catalogue*).

A member a decode reports missing (§ REQ-112 *Value-typed mandatory presence*) is read as absent at its path, so it is reported by the absent-attribute finding alone, the template's or the RM's, and nothing is reported below it.

An RM rule's own finding at the same path, such as a code outside its terminology group, is a second defect, reported beside the first.

A Go value reached from two places **MUST** be validated at each place, against each place's template node, so a defect at the second place is reported at the second path. A value that contains itself is a cycle, reported where it recurs and not entered, as § REQ-112 *Driver* says; the engine detects it on the active ancestry alone and keeps no record of values it has finished. At the depth limit the engine **MUST** stop descending and report `max_depth` once per walk, at the first path where it stopped, and at the visit limit stop and report `max_nodes` once, at the path where it stopped; *Coverage* lists both.

**Trials.** Binding a value among the children of one tier, or an item among those of one rank (§ REQ-102 *Structural — alternatives*, *Structural — binding items*), walks it under each child it tries, in OPT order, until one validates it. That trial is part of the walk, and the order of the steps and the union rule do not change inside it. A trial **MUST** obey three rules: its visits count toward the visit limit and the depth limit applies inside it; a trial in which the depth limit stops the walk never counts as one under which the value validates, whether or not the walk reports that stop there, since the walk reports `max_depth` once, so a stop an earlier part of the walk reported leaves none to report inside the trial, and the binding would otherwise turn on what came before it; and nothing a trial under a child the value does not bind to found reaches the result: no issue, `max_depth` included, no `Coverage` entry and no class for `Unevaluated`. A value of a single-valued attribute under k children of one tier so costs at most k walks of its subtree, since the walk keeps the findings of the first child while it tries the others, and an item of a list at most k + 1, since its path waits on the binding of the items beside it, so the walk walks it once more under the child it binds to. Whether a value validates under a child is decided once: where the walk meets a value it has tried under a child again under that child, read the same way (the same Go value, held by pointer, at the same depth), it takes the verdict already decided rather than try the value again, both to bind it and, inside the trial of an item of a list, whose findings never reach the result, in place of walking it under the child it binds to. So beyond that bound per level, the factor compounds over nested tiers and ranks only where the candidates are distinct subtrees the value is tried under, and the visit limit bounds the rest. Where the visit limit ends the walk inside a trial, no binding is decided at that place: of what its trials found, the engine **MUST** report only the `max_depth` and `max_nodes` issues of the trial in which the walk ended, and, where that trial is of an item of a list, at the path of the list's attribute: the item's own path waits on the binding the stop left undecided, so it would change with the limit.

A root with no template has every attribute unconstrained, so the walk is the floor, and `Validate(root, nil)` on a `Validator` returns the issues `ValidateRM` returns for the same root (*Surface*).

### Finding identity

```go
type Issue struct {
    Path     string               // § REQ-102 Issue paths
    Code     string               // § REQ-102 Issue codes
    Layer    Layer                // LayerTemplate, LayerRM, or LayerNone
    Rule     string               // the clause this issue evaluates; empty with LayerNone
    Detail   string
    Severity Severity
    Value    constraints.Redacted // § REQ-168
}

type Layer uint8
const (
    LayerNone     Layer = iota // a guard, a walk condition, or an issue from ValidateAQL
    LayerTemplate              // a template clause
    LayerRM                    // an RM rule or an RM-mandatory presence
)
func (l Layer) String() string // "", "template", "rm"; any other value "layer(N)"
```

Every issue the instance validators report **MUST** name its `Layer` and carry a non-empty `Rule`, except the issues that judge the call or the walk rather than the instance: the guards (`nil_root`, `nil_template`, `nil_composition`, the nil wrappers' codes, `rm_type_unknown`, and `invalid_shape` on undecodable input) and the walk conditions (`max_depth`, `max_nodes`, `cyclic_value`) carry no layer and an empty `Rule`. An issue a template clause produces is on the template layer; one an RM rule or an RM-mandatory presence produces is on the RM layer. An attribute the template walk finds absent is on the template layer when the template requires it, by its existence and, on a multi-valued attribute, where [§ REQ-102](#req-102--composition-validation) *An existence lower bound alone asks for no member* says it asks for a member there, and on the RM layer when only the RM marks it mandatory. An issue from `ValidateAQL` or `ValidateAQLWithTypeRelation` is not an instance finding and carries neither.

`Rule` names the clause the issue evaluates:

- on the RM layer, for a rule the pinned BMM names, `CLASS.Invariant`: the class that declares the invariant in the pinned RM or BASE BMM and the invariant's name as that BMM spells it (`DV_INTERVAL.Limits_consistent`, `ELEMENT.Inv_null_flavour_indicated`, `ENTRY.Language_valid` on any concrete entry, `Interval.Lower_included_valid` on any interval, `TERM_MAPPING.Match_valid`). That is the key the inventory of *Where the RM rules come from* uses;
- on the RM layer, for a rule the SDK applies that the BMM states in an attribute's definition rather than as a named invariant, a lower-case name with no class: `mandatory` for an RM-mandatory attribute the instance lacks, a mandatory string left empty included, and for an item of a list that holds no RM value (§ REQ-112 *Driver*); `cardinality` for an RM-mandatory container that is present and empty; `precision_range` for a `precision` below -1;
- on the template layer, one of `existence` (an attribute the template requires and the instance lacks, or one it prohibits and the instance carries), `cardinality` (the attribute's item count), `occurrences` (a child's count of bound items), `slot` (an item that fits no child or slot), `type` (type conformance and alternatives), `identity` (archetype and node ids), or, at a primitive leaf, the `Violation.Code` of § REQ-103.

`Code` keeps the vocabulary of § REQ-102 *Issue codes*, so a caller that dispatches on it keeps working. An issue whose code is already specific to a rule (`lower_included_valid`, `is_archetype_root`, `rm_version_valid`, `mappings_valid`, `term_mapping_match`, `code_not_in_value_set`) **MUST** carry both that code and the rule's name. `rm_invariant` stays the code of every other RM rule; `Rule` is what tells them apart, so a caller never needs `Detail` to learn which rule failed. `Layer` and `Rule` carry structure, never a submitted value ([§ REQ-168 *Field classes*](#field-classes)).

### Where the RM rules come from

The generator emits, from the `invariants` of every class in the pinned RM and BASE BMMs, BASE's primitive types included, an inventory keyed by class and invariant name, and a checked-in file classifies each entry as one of: *evaluated*, with the Go function that evaluates it; *not mechanical*, with the reason (the rule needs a terminology service, stored history, or a comparison the RM leaves undefined); or *out of scope*, with the reason. The code-generation check fails when an invariant of the pinned BMMs has no classification, so a BMM bump cannot add an unchecked rule silently ([ADR 0001](../adr/0001-bmm-version-bump-runbook.md)). An invariant that another evaluated check already decides, the mandatory-presence rule among them, is *evaluated* and names that check's function; its findings carry the rule of the check that reports them (*Finding identity*).

The RM rules the validators apply are the *evaluated* entries together with the rules *Finding identity* takes from an attribute's definition (`mandatory`, `cardinality`, `precision_range`); the rule bodies are hand-written. The inventory is a dispatch table, not a rules engine: the validators interpret no BMM invariant expression at run time and load no rule from outside the binary. The openEHR terminology checks of § REQ-112 *Coded invariants* are RM rules and stay inside this table. A seam for an external terminology service, one question (is this code a member of this value set) with a no-op default, is reserved and not built.

### Structural access

The validators read a node's attributes through access the generator emits for every concrete RM class the registry knows: for each attribute its name, declared RM type, whether it is a container, whether it is present, and its value, by plain field access ([idiom.md § Generics and reflection](idiom.md#generics-and-reflection), [ADR 0028](../adr/0028-generated-rm-attribute-access.md)). No registered class is a leaf for want of a reader: the walk **MUST** go below every present attribute of every registered class, the entries of a hash included, in ascending key order, and report an RM-mandatory attribute absent on any of them, unless no serialization carries it, the set [§ REQ-112 *Driver*](#driver) leaves out.

Whether an attribute is present **MUST** be decided from its declared type and the Go value alone, as follows. A pointer is present when it is not nil; an interface when it holds a value that is not a nil pointer; a string when it is not empty; a number or a boolean always; a list or a hash when it is not nil, and it is empty when it is present and holds no item or entry. A value held by value is present when it is not its type's zero value, an interface field holding a nil pointer counting as zero. At an attribute the RM marks mandatory, three types are also empty when their content is missing: a DV_TEXT whose `value` is empty, whether held directly or through an interface; a DV_CODED_TEXT with an empty `value` and an empty defining code; a CODE_PHRASE with an empty `code_string` and an empty terminology. At an optional attribute such a value is present, so the walk enters it and reports what it lacks; an object reference held by value is likewise present unless it is the zero value, so § REQ-112's reference entry reports each missing part at its own path. Three readings are fixed by § REQ-112: an interval bound is absent only when its side is marked unbounded and the bound is empty ([*Driver*](#driver)); EHR_STATUS `subject` is always present from the Go value; and ARCHETYPED `archetype_id` and `rm_version` are always present from the Go value, their emptiness being the *ARCHETYPED* entry's to report. A decode's report of missing members overrides the Go value's reading at each member it names ([*Value-typed mandatory presence*](#value-typed-mandatory-presence)).

### Coverage

```go
type Result struct {
    OK       bool
    Issues   []Issue
    Coverage Coverage
}

type Coverage struct {
    Stopped     []string // paths where a limit stopped the walk
    External    []string // paths of leaves whose value set is outside the SDK (a CONSTRAINT_REF)
    NotInRM     []string // paths of declared attributes the RM class of their node does not have, which the walk left out
    Unevaluated []string // "CLASS.Invariant" entries, of classes the walk visited, the SDK does not evaluate
}
func (c Coverage) Complete() bool // Stopped and External are both empty
```

`OK` reports the absence of error findings and nothing more. `Coverage` **MUST** say what the result does not prove: `Stopped` lists the path of each `max_depth` and `max_nodes` issue, so at most one per limit; `External` lists, in walk order, the path of each leaf the template binds to a `CONSTRAINT_REF` ([§ REQ-103](#req-103--primitive-constraint-introspection)), whose value set is bound outside the template ([§ REQ-111](#req-111--public-compiled-template-bridge) *Term definitions and bindings*) and so cannot be consulted, while a `C_CODE_PHRASE` that names an external terminology without listing codes is checked for that terminology and is not listed, since whether a code exists in an external terminology is outside every check the SDK makes (§ REQ-112 *Trust model*); `NotInRM` lists, in walk order and once per node, the path of each attribute the bound template node declares that the compile marks as absent from the node's RM class ([§ REQ-111](#req-111--public-compiled-template-bridge) *Attributes the RM does not have*) and the walk left out (*One walk*); and `Unevaluated` lists, sorted and once each, the invariants of the classes the walk visited, those their ancestors declare included, that the inventory of *Where the RM rules come from* does not classify as evaluated. `Complete` **MUST** report true exactly when `Stopped` and `External` are both empty: no limit stopped the walk, and every constraint it reached could be checked locally. `Complete` says nothing of `NotInRM`: no instance can carry such an attribute, so its constraint is a defect of the template, not a part of the instance the result failed to check. Nor does it say anything of `Unevaluated`, which lists RM rules the SDK does not evaluate on any instance, so it is reported beside `Complete` rather than folded into it. The zero `Coverage`, which a guard and `ValidateAQL` return, is complete. A coverage path is written by § REQ-102 *Issue paths* and is value-free.

## REQ-113 — Execution-oriented parsed AQL AST

REQ-109's `openehr/aql/parse` returns a lint-shaped `Document` that flattens the FROM/CONTAINS tree to a class set and erases the WHERE expression structure: the lint contract reasons over the *set* of bound classes and the *set* of paths, not their containment shape or the operator tree. An execution consumer (a server lowering AQL to SQL, a planner picking up CONTAINS nesting, a query rewriter) needs to read the *structure*. The construction-side `aql.Builder` (REQ-055) is the write-side mirror of that need.

The SDK **MUST** expose a **stable, generated-type-free, readable** structured AQL AST: a `string → structured query` entry point whose result a consumer can traverse without importing `openehr/aql/parse/gen` or any `internal/` package. The AST **MUST** preserve containment nesting, the WHERE operator/value tree, SELECT function/aggregate wrappers and aliases, ORDER BY direction, and LIMIT / OFFSET values. The WHERE and Value vocabularies are shared with the construction side: `aql.Comparison`, `aql.Junction`, `aql.NotExpr`, `aql.ExistsExpr`, `aql.MatchesExpr`, `aql.LikeExpr`, `aql.ParamValue`, `aql.StringValue`, `aql.IntValue`, `aql.RealValue` and `aql.BoolValue` are populated by both Builder and Parse: one model, two directions. The sealed `SelectExpr`, `WhereExpr` and `Value` sets grow additively, so a consumer type-switching over them treats an unrecognised case as out of catalogue rather than panicking, and each interface's godoc says so.

### Surface

```go
// Package github.com/cadasto/openehr-sdk-go/openehr/aql/parse

// Tier 2 — the target read AST.
func ParseQuery(q string) (*Query, error)              // (*Query, aql.ErrIncompleteAST) on catalogue gap
func (d *Document) Query() *Query                       // best-effort partial AST
func (d *Document) QueryErr() error                     // aql.ErrIncompleteAST diagnostic, nil otherwise

type Query struct {
    Select  SelectClause
    From    FromClause
    Where   aql.WhereExpr  // nil when no WHERE clause
    OrderBy []OrderTerm
    Limit   LimitExpr      // nil when no LIMIT
    Offset  LimitExpr      // nil when no OFFSET
}
func (q *Query) Emit() (string, error)                  // refuses (returns aql.ErrIncompleteAST) on an extractor-incomplete AST

// LIMIT / OFFSET — sealed union of literal and parameter forms.
type LimitExpr  interface { /* sealed */ }
type IntLimit   struct { N int }                        // `LIMIT 50`
type ParamLimit struct { Name string }                  // `LIMIT $rows`

// SELECT
type SelectClause struct {
    Distinct bool
    Star     bool
    Items    []SelectItem
}
type SelectItem  struct { Expr SelectExpr; Alias string }
type SelectExpr  interface{ isSelectExpr() }
type PathExpr    struct { IdentifiedPath }
type FunctionCall struct { Name string; Args []SelectExpr; Distinct, Star bool; Raw string }

// FROM / CONTAINS — nested containment tree
type FromClause   struct { Root ClassExpr; Contains *Containment }
type Containment  struct { Class ClassExpr; Children []Containment; ChildJoin ContainsJoin; Negated bool }
type ContainsJoin int  // ContainsAnd / ContainsOr

// ORDER BY
type OrderTerm struct { Path IdentifiedPath; Dir OrderDir }
type OrderDir  int  // OrderAsc / OrderDesc
```

The shared `aql.Value` vocabulary also carries `aql.NullValue`, a typed NULL, so the unquoted `NULL` keyword round-trips without colliding with a `StringValue{"NULL"}`. `aql.ErrIncompleteAST` is the sentinel `ParseQuery` and `Document.QueryErr` surface, and `(*Query).Emit` returns it for an AST from an incomplete extraction (§ Catalogue and residual).

Tier 1, the cheap interim, exposes the validated ANTLR tree via `(*Document).Tree` (return type `gen.ISelectQueryContext`, explicitly unstable). It removes the re-parse cost for consumers already recursing the generated parser but does not solve the generated-coupling concern; Tier 2 is the stable read AST.

The construction side carries `aql.NotExpr`, `aql.ExistsExpr`, `aql.MatchesExpr` and `aql.LikeExpr` (with their `Not` / `Exists` / `Matches` / `Like` constructors), so the parser populates the same shapes the Builder constructs. `aql.FormatWhere` renders a `WhereExpr` in canonical form, and `(*Query).Emit` renders `WHERE` through it.

### Structured path access

Two path-bearing sub-structures are exposed as parsed structure, not only raw text, so an execution consumer reads them without re-tokenizing AQL the SDK already parsed once:

- **`ClassExpr.PredicateComparison`**: a class *standing* predicate (e.g. `EHR e[ehr_id/value = $x]`) is exposed as an optional `*aql.Comparison` (`{path, operator, value}`, reusing the shared vocabulary) when it is a simple comparison. It **MUST** be nil for an archetype-HRID predicate (on `ClassExpr.Archetype`), a version predicate, or a non-scalar or complex standing predicate, so a comparison is distinguishable from a non-comparison. The comparison's `ParsedPath` carries the relative left-hand path's structured `Segments` with an **empty `Alias`** (a class-predicate path binds no FROM alias); the verbatim `ClassExpr.Predicate` text is retained.
- **`aql.Comparison.ParsedPath`**: a comparison carries the structured path (`*aql.IdentifiedPath`: alias + segments) beside the raw `Path` string, populated by the parser. A WHERE comparison sets the alias root; a class standing predicate sets `Alias == ""` (relative path). It is nil on the write side and for a path shape the parser does not structure. `ParsedPath.Raw` **MUST** equal `Path`.

The shared path vocabulary, `aql.IdentifiedPath` and `aql.PathSegment`, lives in `openehr/aql` so that `aql.Comparison` can carry it. `parse.IdentifiedPath` embeds `aql.IdentifiedPath` and adds the parse-only `Clause` and source `Position` (promoted fields keep existing access unchanged); `parse.PathSegment` re-exports `aql.PathSegment`. Emission uses `Comparison.Path` and the verbatim class `Predicate`, so the structured fields leave the round-trip property below unaffected.

### Round-trip property

For any AQL query the parser accepts and the catalogue models:

```
Emit(ParseQuery(Emit(ParseQuery(x)))) == Emit(ParseQuery(x))
```

The first emit normalises whitespace, keyword casing, optional defaults (ASC), and clause ordering against the canonical write form; the second parse-emit **MUST** be a fixed point. This is the buildable-grammar equivalent of [PROBE-020](conformance.md#probe-020--aql-builder-string-stability), held by [PROBE-080](conformance.md#probe-080--aql-parseemit-round-trip-property).

### Trust model

The structured AST is **syntax-faithful for the catalogue**: it carries the source path text verbatim (`IdentifiedPath.Raw`), and function names are normalised to upper case (`count` → `COUNT`) so emission produces canonical AQL regardless of source casing. It does **not** evaluate:

- archetype / template constraints (that is REQ-102);
- terminology binding;
- semantic validity beyond the SDK grammar profile (the server remains the execute-time authority, [PROBE-021](conformance.md#probe-021--aql-parse-error-mapping)).

### Catalogue and residual

`parse.ParseQuery` **MUST** model every query the SDK grammar profile admits without `aql.ErrIncompleteAST`, apart from the one residual below. `aql.ErrIncompleteAST` is fail-closed by design, so every gap is a query shape a downstream engine has to refuse wholesale even when its own execution layer could run it. Among the shapes the catalogue models:

1. A primitive literal in SELECT (`SELECT 1, e/ehr_id/value FROM …`), as a typed literal item.
2. Mixed `SELECT *, col`, order-preserving.
3. A function call as the left operand of a WHERE comparison (`WHERE LENGTH(o/name/value) > 5`).
4. `MATCHES` with a `TERMINOLOGY(...)` or `{URI}` operand, modelled structurally (function name and three string arguments, or the URI), not as raw text.
5. A path-vs-path comparison (`WHERE a/x = b/y`).
6. A boolean junction at the FROM root (`FROM COMPOSITION c1 OR COMPOSITION c2`, with `AND` and grouping).
7. A parameter, primitive or nested function call as a function argument (`SELECT CONCAT('a', $p, LENGTH(x/y)) …`), in SELECT and in WHERE.
8. `AND` / `OR` junctions over any modelled operand.
9. The deprecated `SELECT TOP` clause (§ The `TOP` carrier).

**The residual is one condition: a numeric literal the value vocabulary cannot represent.** That is a `LIMIT` / `OFFSET` value or a `SELECT TOP` count beyond Go `int`, an INTEGER outside `int64` (the type `aql.IntValue` carries), or a REAL beyond `float64` in either direction (an overflow, or an underflow whose nearest representable value is zero, such as `1e-400`, which `strconv.ParseFloat` reports as `(0, nil)` rather than as a range error), in any value position: a SELECT literal, a comparison operand, a `MATCHES` member. Such a literal **MUST** be refused, never degraded: `ParseQuery` and `Document.QueryErr` return `aql.ErrIncompleteAST`, and `(*Query).Emit` refuses the partial AST with the same error, because degrading it would be silent precision loss (`> 1e-400` emitted as `> 0.0` flips the predicate across the zero boundary). The range of `int64` is asymmetric: its negative bound is exactly representable and is read, not refused, and a repeated unary minus is read at its parity (`numericPrimitive` is recursive), not reported as out of range.

Every other extractor branch is defensive: unreachable against the profile, and recording a gap rather than returning a zero value if a widened grammar ever reaches it. No grammar change is licensed here.

### The `TOP` carrier

openEHR **QUERY Release-1.1.0 § 4.4.3** governs the clause. Its syntax is `SELECT TOP integer [FORWARD|BACKWARD]`; from Release 1.1.0 the modifier is deprecated in favour of `LIMIT` with `ORDER BY`, and the specification announces its removal in a future major release; and `TOP` is not allowed beside a `LIMIT` clause in the same query. A deprecated but legal construct is still one the SDK reads: until the removal release a client, a stored query or a conformance corpus may carry `TOP`.

- The `SELECT` clause **MUST** carry the clause as an optional value (`SelectClause.Top`, an `*aql.TopClause`), so "no `TOP`" stays distinguishable from `TOP 0`: a dropped `TOP` turns a bounded query into an unbounded one, and an absent one read as `0` inverts it.
- The carrier **MUST** model the row count and the direction, with an unspecified zero direction, so a bare `TOP n` round-trips without a direction the source did not write and a `BACKWARD`, which selects the other end of the result set, is never lost.
- `TOP` and the `LIMIT` / `OFFSET` clause **MUST** each report what the source wrote, independently. The parser never normalises one into the other and never picks one when a query carries both: that query is spec-invalid (§ 4.4.3), and reporting it as written is what lets the lint name it (`aql_top_with_limit`, [§ REQ-109](#req-109--aql-static-lint)). `Emit` renders both as written, since the profile accepts the text and the emitter is not the diagnosis layer.

The profile's `top` production admits no `PARAMETER`, and the `SDK-AQL-003` parameter relaxation does not extend to it: the SDK does not widen a construct the specification is removing. The carrier therefore holds an integer count and does not reuse the `LIMIT` vocabulary (`parse.LimitExpr`), which has a parameter form and no direction. A count outside Go `int` is the residual above. The vocabulary lives in `openehr/aql` and is shared with the builder ([§ REQ-163](#req-163--aql-write-side-expressivity-parity)), which also fixes its canonical spelling.

### Projection source text

- `parse.LiteralExpr` **MUST** carry the literal's source text as written (`Raw`) beside its typed `aql.Value`, for a literal in a `SELECT` projection and for a literal in a function-call argument. The openEHR result schema names a projected column with no `AS` alias by its expression text, and re-rendering the typed value gives the canonical form, not the source form (`1.50` → `1.5`, `001` → `1`, `"x"` → `'x'`).
- `parse.FunctionCall` **MUST** carry the call's source text as written (`Raw`), for a function or aggregate call in a `SELECT` projection and for a call nested as a function-call argument, for the same reason: rebuilding the text from the parts gives the upper-cased name and canonical spacing (`length( c/name/value )` → `LENGTH(c/name/value)`), which is neither what the client wrote nor how a path or literal column is named.
- Emission **MUST** render the typed value in canonical form and the call from its parts, never the source text: the canonical write form is normative ([wire.md § REQ-055](wire.md#req-055--wire-boundary)), and a `LiteralExpr` or `FunctionCall` a caller constructed has no source text, so a consumer treats `Raw` as optional.

A value-position call (`aql.FuncCall`) carries no source text, as a `WHERE` literal carries none: only a projection names a result column.

A consumer that needs a deterministic rendering of any `aql.Value`, parsed or constructed, uses `aql.FormatValue`; there is no second escaping implementation.

### Structured node predicates

§ Structured path access types exactly **one** bracketed predicate, the standing comparison at the class position, and leaves every other predicate as the raw text between the brackets, which [§ REQ-119](#req-119--re-parseable-canonical-aql-emission) keeps verbatim because a whitespace-collapsed predicate does not re-parse wherever the grammar separates its operands with a keyword. A consumer comparing that text against a compiled-OPT node id or a name would have to model the lexer's trivia itself. The path-segment predicate is therefore exposed as structure beside its text. **`Raw` is the spelling and stays authoritative for emission; the structured model is the value and is authoritative for comparison.** The model carries what `Raw` does not: where each component begins and ends.

**The bracket is three productions, not one.** A bracketed path predicate is `pathPredicate : SYM_LEFT_BRACKET (standardPredicate | archetypePredicate | nodePredicate) SYM_RIGHT_BRACKET`, and the three alternatives overlap:

| Production | Admits |
|---|---|
| `standardPredicate` | `objectPath COMPARISON_OPERATOR pathPredicateOperand` |
| `archetypePredicate` | `ARCHETYPE_HRID` or `PARAMETER` |
| `nodePredicate` | a node id or HRID with an optional name, `PARAMETER`, a comparison, `objectPath MATCHES CONTAINED_REGEX`, and `AND` / `OR` junctions over itself |

A comparison, a bare HRID and a bare `$param` are therefore each spelled by two productions, once as their own top-level alternative and once inside `nodePredicate`, so which parse-tree node carries a form depends on whether it sits at the top of the bracket or nests as a junction operand. The structured kind **MUST** be a property of the form, not of the production that carried it: a form yields the same kind at the top of a bracket and as a junction operand. The kind set is derived from the vendored grammar and checked against it mechanically ([PROBE-095](conformance.md#probe-095--aql-predicate-structuring)), never from a hand-written list of what the position is believed to admit.

**The structured kinds.** The model **MUST** be a sealed sum in `openehr/aql`, in the package's `aql.Value` / `parse.SelectExpr` style, covering these forms: a node id (`[at0001]`, `[id3]`); a node id with a name (`[at0001, 'Systolic']`); an archetype HRID; an archetype HRID with a name; a parameter (`[$param]`); a comparison, carrying `aql.Comparison`, so a WHERE comparison and a predicate comparison share one vocabulary; a regex match (`objectPath MATCHES CONTAINED_REGEX`, whose token also admits an optional `; 'label'` tail the model carries as its own component); and an `AND` / `OR` junction over two structured predicates, with its operator and both operands.

**The name slot.** The grammar admits `SYM_COMMA (STRING | PARAMETER | TERM_CODE | AT_CODE | ID_CODE)` after both the node-id and the archetype-HRID alternatives. The name carrier **MUST** discriminate all five spellings, on both alternatives, so a consumer resolving names against a template can tell a name deferred to bind time (`PARAMETER`) from a name it can resolve now.

**Components are values, not spellings.** Every component **MUST** be the value a reader compares or displays: delimiters removed (an at-code without its brackets, a name without its quotes), escapes resolved, and trivia (whitespace and `--` comments) absent, while `Raw` keeps the spelling verbatim. A path-valued component follows the comparison vocabulary it reuses: the as-written `Path` beside the structured `ParsedPath`, whose `Segments` are the trivia-free form. A regex component decomposes the `CONTAINED_REGEX` token: the braces, the interior whitespace, the `/` delimiters and the `;` are delimiters, so the model carries the pattern (with only the `\/` spelling resolved, which exists because `/` is the delimiter) and the optional label (unquoted, escapes resolved) as separate values; every other backslash sequence is regex syntax and stays as written.

**An unstructured predicate is a statement, not a gap.** A predicate the SDK does not structure **MUST** report itself as unstructured, a nil structured carrier beside a populated `Raw`, and never as a partial structure, which a consumer could not tell from a complete one at the type level. The unstructured forms at the path-segment position are exactly: a comparison whose right-hand operand the shared value vocabulary does not carry (an `objectPath` operand, a node-code `ID_CODE` / `AT_CODE` operand, or a numeric literal in the residual of § Catalogue and residual), and a junction with an unstructured operand. Every other alternative of every production the position admits is structured, so a reader can fail closed on exactly these forms. Shrinking the set (a `PathValue` carrier for the path operand, a node-code value kind) widens the sealed value vocabulary and is its own change.

**The class position keeps its carrier.** `parse.ClassExpr`'s own fields (`Archetype`, `ParamArchetype`, `Predicate`, `PredicateComparison`) stay the only carrier of the class-position predicate: its three admissible top-level forms already map onto them, and a second carrier derived from the same source node would drift. The structured model sits at the path-segment position only.

**Emission ignores the structured model.** `Emit` **MUST NOT** read it: § REQ-119's round trip renders `Raw`, so a consumer mutating the model cannot change what is emitted.

**Out of scope.** A carrier for the `VERSION` class predicate keywords (`LATEST_VERSION` / `ALL_VERSIONS`): `versionPredicate` is a different production with a different accept set. Validating the predicate sub-grammar ([§ REQ-119 § Out of scope](#req-119--re-parseable-canonical-aql-emission)), since structuring what the parser accepted is not deciding what to accept. Rewriting or normalising `Raw`, which stays verbatim. The builder side: `aql.Builder` writes predicates from typed inputs ([§ REQ-163](#req-163--aql-write-side-expressivity-parity)). And a disclosure policy over the components: each component is individually addressable so a consumer applies its own policy, and the SDK's own diagnostics follow § Value-free structured drop records.

### Comparability

The shared vocabulary is not safely `==`-comparable. `aql.PathValue` and `aql.FuncCall` carry slices, so `==` on either, on a `WhereExpr` or structured predicate holding one, or on an `aql.SelectField` carrying a call-shaped field, compiles and then panics at run time, and so does a map insertion keyed by one. The SDK **MUST** ship a panic-free equality over `aql.Value` (`aql.EqualValues`) and over the structured predicate model (`aql.EqualPredicates`), across every value and pointer shape, a typed-nil pointer included, the predicate equality comparing components and a path through its structured form, so `[name / value = 'x']` equals `[name/value='x']`. The compiler does not see the trap, so the godoc of each affected type states that `==` and map-key use are unsupported. Equality over `WhereExpr` and `SelectExpr` is not offered: predicate-tree equality needs a normalisation policy first (is `a AND b` equal to `b AND a`?), which waits until a consumer needs it. Callers compare built query strings.

### Value-free structured drop records

A diagnostic is useful only if a consumer can act on it without republishing the query it came from. The drop channel names the offending construct by quoting its source text into `aql.ErrIncompleteAST`, and [§ REQ-109](#req-109--aql-static-lint)'s lint issue quotes in its value-bearing fields too. A consumer whose refusal reasons may name structure (an operator, a clause, a path shape) but never a value, because an AQL literal can be a payload value no quoting masks, would otherwise discard the diagnostics wholesale, and its clients would get a generic refusal where the SDK knew what was wrong and where. The field rule below is stated once, here, and binds both surfaces.

**The two field classes.** Each field of a diagnostic surface **MUST** be in exactly one of two classes, and the godoc of the type a consumer holds names each field's class:

| Class | Rule |
|---|---|
| **Value-free** | **MUST NOT** carry source text, in any circumstance: a record that cannot be attributed reports that (a zero span, an unclassified kind) and never falls back to quoting the source |
| **Value-bearing** | **MAY** embed query spellings; a disclosure boundary treats them accordingly |

For the drop record, the construct kind, the clause and the source span are all value-free; it has no value-bearing field. [§ REQ-109 § Value-free lint diagnostics](#value-free-lint-diagnostics) classes the lint issue's fields against this same table: one rule, two surfaces.

**The drop record.** Every construct the extractor drops **MUST** be recorded as a value-free `{kind, clause, span}`, reachable from the `Document` in source order through an accessor that runs the same lazy, once-only extraction as `Query()` / `QueryErr()`, so a `Document` nobody extracted never reads as "nothing dropped", and that returns a copy, so a caller cannot corrupt the shared `Document`. `QueryErr()` keeps its text and its `aql.ErrIncompleteAST` sentinel.

**The kind.** The kind **MUST** be a closed enumeration of drop classes whose zero value means unclassified, so a reader can switch over it exhaustively and fail closed; adding a member is a consumer-visible change. Its members are classes, not extractor call sites. A reachable class, a legal query the profile admits carrying a construct the value vocabulary cannot represent (today the one residual of § Catalogue and residual), has its own member, which the corpus reaches. The defensive arms, unreachable while the catalogue and the profile agree, share one member meaning "a construct the catalogue does not model", and their unreachability is asserted at the unit level, since no corpus can reach a site no legal query reaches. A sweep derived from the extractor source holds every site that sets the incomplete flag to recording a kind, so a drop with no record is a testable defect.

**The clause.** The clause **MUST** be the existing `parse.Clause`, extended append-only: its existing members keep their numeric values, since a consumer may have persisted or compared them, and `String()` gains an arm for each new member. An existing exhaustive switch over `Clause` meets each new member as a case it does not handle.

**The span.** The span **MUST** be a start and an end `parse.Position` (`{Line, Col}`, the package's one positional vocabulary, already on `SyntaxError` and every AST node) over the exact input handed to the parser, pointing at the offending construct rather than at its enclosing clause, and zero when the construct cannot be attributed. A caller holding the input can then quote the construct under its own policy.

Structured diagnostics for the simplified-format codecs ([§ REQ-053](wire.md#req-053)) are a separate surface and out of scope here, and so is redaction policy: what counts as a value is the consumer's decision, and this section guarantees only that the value-free fields carry none.

## REQ-119 — Re-parseable canonical AQL emission

[PROBE-021](conformance.md#probe-021--aql-parse-error-mapping) pins that the typed builders cannot emit syntactically invalid AQL (the write-side complement of [§ REQ-055](wire.md#req-055--wire-boundary)'s canonical form), and [§ REQ-113](#req-113--execution-oriented-parsed-aql-ast) makes `(*Query).Emit` a fixed point of the parse/emit round trip. Both are stated over the *shapes* the catalogue models. This requirement binds the value positions inside those shapes and the text a write path splices in verbatim, so that a consumer gets one guarantee, *what this SDK writes, it can read back*, rather than one that holds per clause and lapses per literal.

Two failure modes run through it. Emitting text the parser **rejects** is loud: the caller gets an error the moment the query is read back. Emitting text the parser **accepts as something else** is silent, invisible to every round-trip, golden and parser check downstream, and it is the only reason to refuse an operand that would otherwise be valid AQL.

### The emission closure property

The validating write paths are `aql.Builder.Build`, `aql.FormatWhere` and `(*parse.Query).Emit`.

- **Round-trip closure.** For every value a validating write path emits, in every value position it renders, the `SELECT` list included, `ParseQuery` of the emitted text **MUST** succeed and recover a value equal to it under `aql.EqualValues`; a value the path cannot read back is refused instead. The write paths apply the same guards, so one input gets one answer by any route: `Build` and `Emit` both render `WHERE` through `aql.FormatWhere`'s single validate-then-emit sequence.
- **One unvalidated formatter.** `aql.FormatValue` returns no error and so cannot refuse; it is the escape hatch for a value the caller has already checked, outside the closure. Being unvalidated does not license a panic: it **MUST** render a value with no wire form (a nil or typed-nil pointer, reachable through the public API as the zero `aql.MatchesExpr.Terminology`) as the empty string. The SDK **MUST** expose `aql.ValidateValue`, which refuses every value the closure refuses, a value with no wire form included, so a caller, or a write path outside `openehr/aql`, can hold the same line before calling `FormatValue`.
- **No silent substitution.** Where a caller-supplied operand is emitted verbatim because its grammar token is unquoted (the `MATCHES {uri}` operand and the single-token identifier positions below), the write side **MUST** refuse operand text that would change the query's structure, even when the resulting text is valid AQL. The path positions REQ-055 rule 3 emits verbatim by contract are outside this rule: caller data belongs in `aql.Param` ([§ REQ-055](wire.md#req-055--wire-boundary), the injection guard).
- **Refuse, never re-spell.** A value the grammar cannot carry **MUST** fail with an error wrapping `aql.ErrInvalidQuery`, not be normalised into a spelling that parses, which would change what the query asks.
- **Verbatim text round-trips as identity.** Text the read side captures and the write side re-emits verbatim (the class and path predicates, `aql.IdentifiedPath.Raw`, `aql.Comparison.Path`) **MUST** come back unchanged, the caller's own spacing, line breaks and comments included. The read side takes that text from the parser's character stream, because the token stream drops the whitespace that separates keyword tokens: `[a/b='c' AND d/e='f']` would come back `a/b='c'ANDd/e='f'`, which does not parse. A projected literal's or function call's source text is read from the character stream too, but it is never re-emitted ([§ REQ-113 § Projection source text](#projection-source-text)).
- **Every shape, and its pointer twin.** The sealed vocabularies `aql.Value`, `aql.WhereExpr`, `parse.SelectExpr` and `parse.LimitExpr` are each satisfied by the value and the pointer form of every shape, and a pointer is reachable without a caller writing `&` (`aql.MatchesExpr.Terminology` is a `*aql.FuncCall`). Every validator, emitter and diagnostic **MUST** give the two forms the same answer, and refuse a nil or typed-nil instead of panicking. The SDK **MUST** export each vocabulary's normaliser (`aql.DerefValue`, `aql.DerefWhere`, `parse.DerefSelectExpr`, `parse.DerefLimitExpr`), so a consumer type-switching over an additive sealed set can bind the same rule to both forms.
- **Absence is positional.** A predicate that denotes nothing (an untyped nil or a nil pointer) **MUST** be read as no clause at the top of a `WHERE`, including beside `FromEHR`'s implicit filter, and be refused as the operand of a `NOT` or a term of a junction, where an arm that quietly vanished changes the result set.
- **A narrower position takes its own accept set.** Where a rule narrows a position below the general `terminal` value set, the write side **MUST** accept only what that position can lex, rather than delegate to the shared value validator: `likeOperand : STRING | PARAMETER`; a braced `MATCHES` member (`valueListItem : primitive | PARAMETER | terminologyFunction`, where `primitive` names the `BOOLEAN` token but `BOOLEAN`, declared after `IDENTIFIER`, never lexes, so `MATCHES {true}` is refused); the bare `matchesOperand : terminologyFunction`, which admits no other call; and `limitValue : INTEGER | PARAMETER`.
- **Junctions.** A junction **MUST** carry at least one term and an operator from its vocabulary, checked as a comparison operator is, whether it came from a constructor or a struct literal. Where two functions decide the same question about a node (is it a class or a junction?) they agree, so a `VERSION` class expression is never reclassified as a grouping and dropped from the emitted chain.
- **Refusals of caller text are value-free.** The refusal of a `MATCHES {uri}` operand, of a class predicate, and of emitted text that fails verification (§ Emission verified after emission, `Build()`'s projection check included) **MUST** name the coordinate and the structural reason (the path, the predicate, the clause or the item, the component or condition that failed, a value-free position such as a byte offset) and **MUST NOT** reproduce value content: no URI text, in whole or in part, no projection text, no string, regex, comment or `TERM_CODE` display-name content of a predicate, and not the parser's own syntax message, which echoes source. These errors are the return value of `Build` and `Emit`, and a class predicate is where openEHR carries the identifiable root (`[ehr_id/value='…']`, `[subject/external_ref/id/value='…']`), so a verbatim body would move a patient identifier into whatever a consuming CDR does with an error. A refused predicate is named in an elided form that keeps every path, operator, node code, term code, numeric literal and delimiter, and replaces only the content of the regions the bracket scan tracks as content (§ The class predicate positions); an unterminated region keeps its opening delimiter, since which construct was left open is the finding. The renderer is exported as `aql.RedactPredicateValues`.

### Canonical value spellings

These value-level rules extend the canonical write form, whose home is [wire.md § REQ-055](wire.md#req-055--wire-boundary). Each is derived from the vendored grammar profile (`resources/aql/grammar/active/`, ADR [0007](../adr/0007-aql-antlr-grammar-profile.md)), which is the authority ([§ REQ-109](#req-109--aql-static-lint)'s syntax floor); no rule here widens the profile.

- **String literals** **MUST** be emitted with the grammar's `ESCAPE_SEQ` (a backslash before the escaped character), never with the SQL-style doubled quote: the `STRING` token admits only `ESCAPE_SEQ`, `UTF8CHAR`, `OCTAL_ESC`, or a character that is neither a backslash nor the delimiter, so a doubled quote ends the token and opens another. Decoding **MUST** be the exact inverse, over all three escape shapes and both delimiter forms: the `STRING`, `DATE`, `TIME` and `DATETIME` tokens all admit `"…"` beside `'…'`, and a delimiter that survives into the decoded value turns a comparison into one that matches nothing.
  - The C0 controls that have an `ESCAPE_SEQ` spelling (`\a \b \f \n \r \t \v`) **MUST** be emitted escaped, so canonical AQL stays single-line and printable, and every other character the token admits raw emitted as it is, `"`, `?`, `*` and the controls with no `ESCAPE_SEQ` spelling included.
  - A byte that begins no valid UTF-8 sequence **MUST** be emitted as `OCTAL_ESC` (`\NNN`), the grammar's only spelling for an arbitrary byte: the lexer decodes its input to runes, so a raw byte would come back as U+FFFD on the second pass.
  - Decoding **MUST** combine an adjacent UTF-16 surrogate pair into the character it denotes, and read a lone half as U+FFFD: `UTF8CHAR` is exactly four hex digits, so a character outside the BMP has no other spelling.
- **Real literals** **MUST** be emitted in decimal form with a fractional part, so the text re-lexes as `REAL : DIGIT* '.' DIGIT+` and never as `INTEGER : DIGIT+` (`2.0`, never `2`), or be refused where no such spelling exists (an infinity or NaN). Scientific notation (`SCI_REAL` / `SCI_INTEGER`) is read and re-emitted in decimal form, a canonicalisation and not a value change.
- **Integer literals** are bounded by `aql.IntValue`'s `int64`; the residual of [§ REQ-113](#req-113--execution-oriented-parsed-aql-ast) covers only a literal outside that type.
- **A value-position function name** **MUST** lex as the grammar's `IDENTIFIER` or one of its `*_FUNCTION_ID` tokens. Shadowing turns on declaration order in `AqlLexer.g4`, not on keyword-ness: a name spelled like a keyword token declared before `IDENTIFIER` is refused, notably the aggregates (`COUNT`, `MIN`, `MAX`, `SUM`, `AVG`), which are real AQL functions but belong to `aggregateFunctionCall`, admitted in `SELECT` alone; `true` / `false` (`BOOLEAN`, declared after `IDENTIFIER`) are accepted, because the grammar admits them as a function name and refusing them would make `Emit` reject an AST `ParseQuery` produced.
  - A **projected** function name in `SELECT`, and its call, **MUST** be held to the same accept set with the aggregates admitted, each call in the shape its rule admits: `COUNT` takes `DISTINCT? path` or a bare `*`, never a star beside arguments or `DISTINCT`; `MIN` / `MAX` / `SUM` / `AVG` take exactly one identified path; and no other projected call carries `DISTINCT` or a star. A call outside its shape is refused, never resolved by dropping a part: `COUNT(*)` emitted where the AST said `COUNT(c/x)` counts rows instead of values.
- **`TERMINOLOGY`** **MUST** carry exactly three string-literal arguments and no `DISTINCT` or star argument, on both carriers: the read and write sides model a value-position call and a projected one as different types (`aql.FuncCall` and `parse.FunctionCall`), and checking one would leave the other emitting text the parser rejects.
- **A parameter placeholder** **MUST** spell the grammar's `PARAMETER : '$' IDENTIFIER_CHAR` (a leading letter, then letters, digits and underscores) in every position that carries one, the in-text `LIMIT` / `OFFSET` operand included. This is [§ REQ-055](wire.md#req-055--wire-boundary) rule 4's channel for caller data, so an unchecked name would let the injection guard's own recommendation emit a structure-changing query: `$p AND c/secret = 1` re-parses as two predicates where the caller wrote one. A parameter is not a projection: `columnExpr` has no `PARAMETER` alternative while a function argument (`terminal`) has, so a bare parameter as a `SELECT` item **MUST** be refused, while one inside a projected call's arguments stays legal. `aql.PathValue` is exempt from the closure: it is one of the identifier positions REQ-055 rule 3 emits verbatim by contract, developer-authored, and not the channel for caller data.
- **A `MATCHES {uri}` operand** **MUST** be refused unless, lexed alone between the braces, it is the grammar's `URI` token and no token declared before `URI` claims it; `TERM_CODE` (`<term>::<code>`) is the case in force. The check follows the token's own decomposition (`URI : URI_SCHEME ':' URI_HIER_PART ( '?' URI_QUERY )? ( '#' URI_FRAGMENT )?`), not a flat union of the delimiter sets, which is broader than any single position admits: `%` leads `URI_PCT_ENCODED` and needs two hex digits, `[` / `]` occur only in an `URI_IP_LITERAL` host, and `#` separates the fragment once and appears nowhere inside it. It is not an RFC 3986 parser: a spellable but structurally odd URI (an empty host, a dotted quad out of range) reaches the wire, where the backend stays the authority (PROBE-021).

**Verbatim text on the read side.** `aql.IdentifiedPath.Raw`, `aql.PathSegment.Predicate` and `parse.ClassExpr.Predicate` report what was written, trivia included. The SDK **MUST** expose its own trivia model as `aql.StripPredicateTrivia`, for a consumer that compares that text rather than re-emitting it, so that the consumer does not model the lexer's skipped trivia a second time; the structured predicates of [§ REQ-113 § Structured node predicates](#req-113--execution-oriented-parsed-aql-ast) let most consumers compare components instead.

### Single-token identifier positions

Three positions carry exactly one `IDENTIFIER` token: a `SELECT` `AS` alias (`selectExpr : columnExpr (AS aliasName=IDENTIFIER)?`), and a class's alias and RM type (`classExprOperand : IDENTIFIER variable=IDENTIFIER? …`). A fourth carries exactly one `ARCHETYPE_HRID` or `PARAMETER` (`archetypePredicate`). All four are spliced verbatim into the emitted text, so a caller string carrying a delimiter re-parses as a different query with no error: `Alias: "x, c/y"` emits `SELECT c/x AS x, c/y FROM …`, which is two projections.

Each of these positions **MUST** accept exactly the strings that lex as its one token, with the `VERSION` rule below as the one carve-out, on every write path that renders it: `aql.Builder` and `(*parse.Query).Emit` refuse the same strings, the builder after trimming surrounding whitespace on intake, a trim that only removes padding and so cannot make a splice. The test is over what the lexer does, not over an alphabet. A keyword declared before `IDENTIFIER` is refused, and the refused set is wider here than for a function name, because `functionCall` lists the `*_FUNCTION_ID` tokens as alternatives: `LENGTH` may name a function but is not an identifier. `true` / `false`, declared after `IDENTIFIER`, are accepted. `at0001` and `id123` lex as `AT_CODE` / `ID_CODE` and are refused, while `AT0001` is a valid alias, because the `at` / `id` prefixes are lower-case literals rather than the case-insensitive letter fragments the keywords use.

`VERSION` is not an identifier but a separate alternative of `classExprOperand` (`VERSION variable=IDENTIFIER? …`). It **MUST** be refused as an alias on every carrier and as the RM type of a `parse.ClassExpr` whose `Version` flag is unset, and accepted as the RM type where the class model has no flag (`aql.Builder` and `aql.Containment` model a class as an RM-type string). On `parse.ClassExpr` the flag is the carrier, and an unflagged `RMType: "VERSION"` would emit text that re-parses with the flag set, an AST the caller did not write; on the builder the spelling is the carrier, so `FROM VERSION v` and `EHR e CONTAINS VERSION v CONTAINS COMPOSITION c` stay buildable. A `VERSION` class takes no archetype predicate on either carrier, since `versionPredicate` has no archetype alternative (§ Emit-side structural parity).

`openehr/aql` does not import the generated lexer (the dependency runs the other way), so these accept sets are hand-derived. Tests confront each with the parser over every token name in the vendored lexer, plus the spellings carried only in fragments, so a disagreement fails a test rather than waiting for review.

### The class predicate positions

`parse.ClassExpr.Predicate`, the bracket text that is neither an archetype HRID nor a `$param`, is spliced verbatim as the identifier positions are, and admits the same substitution: `Predicate: "a/b='c'] CONTAINS OBSERVATION o[d/e='f'"` emits a whole extra containment term that re-parses cleanly. One field feeds both `classExprOperand` alternatives, whose accept sets differ:

| Carrier | Grammar | Admits |
|---|---|---|
| a class | `pathPredicate` | `standardPredicate \| archetypePredicate \| nodePredicate` |
| a `VERSION` class | `versionPredicate` | `LATEST_VERSION \| ALL_VERSIONS \| standardPredicate` |

A write path **MUST** hold the field to the grammar of the position it renders, not to one accept set: validating it uniformly would both emit `VERSION v[at0001]`, which the parser rejects, and refuse `VERSION v[LATEST_VERSION]`, which the extractor produces. `aql.ValidatePathPredicate` and `aql.ValidateVersionPredicate` expose the two accept sets.

**The `VERSION` position is decided whole.** `versionPredicate` is a fixed three-way choice that does not recurse into the position, so its shape is decidable in one pass, and the guard **MUST** accept exactly that shape: one of the two keywords, matched case-insensitively once every trivia rule the lexer skips is removed (whitespace, a `--` comment, a `UNICODE_BOM` wherever it stands), or one `standardPredicate`, with exactly one top-level comparison operator (`<=` and `>=` count as one operator each) and a non-blank operand on each side. A top-level `AND`, `OR` or `MATCHES` is therefore refused here, where `versionPredicate` has no junction alternative, though the same text is lawful `nodePredicate` at a class; the keyword counts only as a whole word outside literals, comments and nested brackets, so `a/brand > 1` and `a/b_and_c = 1` are untouched. The operands are left to the parser: `objectPath` recurses (`pathPart : IDENTIFIER pathPredicate?` reaches `nodePredicate`, which reaches `objectPath`), and judging them would take the sub-grammar validator this requirement does not build. The position's shape is decided; its operands are not.

**The class position is guarded on bracket escape.** Emission writes `"[" + Predicate + "]"`, so the text can change the query's structure only by ending that bracket early. The guard **MUST** refuse exactly the text that escapes its bracket, and nothing else: a malformation that stays inside the bracket is the parser's to reject (`Emit` surfaces that verdict, § Emission verified after emission), while a conservative `nodePredicate` approximation would refuse predicates `ParseQuery` accepts, since a node predicate lawfully carries `AND`, `OR`, quotes and spaces. Escape is decided over the regions in which a bracket character is not a delimiter, each recognised as the lexer recognises its token:

- a string literal, `'…'` or `"…"`;
- a contained regex (`CONTAINED_REGEX`, whose body admits both brackets and the closing brace), matched as a whole token by the lexer's longest match, its optional `; 'label'` tail included, or not at all: `{/[0-9]+/}` and `{/a{2}/}` are content, and a `{` that completes no token is an ordinary character;
- a comment (`COMMENT` is skipped rather than channelled, so it survives into the text): `-- ` and a body running to a line break, or a bare `--` followed at once by a line break;
- a `TERM_CODE` display name, `|…|`, transparent to quotes, braces and dashes, so `at0001,SNOMED-CT::22298006|Barrett's oesophagus|` is ordinary clinical AQL;
- a balanced nested path predicate, as in `a[at0001]/b='c'`.

A region still open where the text ends escapes, because the end of the supplied text is not the end of the query and the region runs on through the emitted `]` into the clauses after it: an unterminated literal, an unclosed regex body and a `-- ` comment with no line break inside the text all escape. Balance holds in both directions: an unclosed `[` lets the emitted `]` close the inner bracket and the outer one close on whatever `]` follows. A bare `--` at the very end starts no comment, since the byte after it is the emitted `]` and not a line break, so `[a/b='c'--]` is a contained malformation while `[a/b='c'-- ]` is the substitution.

This accept set is a lexical condition, not a token, so it has no token names to walk. Tests confront a generated corpus with the parser at both bracket positions and in both directions (accepted text never re-parses as a different query; refused text is never text the parser reads back unchanged), splice it into bases with clauses and a line break after the bracket, and show each base able to fail; [PROBE-090](conformance.md#probe-090--aql-emission-round-trip-closure) carries that construction.

### Emit-side structural parity

`(*parse.Query).Emit` **MUST** refuse, with an error wrapping `aql.ErrInvalidQuery`, a tree the grammar cannot carry as written: a containment junction anywhere but at the end of its chain (the rule `Build()` holds, [§ REQ-163](#req-163--aql-write-side-expressivity-parity)); a class node with no RM type that is not a `VERSION` class expression, or with a child-join of its own; and a class expression carrying both an archetype and a standing predicate, the two mutually exclusive spellings of its one `[...]` position, where emitting whichever a switch reaches first drops the other, a row filter, and the query returns more rows than the AST asked for. The same dual-operand rule binds `aql.Comparison` (`Path` and `Left`) and `aql.MatchesExpr` (its three operand forms).

`Emit` **MUST** also refuse a tree carrying a content field it would not render, because a guard that passes a field the emitter then drops hides the loss: a `VERSION` class expression carrying an RM type other than `VERSION`, or an archetype predicate (the alternative has neither slot; `RMType: "VERSION"` beside the flag is accepted, since the extractor sets the two together); a `$param` archetype flag with no parameter; a non-zero FROM root beside a root junction; a blank standing predicate, which would emit `[   ]`; class data on a containment junction node, or a negation on the FROM-root junction or on a junction operand, where `NOT` has no spelling (negation on a chain child, `NOT CONTAINS`, stays legal); and a structured predicate comparison with no verbatim predicate text. `ClassExpr.HasPredicate` is exempt: it is a derived flag carrying no content, so no value of it adds or removes emitted text.

Completeness is checked before placement: the read side infers a node's kind from an absent RM type, so an incomplete class node checked the other way round would be reported as a misplaced junction the caller never wrote. The parity with `Build()` is deliberately not total: `aql.Builder` also requires an alias, which `classExprOperand` takes as optional, so requiring one in `Emit` would refuse valid AQL `ParseQuery` had just accepted. The extractor never builds a violating tree; these rules bind a consumer that assembles or rewrites an AST by hand.

### Emission verified after emission

Every rule above decides one position from the text handed to it, and that is not enough: a `CONTAINED_REGEX` body can complete a token inside the bracket text and still reach beyond it (`{/a\/}`), so which token the lexer forms depends on text the predicate does not contain. No per-position validator decides that, and refusing `{/a\/}` outright would refuse text `ParseQuery` reads back unchanged in every ordinary query.

`(*parse.Query).Emit`, and `aql.Builder.Build` for the projection list it renders, **MUST** read the emitted text back before returning it and refuse, with an error wrapping `aql.ErrInvalidQuery` (and `aql.ErrSyntax` as well where the parser refuses the text) and a diagnostic that follows § The emission closure property, text that does not re-parse or that re-parses as a different query. `Emit` reads the text back with the parser; `Build` reads its `SELECT` clause by the means [§ REQ-163](#req-163--aql-write-side-expressivity-parity) describes. A different query is one that adds or removes a class expression, a projection, a predicate leaf or a whole clause, or that changes a containment connective, a negation, or the grouping of containment operands across operators. A substitution confined to the text of one path position is outside the check, since REQ-055 rule 3 emits a path verbatim by contract.

`Emit` **MUST NOT** refuse text that re-parses as the same query by that definition, except a shape the skeleton below cannot model. `Emit`'s comparison runs over an encoding-independent skeleton of what it renders, not over field-by-field equality. It leaves out the read-side carriers a constructed AST does not populate, factors out the encodings the emitted text erases (same-operator junction nesting, one-term junctions, the bracketing of a containment chain, the two carriers of a comparison's path, edge whitespace on path text, a sole unaliased star item against the bare `SELECT *` flag), and keeps the structure the text carries, including each containment junction's operator at its coordinate. A shape the skeleton cannot model makes `Emit` refuse rather than compare equal to itself. The check costs one extra parse per `Emit`, a per-query call whose result goes on to a network round trip, and there is no unverified `Emit`. `Build()` verifies its projection list only, because the rest of the builder's vocabulary takes no free text: `aql.Containment` holds an RM type, an alias and an archetype id, its brackets render from typed comparisons, and `WHERE` arrives structured.

### Out of scope

- **Guarding path text against splices.** A path is emitted verbatim by REQ-055 rule 3's contract, so `aql.Exists("c/x AND c/y = 1")` emits text that re-parses as a junction rather than one `EXISTS`. Paths are developer-authored identifiers, and caller data goes through `aql.Param`, which is guarded. Guarding `aql.IdentifiedPath.Predicate` and `aql.PathSegment.Predicate` with the bracket-escape scan would be a scope change.
- **A full `nodePredicate` validator** at the class position. The guard decides bracket escape, which closes the silent class and refuses nothing `ParseQuery` accepts; a malformation inside the brackets (`[a b c]`) is left to the parser, and `Emit` surfaces its verdict.

### Acceptance

[PROBE-090](conformance.md#probe-090--aql-emission-round-trip-closure) checks that every value kind survives emit, parse and compare in every value position, on both carriers. The guards derived from the grammar are checked against the vendored grammar by tests that read their cases from it, or generate them where a position has no token names to walk, rather than against a list a maintainer has to remember to update. Every guard has a test that fails when the guard is removed, and the accept direction has rows of its own, one per encoding the emitted text erases, so an over-refusal fails as surely as a missed splice. String-literal closure is also fuzzed.

## REQ-160 — AQL containment admissibility relation

The SDK **MUST** ship a building-block relation that answers, for two AQL class expressions, whether a containment route under the pinned openEHR Reference Model connects them (§ Verdicts: route existence, not a claim of RM truth), so that the lint (REQ-161), the builder's verification ([§ REQ-161 § Builder adapter](#builder-adapter)) and future consumers judge `FROM … CONTAINS …` shapes from one shared RM-derived relation instead of each guessing. Architecture: [ADR 0017](../adr/0017-aql-semantic-layer.md).

Motivation: almost any `X CONTAINS Y` parses, but only RM-nestable pairs can ever match data. Engines commonly accept the rest and return zero rows (EHRbase, for example, validates containment at storage-root granularity, as observed), so an empty result set cannot be told apart from an impossible query. Whether the specification requires an engine to *reject* an RM-impossible containment is an open specification gap; this relation is the SDK's documented position on it, not enforcement of existing spec text.

### Nil and zero relations

**A nil relation is the default relation, on the receiver too.** Every seam that *takes* a relation reads nil as the default ([REQ-161 § Relation supply](#relation-supply) states that half, for the entry points that run the semantic group). The relation's own **methods MUST read a nil receiver the same way**, returning what the default relation would return rather than dereferencing it: nil is caller-constructible and documented, so panicking on it is what [idiom.md § No panics](idiom.md#errors-req-025) forbids, and a nil that means "the default" when passed but panics when used would be one spelling with two meanings. This holds for the extension method as much as for the verdict methods: a consumer that conditionally extends a relation it might not hold (`var rel *TypeRelation; …; rel = rel.WithOverlay(e)`) writes the shape the nil convention invites. A nil relation is therefore **not** the *zero* relation: the zero value is a real relation that knows no classes and answers UnknownClass for every one (§ Verdicts), a different answer rather than the same one reached differently.

### Verdicts

The relation answers two questions — **operand containability** (may this class be a `CONTAINS` operand at all?) and **pair admissibility** (does a containment route connect this ancestor/descendant pair?) — each yielding exactly one verdict from the table below; **ByReference** arises only on the pair question.

Beside the two verdict questions the relation answers one reachability query that yields no verdict: `Unavoidable(anc, via, desc)` reports whether every containment route from `anc` to `desc` passes through `via`. It is computed over the same overlaid graph as the verdicts, so a consumer overlay changes its answer, and like every other method it reads a nil receiver as the default relation. Its consumer is [REQ-164](#req-164--aql-path-shape-and-paging-lint)'s `aql_contains_redundant_step`.

**Admissible is route-existence, not a claim of RM truth.** A verdict is derived from the pinned BMM's by-value graph plus the overlay edges; on the RM-faithful subgraph an Admissible verdict *is* genuine RM nesting, but where the default relation is deliberately loose (the family-agnostic `VERSION` hub, § Overlay edges) it **MAY** report Admissible for a pair that cannot actually nest. That looseness is a documented missed defect, never a false Error (§ REQ-161 § Flagging policy); consumers needing RM-exact verdicts use a stricter profile once one ships (§ Out of scope).

| Verdict | Meaning |
|---|---|
| **Admissible** | Pair: a route (by-value or overlay) connects the pair using only non-reference edges. Operand: a legal `CONTAINS` operand. |
| **Never** | Pair: no route connects the pair — a `CONTAINS` over it is always empty, and a `NOT CONTAINS` over it is trivially true. Operand: not a containment target at all. |
| **ByReference** | The pair is resolvable only through a reference hop that some engines implement as containment; portable behaviour is not guaranteed. |
| **UnknownClass** | The class is not one the relation knows (pinned BMM + overlays). Unknown is **not** wrong: future RM releases, demographic deployments, and dialects are legitimate sources of unknown names. |

The pair question is total: it answers for **every** ordered operand pair. The pair verdict **MUST** be UnknownClass when either operand is UnknownClass, and otherwise Never when either operand's containability is Never; REQ-161 reports such operands once, through the operand-level codes, and suppresses the pair codes. Neither short-circuit can pre-empt an overlay edge: every class an overlay edge of the relation in use names is thereby a known, containable class of that relation (§ Containable operands, § Extensibility).

### Reachability semantics

- `CONTAINS` admissibility **MUST** be **descendant-at-any-depth reachability** over the RM's by-value composition graph, derived from the pinned BMM through `openehr/rm/rminfo` (REQ-048). `COMPOSITION CONTAINS ELEMENT` is Admissible even though levels are skipped: level-skipping is the QUERY specification's own worked-example behaviour (its `COMPOSITION c CONTAINS OBSERVATION o` matches observations nested under `SECTION`s, against prose that reads the left operand as the direct "parent object") and the engine consensus, the depth question being part of the open containment gap; a direct-child rule would flag valid queries.
- The derivation crosses non-LOCATABLE by-value classes (e.g. `EVENT_CONTEXT` on the way from `COMPOSITION` to `ITEM_STRUCTURE`) while collecting only containable classes, and a reference-typed attribute (`OBJECT_REF` and its descendants) ends structural reachability: reference hops are overlay data, never derived.
- An attribute whose declaring class (`rminfo` `DeclaredOn`) is `LOCATABLE` or `PATHABLE` **MUST NOT** be a containment edge: AQL `CONTAINS` navigates archetyped content, not audit or reference metadata. The exclusion is read from the declaration site, not from a list of attribute names, so it covers a housekeeping attribute a later pin declares and spares a content attribute that happens to share a name. On the current pin it resolves to the six `LOCATABLE` housekeeping attributes (`name`, `uid`, `links`, `feeder_audit`, `archetype_details`, `archetype_node_id`) and to no `PATHABLE` property (the pin's `parent` back-reference is a BMM function, not an attribute). Without the exclusion an `ELEMENT` would reach `CLUSTER` through `LOCATABLE.feeder_audit` (a `FEEDER_AUDIT`) → `originating_system_audit` (a `FEEDER_AUDIT_DETAILS`) → `other_details` (an `ITEM_STRUCTURE`), a by-value path the RM permits but AQL containment does not, which is why `ELEMENT CONTAINS CLUSTER` is **Never** (§ Acceptance).
- **Abstract classes stand for their concrete kinds, on both operands:** a pair **MUST** be Admissible when *any* concrete-descendant combination is (`rminfo` `ConformsTo` / `ConcreteDescendants`). `ENTRY CONTAINS CLUSTER` is Admissible because a concrete entry admits it.
- **ByReference closes over routes, not edges:** a *route* is any edge sequence connecting the pair in the closure, derived and overlay edges alike. The pair verdict **MUST** be Admissible when at least one route crosses no ByReference edge, ByReference when routes exist but every one crosses at least one ByReference edge, and Never when no route connects the pair. `FOLDER CONTAINS OBSERVATION` is therefore ByReference: every route crosses one of `FOLDER`'s reference hops (§ Overlay edges).
- Class-name matching **MUST** be ASCII-case-insensitive against the BMM's canonical spelling (engines and the EHRbase SDK round-trip lower-case class spellings; a case mismatch is not a semantic difference).
- Verdicts are derived at run time from the pinned BMM and may be memoized; the relation needs no code generation and no network access.

### Containable operands

A class **MUST** be a legal `CONTAINS` operand exactly when it **conforms to** one of `LOCATABLE`, `VERSIONED_OBJECT`, or `VERSION` (conformance, not name equality, so every `VERSIONED_*` container the pin ships, `VERSIONED_FOLDER` and `VERSIONED_PARTY` included, and the concrete `ORIGINAL_VERSION` / `IMPORTED_VERSION` are containable), or is `EHR` (the non-LOCATABLE root), **or is named as an endpoint of an overlay edge of the relation in use**: naming a class in an edge makes it a known, containable class of that relation (§ Extensibility). A data value (`DV_*`) or another known class outside that set therefore has containability **Never**: values are read through paths, not bound by `CONTAINS`. Demographic classes are containable exactly when the pinned BMM declares them; their presence is a property of the pin, not of this contract.

**An engine that binds a class outside this set does so by an engine extension.** EHRbase, for example, answers `COMPOSITION c CONTAINS EVENT_CONTEXT ec`, although `EVENT_CONTEXT` conforms only to `PATHABLE` and is reached by value through `COMPOSITION.context`. The default relation still answers Never for such a class: an engine extension is not an RM containment, and the compatibility guard (§ Overlay edges) does not reach it. A deployment that relies on the extension **MAY** declare it as a consumer overlay edge (`COMPOSITION` → `EVENT_CONTEXT`, § Extensibility), which makes the class containable for that relation only.

### Overlay edges (default relation)

The default relation **MUST** carry the overlay edges below, the facts the BMM cannot express, each with its citation and each conformance-aware on both endpoints like any derived edge: an edge naming `VERSIONED_OBJECT` covers every class conforming to it. They take part in the same reachability closure as the derived edges.

| Edge | Verdict contribution | Basis |
|---|---|---|
| `EHR` → `COMPOSITION`, `EHR_STATUS`, `FOLDER`, `EHR_ACCESS`, **and those four payload families' `VERSIONED_*` and `VERSION` tier** | Admissible | RM EHR IM: the EHR references its versioned objects — ehr_access, ehr_status, directory (folders) and compositions — so those four families are `EHR`'s **direct** overlay endpoints; the EHR IM versions no parties, so the demographic family is not a direct endpoint (a deployment that wants demographic containment adds a consumer edge, § Extensibility). Onward reachability through the shared, family-agnostic `VERSION` node may still resolve a hub-mediated cross-family route Admissible — deliberate, bounded looseness, never a false Error (§ Overlay edges, the family-agnostic note). `FROM EHR e CONTAINS …` is the specification's own canonical example shape and consensus engine behaviour. |
| For each **payload family** X in {`COMPOSITION`, `EHR_STATUS`, `EHR_ACCESS`, `FOLDER`, `PARTY`} — the payload classes of the concrete `VERSIONED_*` containers the pinned BMM ships — the pair of edges `VERSIONED_X` → `VERSION` and `VERSION` → `X` | Admissible | Version-tier mechanics are RM facts for every pin-shipped container (RM common IM version tier; the EHR IM's versioned objects; `VERSIONED_PARTY` is the demographic IM's, shipped by the pin), and the QUERY grammar admits the operands while CDR practice resolves them. `VERSION.data` is generic — in the pinned tables `ORIGINAL_VERSION.data` is literally typed `T`, and [REQ-048](bmm-conformance.md#req-048--rm-meta-model-introspection-surface) leaves generic-parameter resolution out of scope — so the payload pairing is **cited overlay data reviewed on a BMM pin bump** ([ADR 0001](../adr/0001-bmm-version-bump-runbook.md) drift triage), not derivable from `rminfo`. |
| `FOLDER` → `COMPOSITION` | **ByReference** | `FOLDER.items: List<OBJECT_REF>`; engines that support it resolve the reference hop — engine-specific, verify before use. (`FOLDER → FOLDER` is by-value and needs no overlay.) |
| `FOLDER` → `VERSIONED_COMPOSITION` | **ByReference** | RM Common IM, directory package: a folder's items are "references to other (usually versioned) objects", `VERSIONED_COMPOSITION` its worked example. The hop lands on the version tier, so `FOLDER CONTAINS VERSION` and `FOLDER CONTAINS VERSIONED_COMPOSITION` resolve **ByReference** through the version-tier edges above, as the `FOLDER → COMPOSITION` shorthand above does for the payload. Onward through the family-agnostic `VERSION` node every other payload family resolves ByReference from `FOLDER` too, and a version-tier class reaches `VERSIONED_COMPOSITION` through a folder version's `FOLDER`: `VERSIONED_FOLDER CONTAINS VERSIONED_COMPOSITION` is a real reference chain, `VERSIONED_PARTY CONTAINS VERSIONED_COMPOSITION` a cross-family over-admission — the same bounded looseness as the hub's, never a false Error. |

The `VERSION` node is **family-agnostic** in the default relation. Because `VERSION.data` is generic (one RM class for every payload), a bare `VERSION` or `VERSIONED_OBJECT` operand stands for any payload family (abstract expansion, § Reachability semantics), and the shared node carries no payload-family state along a route. The relation therefore **MAY** over-admit a rare cross-family version-tier pair rather than assert an impossibility it cannot cheaply prove: because the shared node offers a plain (non-reference) exit to *any* payload family, a route with no ByReference edge exists, and the route-closure rule (§ Reachability semantics) yields **Admissible** for both `VERSIONED_FOLDER CONTAINS COMPOSITION` (route `VERSIONED_FOLDER → VERSION → COMPOSITION`) and a hub-mediated `EHR … PARTY` pair. This looseness is deliberate and bounded: it is a *missed defect*, never a false Error ([§ REQ-161 § Flagging policy](#flagging-policy)), and it never contradicts the EHRbase-compatibility guard below. What waits for its own requirement is a **family-precise** profile that would refuse these pairs, and shipped demographic containment edges (§ Out of scope, § Extensibility). The version-tier overlay set is pin-reviewed data that follows the pin: a test fails when the family enumeration and `ConcreteDescendants("VERSIONED_OBJECT")` diverge, so a pin that adds a versioned container fails until its family edges are carried, and the `VERSIONED_<CLASS>` naming convention that test uses to pair a container with its payload class is never used in the relation.

Under the default relation nothing contains `EHR`: a pair with `EHR` as the descendant **MUST** verdict Never, and no reference hop beyond the table above is admitted. The default relation expresses the openEHR RM and specifications only, never one vendor's storage model: **an RM-valid pair that a conformant engine (EHRbase among them) admits MUST NOT verdict Never.** An engine admits a pair when it answers the query with the rows the pair selects. A pair an engine accepts but answers with no rows is consistent with Never (the motivation above), and a class an engine binds by an engine extension is outside this guard (§ Containable operands).

### Archetype/class conformance

For a class expression carrying a literal archetype predicate, the HRID's type segment (`openEHR-<pkg>-<TYPE>.<concept>.vN`) **MUST** conform to the declared class (ConformsTo, case-insensitive): `ENTRY o[openEHR-EHR-OBSERVATION.…]` conforms; `EVALUATION o[openEHR-EHR-OBSERVATION.…]` does not. The HRID is decomposed by [REQ-120](rm-functions.md#req-120--rm-identifier-parsing-and-derivation)'s canonical parser, `rm.ParseArchetypeID`, with no second lexical logic here. HRID token shape is grammar-guaranteed on parsed input; an unparseable HRID reaching the relation directly, or a declared class or type segment the relation does not know, **MUST** yield **UnknownClass**, never a false mismatch: a mismatch is only ever asserted between two known classes.

### Extensibility

An overlay edge, default and consumer alike, is a record of two class-name endpoints (`From`, `To`) and a by-reference marker: a plain edge contributes **Admissible** to routes through it, a marked edge contributes **ByReference** (§ Reachability semantics, the ByReference closure). Consumers **MUST** be able to extend the relation with their own overlay edges without forking it, as an immutable copy (matching the `Containment` algebra's style) that leaves the default relation unaltered. A consumer edge **MUST** be honoured as written, whether or not its endpoints are BMM-known, which is what lets a dialect deployment (e.g. demographic containment) verify its own queries without false findings: a BMM-known endpoint matches by conformance (like any derived edge, § Overlay edges: `WithOverlay(VERSIONED_OBJECT → PERSON)` covers every `VERSIONED_*`), an endpoint the pin does not know matches by exact name, the endpoints become known, containable classes of the extended relation (§ Containable operands), and a pair a consumer edge names takes that edge's verdict, since the UnknownClass / Never short-circuit (§ Verdicts) applies only to classes no edge of the relation names.

## REQ-161 — AQL semantic and portability lint

REQ-109's Layer 2 **MUST** carry two additive check groups: **semantic checks** backed by the REQ-160 relation (RM-impossible shapes a CDR will typically accept and answer with zero rows), and **portability checks** for behaviours the QUERY specification leaves open (each citing the open specification question or community source where one exists). The layer contract is preserved: AST walk, collect-all, no CDR, no OPT; the relation is derived in-process from the pinned BMM.

### Checks

| Check | Code | Severity | Rule |
|---|---|---|---|
| Impossible containment | `aql_impossible_containment` | Error | An adjacent FROM/CONTAINS pair of containable operands whose REQ-160 **pair verdict** is **Never** **MUST** raise this code — including junction operands (checked against the junction's enclosing parent) and `NOT CONTAINS` pairs (the exclusion is trivially true: a dead constraint is equally a defect). |
| Non-containable target | `aql_contains_not_containable` | Error | A `CONTAINS` operand whose REQ-160 **containability verdict** is **Never** — a known class that is not a containment target, e.g. a `DV_*` type — **MUST** raise this code. |
| Archetype/class mismatch | `aql_archetype_class_mismatch` | Error | A literal archetype predicate whose HRID type segment does not conform to the declared class (REQ-160 § Archetype/class conformance) **MUST** raise this code. `$param` archetype predicates are skipped — the CDR resolves the bound scope at execution (PROBE-021), the same skip REQ-109 Layer 3 applies. |
| Unknown RM class | `aql_unknown_rm_class` | Warning | A class token whose REQ-160 verdict is **UnknownClass**, **or** a literal archetype predicate whose HRID type segment is not a class the relation knows (`ArchetypeMatches` → **UnknownClass**, REQ-160 § Archetype/class conformance), **MUST** raise this code, once per class-expression occurrence — Warning, because unknown is not wrong (future RM, demographic deployments, dialects). This is the code that fires when `aql_archetype_class_mismatch` is suppressed for an unknown type segment, so an unknown name is never silent. |
| Containment by reference | `aql_containment_by_reference` | Warning | A pair whose REQ-160 pair verdict is **ByReference** **MUST** raise this code — Warning, because the hop is engine-specific: verify against the target CDR. |
| `VERSION` without predicate | `aql_version_no_predicate` | Warning | A `VERSION` class expression carrying no version predicate **MUST** raise this code: the default is unspecified ([SPECPR-481](https://openehr.atlassian.net/browse/SPECPR-481)), so portable queries **SHOULD** state `[LATEST_VERSION]` / `[ALL_VERSIONS]` explicitly. |
| Unreferenced `VERSIONED_OBJECT` | `aql_versioned_object_unreferenced` | Warning | An operand **MUST** raise this code exactly when its class conforms to `VERSIONED_OBJECT` (REQ-160 § Containable operands: conformance, not a name list), it carries **no class-position predicate** of its own, and its alias roots no identified path outside FROM/CONTAINS: the step is redundant unless container-level attributes are read ([Discourse #14186](https://discourse.openehr.org/t/aql-versionedobject-grammar/14186)). A **class-position predicate** is any bracket the operand carries in class position, a standing predicate or an archetype predicate, and any one of them suppresses the code, because each selects the container and so is itself a container-level attribute read. The motivating shape is `… CONTAINS VERSIONED_COMPOSITION vo[uid/value=$vo] CONTAINS VERSION v[ALL_VERSIONS]`, the canonical *all versions of one composition* query, where the step does work although no identified path names its alias. A class-position predicate is not an identified path, so "outside FROM/CONTAINS" answers *referenced*, never *redundant*. |
| Engine-defined row grain | `aql_fanout_row_grain` | Warning | **MUST** fire exactly when an `AND` containment junction that no inherited negation covers has two or more **projected** aliases among its class-expression **leaves**: the class expressions reached by flattening nested `AND` junctions, descending into neither an `OR` junction nor a negated node. An alias is **projected** when it roots at least one SELECT column, **or** when the projection carries a `*` item in any form (bare `SELECT *`, mixed `SELECT *, col`): a star projects **every** alias bound in FROM/CONTAINS, because the engine returns a column per alias, and a star roots no identified path, so a SELECT-column-only reading would exempt the shape where the question is most live. Negation is inherited downward and alternation is not: a `NOT CONTAINS` at any depth above an `AND` junction, including through an intervening un-negated `OR`, covers it, because a `NOT CONTAINS` collapses to a boolean filter on the parent row and multiplies nothing inside its excluded subtree, while an un-negated `AND` nested under an un-negated `OR` is covered by nothing and fires. So the code stays silent on an `AND` junction with one projected alias, on an `OR` junction with two (under named columns and under `SELECT *` alike, since alternation selects rows and does not multiply them), on `NOT CONTAINS (A AND B)`, and on `NOT CONTAINS (B OR (D AND E))`. Possibility is sign-blind and row multiplicity is not, which is why `aql_impossible_containment` checks a `NOT CONTAINS` pair and this code does not. `Detail` states that row multiplicity for this shape is engine-defined (result-shape semantics are an open specification question, SPECQUERY-9). This code covers the **junction** source of engine-defined row multiplicity; the **path** source, two projected paths on one alias descending through different repeating scopes, is `aql_fanout_path_grain` ([§ REQ-164](#req-164--aql-path-shape-and-paging-lint)). |

An operand whose verdict is **UnknownClass** or whose containability is **Never** **MUST** suppress the pair checks (`aql_impossible_containment`, `aql_containment_by_reference`) for every pair it participates in. An archetype predicate whose declared class or HRID type segment is UnknownClass raises no `aql_archetype_class_mismatch`, since the class expression already carries `aql_unknown_rm_class` through the class-token or the type-segment arm, and REQ-160 § Archetype/class conformance yields no mismatch on an unknown name: one finding per defect, and no Error built on an unknown name.

`aql_contains_not_containable` is scoped to a `CONTAINS` operand, not to the FROM root. A **FROM root** whose REQ-160 containability verdict is Never (`FROM DV_TEXT t …`) **MUST** raise no containability code, in the single-root or the root-junction spelling: the catalogue above authorises that code for a `CONTAINS` operand only. The boundary binds that one code, not the root generally: a root's archetype predicate is checked by `aql_archetype_class_mismatch` exactly as a `CONTAINS` operand's would be, because that check is orthogonal to operand role, and an *unknown* root still raises `aql_unknown_rm_class` (unknown is not wrong).

The SDK adjudicates **no row semantics**: it does not deduplicate, reason about expected row counts, or refuse a row shape. The two fan-out advisories, `aql_fanout_row_grain` above and `aql_fanout_path_grain` in [§ REQ-164](#req-164--aql-path-shape-and-paging-lint), are the entire footprint.

### Flagging policy

The semantic checks are **conservative**: a false **Error** is worse than a missed defect, so the layer flags only what the pinned BMM and overlays prove. An **Error** code (`aql_impossible_containment`, `aql_contains_not_containable`, `aql_archetype_class_mismatch`) **MUST** fire only on a verdict the relation proves, so where the relation is deliberately loose (the family-agnostic `VERSION` hub, REQ-160 § Overlay edges) the layer raises no Error the relation does not support. An unknown name is **not** an error: it **MUST** surface as the `aql_unknown_rm_class` **Warning**, never as silence and never as an Error. This policy is the canonical home of the rule that uncertainty stays out of Error, which ADR 0017 cites.

### Relation supply

`lint.Options` **MUST** carry a nilable relation field, typed `*contain.TypeRelation` (the relation is over RM **type names**, and the type says so); nil uses the REQ-160 default relation. A caller with dialect overlay edges (REQ-160 § Extensibility) lints without false findings. Because adding a field breaks positional struct literals ([idiom.md § Public-API stability](idiom.md#public-api-stability)), callers **SHOULD** construct `lint.Options` field by name.

Every entry point that runs the REQ-161 group **MUST** offer this supply, or the escape hatch reaches only the callers who bypass the seams: the read side through `lint.Options`, the write side through `(*aql.Builder).VerifyContainment` (§ Builder adapter), and the validation seam through `validation.ValidateAQLWithTypeRelation` (REQ-109 § Issue model and entry points), whose no-relation form `ValidateAQL(q, c)` **MUST** be exactly the nil call. A relation is supplied, never gated: nil **MUST** select the REQ-160 default at every one of them, and never switches the group off.

A supplied relation governs the containment questions only: the five containment codes above and [§ REQ-164](#req-164--aql-path-shape-and-paging-lint)'s `aql_contains_redundant_step`. An overlay **MUST NOT** retire a Layer-1 syntax finding, a Layer-2 shape or parameter-binding finding ([§ REQ-109 § Layer 2](#layer-2--shape-ast-walk-no-cdr)), or a Layer-3 template finding. A portability finding and the other path-shape findings are out of its reach as well, because their checks put no question to the relation: the three portability advisories consult none, and `aql_versioned_object_unreferenced` reads `VERSIONED_OBJECT` conformance from the pinned BMM directly, a class fact no supplied relation answers differently. The scope is by code, not by layer: the containment codes are themselves Layer 2 (REQ-109 § Layer 2).

### Additivity

The codes reuse the REQ-109 issue model verbatim: `Code` / `Severity` / `Span` value-free, `Detail` / `Path` value-bearing ([§ REQ-109 § Value-free lint diagnostics](#value-free-lint-diagnostics)), with `Span` on the offending class expression or path. A check group added to Layer 2 changes no existing code, severity, `Detail` text or `Result.OK()` semantic. It re-baselines [PROBE-028](conformance.md#probe-028--aql-lint-stability)'s corpus only where a corpus query genuinely carries a newly checked defect, as a deliberate re-baseline recorded in the probe's catalogue entry; a query carrying no such defect keeps its issue-code multiset unchanged ([PROBE-097](conformance.md#probe-097--aql-semantic-and-portability-lint-corpus)'s additivity guard holds this for the codes above). A query the new checks legitimately flag, e.g. `OBSERVATION CONTAINS COMPOSITION`, gains its code; that is the feature, not an additivity breach.

### Builder adapter

The write side **MUST** offer the same semantic judgement as the read side, opt-in: `(*aql.Builder).VerifyContainment` walks the builder's own FROM root and containment algebra (junctions and `NOT CONTAINS` included), with no emission and no re-parse, and reports the containment findings of the catalogue above (`aql_impossible_containment`, `aql_contains_not_containable`, `aql_archetype_class_mismatch`, `aql_unknown_rm_class`, `aql_containment_by_reference`). It takes a nilable REQ-160 relation (nil is the default, § Relation supply), and each code's severity and firing rule are the catalogue's; this section adds none.

- A finding **MUST** carry exactly a value-free `Code` and a value-bearing `Detail` (which may quote class names and HRIDs), mirroring the REQ-109 field classification, and no `Span`, `Path` or severity field: a builder tree has no source text to point into, and severity is looked up per code in the catalogue.
- Verification **MUST** stay opt-in: `Build()` never runs it, so a query carrying a Never pair still builds.
- **Read/write parity:** for a query expressible through the builder, the verification's code multiset **MUST** equal the containment-check subset of `lint.LintString` over the emitted text: one rule engine shared by both adapters, so they cannot drift.

### Out of scope

Engine-capability findings (valid AQL a particular engine does not implement) are a deferred per-engine-profile concern; terminology, function signatures, and `ORDER BY` type checking remain out of scope as in REQ-109.

Widening `aql_contains_not_containable` to the FROM-root anchor position is also out of scope (§ Checks): the catalogue scopes that code to a `CONTAINS` operand, and a root-position finding would need its own catalogue row, severity and span rule rather than a re-pointed existing code.

- **Probes:** [PROBE-097](conformance.md#probe-097--aql-semantic-and-portability-lint-corpus) (its read/write parity arm included); PROBE-028 re-baseline where applicable

## REQ-163 — AQL write-side expressivity parity

The write side of `openehr/aql` **MUST** be able to construct the vocabularies its own read side already models at the class, projection and row-bound positions: the **containment algebra** (negated containment and sibling junctions) and **in-text paging**, the deprecated **`TOP`** clause, the **version predicate** on a `VERSION` class expression, the **standing comparison** in class position, and the **typed projection** (`DISTINCT`, `AS`, aggregate and function calls, literal items). Each is already parsed, structured and re-emitted by [§ REQ-113](#req-113--execution-oriented-parsed-aql-ast)'s AST, so what this requirement adds is the carriers, their guards, and the canonical spellings that make the mirror byte-exact, not a new model.

Without these carriers a caller who needs one of the constructs abandons the typed builder for a hand-assembled string, the one construction route [§ REQ-055](wire.md#req-055--wire-boundary)'s injection guard cannot cover. Two shapes the SDK itself recommends depend on them: the explicit version predicate `aql_version_no_predicate` asks for ([§ REQ-161 § Checks](#checks), [SPECPR-481](https://openehr.atlassian.net/browse/SPECPR-481)), and REQ-161's suppression shape `… CONTAINS VERSIONED_COMPOSITION vo[uid/value=$vo] CONTAINS VERSION v[ALL_VERSIONS]`.

Every rule below is derived from the vendored grammar profile (`resources/aql/grammar/active/`, [ADR 0007](../adr/0007-aql-antlr-grammar-profile.md)), which stays the authority.

### Containment algebra and in-text paging

The builder expresses three forms the parse side models:

- **Negated containment**: `CONTAINS … NOT CONTAINS …`, per the grammar's `classExprOperand (NOT? CONTAINS containsExpr)?`.
- **Sibling containment junctions**: `AND` / `OR` over containment operands, parenthesised only where nesting departs from the default precedence (`NOT` binds tightest, then `AND`, then `OR`, mirroring the parse profile).
- **In-text `LIMIT n [OFFSET m]`**, as an explicit opt-in, so a bound survives stored-query registration; envelope paging (`Query.Fetch` / `Query.Offset`) stays the default.

The grammar takes a parenthesised group as a whole `containsExpr` alternative (`classExprOperand (NOT? CONTAINS containsExpr)? | '(' containsExpr ')'`), so no `CONTAINS` keyword may follow a containment junction, and deeper nesting is written inside the junction's operands. `Build()` **MUST** refuse, with an error wrapping `aql.ErrInvalidQuery`, a junction placed anywhere but at the end of its chain, whether through `Containment.Contains` / `Containment.NotContains` or across repeated `Builder.Contains` / `Builder.NotContains` calls, which emit as one chain, and never re-shape the emission to make the placement expressible: distributing the chain tail under the junction's operands changes what the query asks.

### The `TOP` clause and the row-bound channels

`aql.Builder` constructs the deprecated `SELECT TOP n [FORWARD|BACKWARD]` in its plain and directed forms, so a consumer can author the shape for a corpus, a migration or a round-trip fixture without hand-assembling AQL text. The vocabulary is the shared `aql.TopClause` ([§ REQ-113 § The `TOP` carrier](#req-113--execution-oriented-parsed-aql-ast)), and its godoc states the upstream deprecation and names the in-text `LIMIT` with `ORDER BY` as the replacement.

- A negative `TOP` count **MUST** fail `Build()` with an error wrapping `aql.ErrInvalidQuery`: the profile's `top` production admits no sign, so a negative count could only emit text the parser rejects.
- A query has three row-bound channels: in-text `LIMIT` / `OFFSET`, the request envelope (`Query.Fetch` / `Query.Offset`), and `TOP`, itself an in-text row bound. `Build()` **MUST** refuse a query that sets more than one, with an error wrapping `aql.ErrInvalidQuery`, rather than combine them silently; QUERY Release-1.1.0 § 4.4.3 additionally forbids `TOP` beside `LIMIT`.

### The version-predicate carrier

`versionPredicate : LATEST_VERSION | ALL_VERSIONS | standardPredicate`. The write side **MUST** carry that position as a **sealed sum** in `openehr/aql`, in the package's existing `aql.Value` / `parse.SelectExpr` style (an unexported marker method), with **exactly three** shapes: the two keywords, and one `standardPredicate` comparison carrying `aql.Comparison` rather than a second, structurally identical vocabulary. The production is a fixed three-way choice that does not recurse into its own position, the property [§ REQ-119 § The class predicate positions](#req-119--re-parseable-canonical-aql-emission) relies on to decide the position in one pass; a fourth shape would be a grammar change, not an extension.

The predicate reaches a class expression through a **`VERSION`-fixed constructor** (`aql.Version(alias, pred)`), so the RM type at that position is the SDK's spelling and never a caller string. Absence stays legal: a `VERSION` class with no predicate **MUST** stay buildable, since REQ-161 advises on it with a Warning and does not refuse it.

- The rendered bracket text **MUST** be held to `aql.ValidateVersionPredicate`, the guard `(*parse.Query).Emit` applies at this position, so `Build` and `Emit` accept the same brackets.
- A version predicate on a class node **not** spelled `VERSION` **MUST** be refused: the grammar reaches `versionPredicate` from the `VERSION` alternative of `classExprOperand` alone.
- An **archetype** predicate on a `VERSION` node stays refused: the `VERSION` alternative has no archetype slot at all (§ REQ-119 § Single-token identifier positions states the same rule for the read-side carrier).

The combinators return a `Containment` rather than an error, so a misuse **MUST** be carried on the node and surfaced at `Build()` as an error wrapping `aql.ErrInvalidQuery`, the route the containment algebra already uses, never absorbed into a shape that means something else.

### The standing-predicate carrier

`pathPredicate : '[' (standardPredicate | archetypePredicate | nodePredicate) ']'`. The write side **MUST** carry a class-position standing predicate spelling the **`standardPredicate`** alternative, `objectPath COMPARISON_OPERATOR pathPredicateOperand`: **exactly one comparison**, never a junction, since that production has no junction alternative of its own. The bound belongs to the **carrier**, not to the position: the bracket's third alternative, `nodePredicate`, is defined over `AND` / `OR`, so a junction class predicate is legal AQL that no builder carrier spells (§ Out of scope).

The comparison **MUST** be the `aql.Comparison` shape, so that a `WHERE` comparison, the parsed class predicate (`parse.ClassExpr.PredicateComparison`) and the built class predicate share **one** comparison model. The left-hand path is relative (it binds no FROM alias), and the value renders through § REQ-119 § Canonical value spellings.

Four refusals bind, and each **MUST** wrap `aql.ErrInvalidQuery`:

- a **junction** receiver: a junction node carries no class of its own, so it has no bracket position (the content-free reasoning § REQ-119 § Emit-side structural parity applies to `parse.Containment`);
- a node that **already carries an archetype predicate**: archetype and standing are the two mutually exclusive spellings of the one `[...]` position, and emitting whichever a switch reaches first drops the other, a row filter, so the query returns more rows than the caller asked for (the dual-operand rule § REQ-119 binds `aql.Comparison`, `aql.MatchesExpr` and `parse.ClassExpr` with);
- a node that **already carries a standing predicate**: one bracket renders one predicate, and `standardPredicate` has no conjunction to carry a second, so the first comparison would be dropped. Two conditions on one node belong in `WHERE`, or, under `NOT CONTAINS`, where the node's alias binds no result row, in a restructured term;
- a **`VERSION`-spelled node**, routed as below.

The rendered bracket text **MUST** be held to `aql.ValidatePathPredicate`, the guard the position already has.

### One carrier per grammar position

`versionPredicate` admits `standardPredicate`, so a comparison **on a `VERSION` node is legal AQL** and **MUST** be expressible, through the version-predicate carrier's comparison shape (`aql.VersionCompare`) alone: the standing-predicate carrier applied to a `VERSION`-spelled node **MUST** be refused with an error wrapping `aql.ErrInvalidQuery` that names `aql.VersionCompare`, the constructor which does carry it. The two accept sets differ in both directions, `versionPredicate` carrying no node predicate and `pathPredicate` no `LATEST_VERSION`, so routing a class-position call to the version position silently would change the caller's accept set with no diagnostic (§ REQ-119 § The class predicate positions); refusing instead is loud and named.

Both spelling tests, this routing refusal and the version carrier's refusal of a node not spelled `VERSION`, **MUST** match the RM type ASCII-case-insensitively, so each accept set is exactly the spellings the lexer reads as the keyword: `VERſION` (U+017F, Unicode-fold-equal to the keyword and unreadable to the lexer) is an ordinary class, and a Unicode fold would either answer a class-position call on it by naming a constructor that fixes the RM type to `VERSION`, or carry a `versionPredicate` bracket onto a node the lexer reads as an ordinary class. In this carrier the spelling *is* the carrier: the builder's class model has no `Version` flag beside it, which is why `RMType: "VERSION"` is accepted here and refused on an unflagged `parse.ClassExpr` (§ REQ-119 § Single-token identifier positions).

### The typed projection model

`parse.SelectClause` is the **reference shape**, and the write side **MUST** mirror it rather than grow a second projection vocabulary: a clause-level `Distinct` flag and star form, an ordered item list, and per item an expression plus an optional `AS` alias, over a sealed expression vocabulary of a path, a function or aggregate call (name, arguments, `DISTINCT` and star flags), a literal, and a star item. `columnExpr : identifiedPath | primitive | aggregateFunctionCall | functionCall`, and as on the read side one call type models both call productions, so a shape rule written once binds both carriers.

The rules that already govern a projected item bind the builder unchanged ([§ REQ-119 § Canonical value spellings](#req-119--re-parseable-canonical-aql-emission)): `aql.ValidateSelectFuncName` holds the projected name (the aggregates are admissible in `SELECT` and in no value position); `COUNT` takes `DISTINCT? identifiedPath` or a bare `*` and never a star beside arguments; `MIN` / `MAX` / `SUM` / `AVG` take exactly one identified path; no other projected call carries `DISTINCT` or a star; `TERMINOLOGY` keeps its fixed arity and argument type; a bare parameter is **not** a projection while a parameter inside a projected call's arguments is; and an `AS` alias is a single-token identifier position held to `aql.ValidateIdentifier`.

`Build()` **MUST** refuse, with an error wrapping `aql.ErrInvalidQuery`, a typed construction the grammar does not admit at the position it renders: a call-shaped `Lit` (`literalColumn` is `columnExpr`'s `primitive` alternative, `Fn` being the call route), an aggregate-shaped argument inside `Fn` (aggregates are admitted as a top-level `columnExpr` alone), a function-shaped comparison operand in either bracket carrier (`pathPredicateOperand : primitive | objectPath | PARAMETER | ID_CODE | AT_CODE` has no `functionCall`), and a `VersionPredicate` shape outside the three § The version-predicate carrier seals, reachable by embedding the exported interface, which is refused rather than panicking ([idiom.md § No panics](idiom.md#errors-req-025)).

**Read-side mirror duty.** For **every** construct this requirement adds, `Build()` → `parse.ParseQuery` → `(*parse.Query).Emit` **MUST** be **byte-identity**, not merely re-parseable. Identity is the right bar: the read side re-emits a class bracket verbatim and normalises a projected function name, so anything weaker would let the two sides disagree about the canonical spelling of a construct they both model, a disagreement invisible to a parseability check. § Canonical spellings for the new constructs is what makes identity reachable.

### `Col` stays lenient, and `Build()` verifies what it emitted

`aql.Col(path)` renders its argument into the projection list verbatim, with no check beyond emptiness, so `Col("COUNT(x) AS n")` builds, and `Col("a, b")` would build into two projections. Two rules settle it, opposite in direction because the two failure modes are.

**1. `Col` keeps its signature and its leniency.** A `Col` whose text re-parses as a **single** projected item *and* introduces **no clause-level flag the builder did not record** (a function call, an aliased item, a path) **MUST** be accepted: it is loud, ordinary AQL that says what the caller wrote, and refusing it would break callers for no correctness gain. This applies § REQ-119's own rule, that refusal is reserved for the silent-substitution mode. The typed constructors above are the recommended route and their godoc says so; `Col` is not deprecated.

**2. `Build()` verifies the projection it emitted.** `Build()` reads the emitted `SELECT` clause back once and refuses, as [§ REQ-119 § Emission verified after emission](#req-119--re-parseable-canonical-aql-emission) requires, a projection whose structure changed: a `Col` whose text splits into two or more items, spills out of `SELECT` into another clause, or adds a clause-level flag is the silent mode, valid AQL asking a different question. The compared structure **MUST** include the item count, each item's `AS` alias and the clause-level flags (`DISTINCT`, and the deprecated `TOP` with its `FORWARD` / `BACKWARD` direction, which `top : TOP INTEGER direction?` consumes into the clause as `selectClause` consumes `DISTINCT`), compared after factoring out the encodings the emitted text erases: a sole unaliased star item and the bare `SELECT *` flag are one encoding, path text enters its slot with edge whitespace trimmed, and a closed top-level comment run reads as whitespace. A `Col` text that leaves a lexical region **open** where the clause ends (a string literal, a comment run, a bracket or a parenthesis) **MUST** be refused, even where it would read back unchanged: what closes the region is the text after the projection, so the same text is a loud error in one query and a silent substitution in the next. No typed constructor produces such a region, so the refusal reaches only a legacy `Col` carrying half a token.

So `Col("COUNT(c/uid/value) AS n")` and `Col("-- note\nc/uid/value")` are accepted, while `Col("DISTINCT c/uid/value")` (one item plus an unrecorded `DISTINCT`), `Col("a, b")` (two items), `Col("BACKWARD c/uid/value")` beside a recorded `Top(5)` (one item plus an unrecorded direction, a byte-stable query for the *last* five rows), `Col("-- x\n*")` (the parser reads the bare star form, the builder recorded one non-star item) and a `Col` leaving a region open are refused. The refusal follows the value-free rule of [§ REQ-119 § The emission closure property](#req-119--re-parseable-canonical-aql-emission): it names the item index and the clause, never the projection text or the parser's own message.

`openehr/aql` cannot import `openehr/aql/parse`, which imports it, so `Build()` reaches this decision by its own reading of the clause, with the parser as the reference the tests confront it with; the choice of means never weakens the exactness above. The version and standing brackets are not part of this check: neither carrier takes bracket text, both rendering `<path> <op> <value>` from a typed comparison under their own guards, so the projection is the one clause a caller's own free text still enters.

### Canonical spellings for the new constructs

These spellings are **additions** to the canonical write form whose home is [§ REQ-055](wire.md#req-055--wire-boundary), not amendments to it: no rule there changes and no existing golden is rewritten. Each is what `(*parse.Query).Emit` produces at that position, and any other spelling would break the mirror duty's byte identity. `Build()` and `Emit` **MUST** emit the spellings in this table:

| Construct | Canonical spelling |
|---|---|
| Containment junctions and negation | One space around `AND`, `OR` and `NOT CONTAINS`; parentheses only where precedence requires them. |
| In-text paging | `LIMIT n[ OFFSET m]`, emitted after `ORDER BY` in clause order. |
| `TOP` (deprecated) | `SELECT [DISTINCT ]TOP <n>[ FORWARD\| BACKWARD] <items>`: keywords upper-cased regardless of source casing, single spaces, the direction only where the source or the builder set one. |
| Projected function and aggregate names | **Uppercase ASCII.** Required for identity, not taste: the extractor upper-cases every projected name while the emitter renders the name as carried, so a lower-case builder spelling comes back upper-cased and the round trip is not identity. The upper-casing **MUST** be ASCII-only: a Unicode mapping folds some non-ASCII letters *into* the ASCII alphabet (`ı` → `I`) and so turns a spelling the lexer cannot tokenise into a legal-looking one, the rule the read side already states for itself. |

`Build()` **MUST** emit the spellings in the next table as well; `Emit` renders the same ones, except a class bracket it re-emits verbatim (§ REQ-119).

| Construct | Spelling |
|---|---|
| Version keywords | `VERSION v[LATEST_VERSION]` / `[ALL_VERSIONS]`: uppercase, no padding inside the brackets. The casing follows [§ REQ-055](wire.md#req-055--wire-boundary) rule 1's keyword *principle*, not its enumeration, which is closed over the clause keywords and names neither these nor `TOP`. The read side matches them case-insensitively and re-emits the bracket verbatim, so identity requires the write side to pick exactly one spelling. |
| A comparison in either bracket | `<path> <op> <value>`, **one space each side of the comparison operator**, no padding inside the brackets: `vo[uid/value = $vo]`, `v[commit_audit/time_committed > $since]`. This is what `aql.Comparison` already renders in `WHERE`, so the builder keeps **one** comparison renderer rather than two that can drift. The path is trimmed of EDGE whitespace on intake, as `aql.Builder` already trims its identifier positions (§ REQ-119 § Single-token identifier positions): the trim widens the accept set by one harmless equivalence and cannot manufacture a splice, and without it a padded path would be a second spelling of one bracket — padding this row forbids. |
| `DISTINCT` (clause) | Uppercase, directly after `SELECT` and **before** the deprecated `TOP` clause — `selectClause : SELECT DISTINCT? top? selectExpr …` — one space after. |
| `AS` | Uppercase, one space each side: `COUNT(c/uid/value) AS n`. |
| An aggregate's `DISTINCT` argument | `COUNT(DISTINCT c/uid/value)` — uppercase, one space after; arguments comma-separated with one space after each comma, the spelling REQ-055 rule 5 fixes for the item list. |
| Star | `COUNT(*)` with no padding; a sole unaliased star item emits as the bare `SELECT *` form, which is how it re-parses. |

### Additivity

No [§ REQ-161](#req-161--aql-semantic-and-portability-lint) code, severity or `Detail` text changes, and verification stays opt-in and reports the containment codes only ([§ REQ-161 § Builder adapter](#builder-adapter)). What changes is **reachability**: shapes that were builder-inexpressible become buildable, so [PROBE-097](conformance.md#probe-097--aql-semantic-and-portability-lint-corpus) arm (c) gains rows and its catalogue caveat narrows. The additions extend [PROBE-088](conformance.md#probe-088--aql-builder-containment-and-paging-stability)'s fixture set rather than re-baselining it.

### Acceptance

Each new construct is tested to build, emit and pass the identity round trip `Build → ParseQuery → Emit`, and the verb functions and the struct builder emit the same strings for it. A builder-emitted `… CONTAINS VERSION v[LATEST_VERSION]` draws no `aql_version_no_predicate` from `lint.LintString`, and REQ-161's suppression shape `… CONTAINS VERSIONED_COMPOSITION vo[uid/value = $vo] CONTAINS VERSION v[ALL_VERSIONS]` builds end to end, draws no `aql_versioned_object_unreferenced`, and gets the same containment codes from `(*aql.Builder).VerifyContainment` as from the linter. Each refusal has a named test that fails when its guard is removed, the `VersionPredicate` row asserting a returned `aql.ErrInvalidQuery` rather than a recovered panic. Each `Col` shape above has its own row with its expected verdict, one per region kind for the open-region refusal, and the accept direction has rows of its own, one per encoding the emitted text erases, so an over-refusal fails as surely as a missed splice.

### Out of scope

- **A FROM-root standing predicate.** [§ REQ-055](wire.md#req-055--wire-boundary) rule 6 keeps the `WHERE <alias>/ehr_id/value = $param` form deliberately, noting the `EHR e[ehr_id/value=$param]` spelling is equally valid AQL and not what the builders emit. This REQ adds the standing predicate to `CONTAINS` operands and does not disturb that choice.
- **A FROM-root archetype predicate** — separately unreachable and recorded in PROBE-097; unchanged here.
- **A FROM-root version predicate** — the third spelling of the same position, and deferred with the other two so the deferral is one fact rather than a list that reads short. `Builder.From` takes an RM type and an alias and nothing else, so the root carries no bracket in ANY spelling: `FROM VERSION v` builds and stays predicate-less, and `aql.Version` places its bracket on a `CONTAINS` operand. This is what [PROBE-097](conformance.md#probe-097--aql-semantic-and-portability-lint-corpus) records as the residual unreachable shape.
- **A FROM-root containment junction** (`FROM COMPOSITION c1 OR COMPOSITION c2`, which the read side models via `parse.FromClause.Junction`): the builder keeps a single root class until a consumer needs write-side root junctions, so `Builder.From` / `Builder.FromEHR` take one class and a builder-emitted FROM root is never parenthesised.
- **A parameterised `TOP`.** `top : TOP INTEGER direction?` admits no `PARAMETER` ([§ REQ-113 § The `TOP` carrier](#req-113--execution-oriented-parsed-aql-ast)), so there is nothing to add.
- **The class position's other bracket alternatives** — a `nodePredicate` junction, a node id, a name slot, a regex match. All are legal AQL that [§ REQ-113 § Structured node predicates](#req-113--execution-oriented-parsed-aql-ast) already structures on the read side and that no builder carrier spells. Adding them is a widening of the write vocabulary and rides its own requirement; until then the read/write parity this REQ establishes is bounded by the `standardPredicate` and `archetypePredicate` alternatives, and § The standing-predicate carrier says so.
- **Deprecating or narrowing `Col`.** Settled the other way above, deliberately.

- **Probes:** [PROBE-088](conformance.md#probe-088--aql-builder-containment-and-paging-stability) (the builder golden set and its refusals); [PROBE-097](conformance.md#probe-097--aql-semantic-and-portability-lint-corpus) arm (c) (the read/write parity corpus).

## REQ-164 — AQL path-shape and paging lint

[§ REQ-109](#req-109--aql-static-lint)'s Layer 2 **MUST** carry a third additive check group, **path-shape checks**: five codes covering authoring rules the other groups do not reach, namely an identified path stepping through an unconstrained **repeating** RM attribute, a **row-bounded** query with no total order, an **unaliased** projection, the *path* source of engine-defined row multiplicity, and a **containment step that provably does nothing**. The layer contract is preserved and not restated: AST walk, collect-all, no CDR, no OPT ([§ Layer 2](#layer-2--shape-ast-walk-no-cdr)). The RM facts come from the pinned BMM through `openehr/rm/rminfo` ([REQ-048](bmm-conformance.md#req-048--rm-meta-model-introspection-surface)), the same pin [§ REQ-160](#req-160--aql-containment-admissibility-relation)'s relation is derived from, so no new input is needed to run any of these checks.

Each rule below is stated as a rule by the openEHR authoring guidance and is decidable from the query text plus the pin. Path shape is otherwise covered only by the OPT-gated Layer 3. The consumers are the ones [§ REQ-109 § Layer 2](#layer-2--shape-ast-walk-no-cdr) already serves: anyone holding a query string, most valuably CI over a stored-query catalogue.

### Path-shape checks

| Check | Code | Severity | Rule |
|---|---|---|---|
| Unconstrained repeating segment | `aql_path_repeating_unpredicated` | Warning | An identified path segment **MUST** raise this code exactly when it types to a **multi-valued** RM attribute (`rminfo` `IsContainer`) and carries **no predicate** of any kind (a node id, a name and a standing comparison all count: presence suffices and content is **not** judged, § The conservative segment walk), once per offending segment, with `Span` on that segment, in **every** identified path the document records (`SELECT`, `WHERE` and `ORDER BY` alike, `parse.Document.Paths`): a `WHERE` filter or an `ORDER BY` key over an unconstrained repeating segment leaves the same which-occurrence question to the engine as a projected path. Whether `[at0006]` is the *right* node id is a template question owned by Layer 3's `aql_path_not_in_template`. |
| Row bound without a total order | `aql_paging_no_order_by` | Warning | A query **MUST** raise this code exactly when it carries a **row bound** and no `ORDER BY`, at most once per query, `Detail` naming the channel(s) that carried the bound. A row bound is the **in-text** `LIMIT` clause (`parse.Document.HasLimit`; the profile's `limitClause` admits no `OFFSET` without a `LIMIT`, so keying on `LIMIT` misses no in-text spelling) or a supplied `Options.Query` whose `Fetch` **or** `Offset` is non-zero. Without a total order a page boundary is engine-defined, so successive pages can repeat or drop rows. A nil `Options.Query` leaves the envelope arm unable to fire, as it leaves the parameter-binding checks ([§ REQ-109 § Issue model and entry points](#issue-model-and-entry-points)), and a deprecated `TOP` is not a row bound here, because `aql_deprecated_top` already carries the `ORDER BY` remedy for that clause and one defect gets one finding. The envelope arm reads `Offset` as well as `Fetch`, unlike `aql_top_with_fetch`'s fetch-only scope: that code reports an exclusion the Query API *states*, while this one reports an unstable page boundary, which an offset into an unordered result produces on its own. |
| Unaliased projection | `aql_select_no_alias` | Warning | A `SELECT` item **MUST** raise this code exactly when it is not a `*` item and carries no `AS` alias, once per item, with `Span` on the item where the item has a position of its own (a bare path) and the **zero `Span`** otherwise (a function-call or literal item, which `Detail`'s item ordinal locates instead), REQ-109's answer for an issue not attributable to a position ([§ REQ-109 § Value-free lint diagnostics](#value-free-lint-diagnostics)). A stored-query contract and every column-addressed result reader depend on stable column names, and an unaliased column's name is engine-defined. A `*` item is REQ-109's `aql_select_star`; a **bare alias** item (`SELECT o`) is **not** exempt, because it names no column either. |
| Path row grain | `aql_fanout_path_grain` | Warning | A query **MUST** raise this code exactly when two projected identified paths rooted on the **same** alias diverge after their longest common prefix, **each** passing at least one unpredicated multi-valued segment at or after the divergence: the Cartesian-product shape, whose row multiplicity is engine-defined (result-shape semantics are an open specification question, SPECQUERY-9), which `Detail` states as its sibling's does. It fires **once per alias**, not once per pair: the first offending pair in document order fixes the `Span` (the later path of that pair) and is named in `Detail`, so a wide projection yields one advisory rather than a quadratic report. So it stays silent on two paths whose multi-valued segments are all in their **common prefix** (one repeating scope, no product), on a pair in which **either** path predicates every multi-valued segment at or after the divergence, on paths rooted on **different** aliases (the junction question, `aql_fanout_row_grain`, REQ-161), and on a bare `SELECT *`, which projects no identified path (the star's row-grain question belongs to the junction code). The two codes are disjoint by construction: this one needs two paths under one alias, that one two projected aliases under one `AND` junction. |
| Redundant containment step | `aql_contains_redundant_step` | Warning | A `CONTAINS` operand **MUST** raise this code exactly when **all** of the following hold: it is **not** the FROM root; it is **not** a leaf of the containment tree; it carries **no class-position predicate** of any kind, archetype, standing or version (`parse.ClassExpr.HasPredicate` false); its alias roots **no** identified path outside FROM/CONTAINS; it sits inside no containment **junction** and under no **negation**; its class does not conform to `VERSIONED_OBJECT` (§ No double-reporting); and its class is **unavoidable** under the REQ-160 relation, every containment route from its parent operand's class to its child operand's class passing through it. Removing such a step provably changes no result: `EHR e CONTAINS COMPOSITION c CONTAINS OBSERVATION o` with `c` unreferenced, where every EHR→OBSERVATION route passes `COMPOSITION`. The rule is narrower than the guidance sentence it comes from ("containment is minimal"), and the narrowing is its substance: an **avoidable** intermediate narrows the result (removing `SECTION s` from `… CONTAINS SECTION s CONTAINS OBSERVATION o` admits observations outside sections), an unreferenced **leaf** is an existence filter, and inside a junction or under a negation removing the step changes the junction's arity or the excluded set, which the relation alone cannot prove inert. |

Every code above is **Warning** and every rule is **conservative**: where a fact is not provable from the query text plus the pin, the check **MUST** stay silent rather than guess. [§ REQ-161 § Flagging policy](#flagging-policy) is the canonical home of that rule for Errors; this group has no Error-severity member.

### The conservative segment walk

The repeating-segment check, and the divergence test `aql_fanout_path_grain` builds on it, share one walk. It starts at the class the path's alias binds (`parse.Document.Classes`), types each step through `rminfo`'s flattened attribute typing, and reads multiplicity from `IsContainer`. Segment predicate presence is read from the verbatim `parse.PathSegment` predicate text ([§ REQ-113](#req-113--execution-oriented-parsed-aql-ast)): presence only, never content, so no predicate spelling has to be understood for the check to be sound.

The walk ends **silently**, with no issue on that segment and none on any segment beyond it, at the first step it cannot type, and never guesses or descends a sibling. It stops at a **class the pin does not know** (the alias's own class included); at an **attribute the pin does not declare** on the current class, own or inherited; at an attribute whose declared type is **not a class of the universe**, which includes a BMM **generic parameter** (on the current pin `EVENT.data` is typed `T`, exactly as `ORIGINAL_VERSION.data` is, and [REQ-048](bmm-conformance.md#req-048--rm-meta-model-introspection-surface) leaves generic-parameter resolution out of scope; [§ REQ-160 § Overlay edges](#overlay-edges-default-relation) records the same fact); and at a **`$param` archetype scope**, whose extent the CDR resolves at execution, the skip [§ REQ-109 § Layer 3](#layer-3--path--template-only-when-a-compiled-opt-is-supplied) and [§ REQ-161 § Checks](#checks) apply for the same reason. This is the Layer-3 false-positive policy applied to a check that needs no OPT: a false Warning on a legal path is worse than a missed one, because the consumer that runs this in CI cannot tell them apart.

**The walk's reach on the current pin is bounded, and the bound is a property of the pin, not of this contract.** `OBSERVATION/data` types to `HISTORY` (single-valued) and `HISTORY/events` to `EVENT` as a container, the anchor case, which fires when unpredicated; the walk then stops at `EVENT/data`'s generic `T`. A path continuing `…/items/value/magnitude` therefore raises one issue, on `events`, and not one per repeating segment further down. The bound narrows where `aql_fanout_path_grain` can be witnessed without disabling it: on that canonical shape the one reachable container (`events`) sits in the two paths' common prefix, so a firing pair is one whose repeating segments are typed before the stop. `SELECT o/data/events/time, o/links/meaning/value` diverges at the alias with an unpredicated container on each branch (`HISTORY.events` and `LOCATABLE.links`) and fires. Widening the reach means carrying the RM's generic constraints as cited data in the BMM band, not changing this check (§ Out of scope).

The walk's two codes and the two parse-only codes (`aql_paging_no_order_by`, `aql_select_no_alias`) put no question to the relation. `aql_contains_redundant_step` asks a containment-route question, which is what an overlay edge states, so it **MUST** be asked of the relation **in use** ([§ REQ-161 § Relation supply](#relation-supply)): consulting the default instead would raise a false finding on the dialect deployment [§ REQ-160 § Extensibility](#extensibility) exists to serve. That is governance, not gating: nil selects the default relation (§ Always on, never gated).

### Always on, never gated

All five codes are Warnings, so none of them flips `Result.OK()` ([§ REQ-109 § Issue model and entry points](#issue-model-and-entry-points)). They **MUST** run whenever Layer 2 runs, with no option to enable them: a caller who does not want one filters the result by `Code`, which is value-free and stable, and a caller who gates CI on Warnings has opted into exactly this class of advice. An `Options` field switching the group on would buy nothing, since the group has no Error member to hold back, and would give a nilable `Options` field a third meaning beside `Relation`, which selects a default, and `Compiled` and `Query`, which gate checks that have no input without them.

### No double-reporting

The four guidance rules and the **two** documented sources of engine-defined row multiplicity are each covered by exactly one code. Where a shape could attract two, this section fixes the owner:

- `aql_versioned_object_unreferenced` (REQ-161) **owns** the unreferenced version container: an operand whose class conforms to `VERSIONED_OBJECT` ([§ REQ-160 § Containable operands](#containable-operands): conformance, not a name list) keeps that code and draws no `aql_contains_redundant_step`. The REQ-164 check is the general case of the REQ-161 one, so the general case yields to the specific.
- `aql_fanout_row_grain` (REQ-161) owns the **junction** source; `aql_fanout_path_grain` owns the **path** source. REQ-161's catalogue row carries the boundary sentence and neither row restates the other's rule.
- `aql_path_repeating_unpredicated` (multiplicity, no OPT) and `aql_path_not_in_template` (Layer-3 membership, OPT-gated) report **different** defects and can both fire on one path; neither suppresses the other.
- `aql_deprecated_top` / `aql_top_with_limit` / `aql_top_with_fetch` (REQ-109) own the deprecated `TOP` clause, including its `ORDER BY` remedy, so `aql_paging_no_order_by` stays off a `TOP`-only query (§ Path-shape checks).
- `aql_select_star` (REQ-109) owns the `*` item.

### Additivity

- No REQ-109 or REQ-161 **code, severity, `Detail` text, `Span` rule or `Result.OK()` semantic** changes, and no entry point changes. REQ-161's catalogue carries one scope-boundary sentence on its `aql_fanout_row_grain` row, and no rule.
- The issue model is REQ-109's ([§ REQ-109 § Value-free lint diagnostics](#value-free-lint-diagnostics)), with `Span` on the offending segment, projection item, path or class expression as each row above states.
- The PROBE-028 re-baseline follows [§ REQ-161 § Additivity](#additivity), and is recorded in [PROBE-099](conformance.md#probe-099--aql-path-shape-lint-corpus)'s catalogue entry.
- Consumers gating CI on Warnings see new findings on unchanged queries; that is the feature, and the per-code filter is the opt-out (§ Always on, never gated). No finding of this group can turn a passing result into a failing one.

### Acceptance

Every firing rule and every silence rule above has a named test, and each guard a test that fails when it is removed. The corpus carries three firing witnesses: the unpredicated repeating-segment projection over an `OBSERVATION` alias, a `LIMIT 50 OFFSET 100` query with no `ORDER BY`, and a repeating unpredicated segment whose path appears only in `WHERE`, which an implementation narrowed to the projection fails. The silence direction has a row per near-miss, so an over-firing linter cannot pass: a predicated repeating segment; `ORDER BY` beside a `LIMIT`; a nil `Options.Query`; a `TOP`-only row bound; an aliased projection item; a `*` item; two projected paths whose repeating segments are all in their common prefix; two projected paths on different aliases; an avoidable unreferenced intermediate; an unreferenced leaf; and a `VERSIONED_OBJECT`-conforming operand, which carries REQ-161's code and not this group's. The walk's silent stops are pinned by name (an unknown alias class, an attribute the pin does not declare, the generic-parameter stop at `EVENT.data`, a `$param` archetype scope), severity is pinned per code, and a `Result` carrying only this group's findings reports `OK()` true. [PROBE-099](conformance.md#probe-099--aql-path-shape-lint-corpus) carries the corpus, mirroring [PROBE-097](conformance.md#probe-097--aql-semantic-and-portability-lint-corpus)'s per-code positive and negative near-miss structure.

### Out of scope

- **OPT-aware path checking and node-id correctness**: Layer 3's, and unchanged; terminology and function-signature checking stay out, per [§ REQ-109](#req-109--aql-static-lint) and § REQ-161 § Out of scope.
- **Resolving a BMM generic parameter to its RM constraint.** The RM constrains the generic the pinned tables carry as `T`, but the pin does not express the constraint and REQ-048 does not resolve it, so the walk stops there (§ The conservative segment walk). Widening the reach would be **cited data in the BMM band**, reviewed on a pin bump like REQ-160's overlay table, and is its own requirement, not a change to this check.
- **Row-semantics adjudication**, as [§ REQ-161 § Checks](#checks) states it: the two fan-out advisories are the entire footprint.
- **Rewriting a query.** No suggested alias, no suggested predicate, no auto-fix: these codes advise, they never author. `Detail` names the defect and its location, and nothing in this group edits or emits AQL.
- **Any promotion of these checks to Error severity**, and any option gating them (§ Always on, never gated).
